Chapter 2 the Observer Pattern

Keeping your Objects in the Know

One object changes state, and an unknown number of other objects need to know about it — right now, and without being welded together. That is the whole idea behind the pattern that runs through Swing, JavaBeans and most GUIs you have ever clicked.

Part 1the contract

You won the Weather-O-Rama contract

Chapter 1 taught you to encapsulate what varies. Chapter 2 hands you a real client with a real deadline. Your team has just won the contract to build Weather-O-Rama, Inc.’s next-generation, internet-based Weather Monitoring Station. The good news: they are paying you in stock options. The other news: they want three displays, real-time updates, and a marketplace for displays that other developers will write later.

What the client is giving you

Weather-O-Rama supplies the physical weather station (temperature, humidity and pressure sensors) and the WeatherData object that talks to it. Your job is the part they did not write: the displays, and the glue between the data and the displays.

  • Three displays, to start: current conditions, weather statistics, and a simple forecast.
  • Real time: every display updates as soon as new measurements arrive.
  • Expandable: new displays — written by anyone — should plug in without touching the existing code.
  • Add and remove at runtime: the customer should be able to switch displays on and off.
Remember the constant: change. Chapter 1’s lesson applies directly — the number and type of displays is the thing that varies, so that is the thing to encapsulate.

The application overview

Three components: the weather station (hardware that acquires the data), the WeatherData object (tracks the data and updates the displays) and the display device (shows the user what is going on).

Unpacking the WeatherData class

The source files Johnny Hurricane attached are short. WeatherData has three getters for the latest measurements, and one method that matters:

WeatherData.javathe part you must fill in
public class WeatherData {
    // instance variable declarations

    public float getTemperature() { /* most recent temp */ }
    public float getHumidity()    { /* most recent humidity */ }
    public float getPressure()    { /* most recent pressure */ }

    /*
     * This method gets called
     * whenever the weather measurements
     * have been updated
     */
    public void measurementsChanged() {
        // Your code goes here
    }

    // other methods
}

You never call measurementsChanged() yourself — the station calls it whenever fresh values arrive. Your only job is to make that method tell the displays.

Our goal

Update every display whenever measurementsChanged() fires. Sounds like three lines of code. It is — and they are the wrong three lines, which is exactly why this chapter exists.

Stretch goal: let users add (or remove) as many display elements as they want. We know about the first three display types, but Weather-O-Rama expects “a vibrant marketplace for new displays in the future.” Any design where the set of displays is baked into WeatherData fails this before it ships.
Part 2the first, misguided implementation

Three lines that look fine (they aren’t)

Here is the implementation everyone writes first. Grab the latest measurements, then call update() on each display you know about.

WeatherData.javafirst attempt
public class WeatherData {
    // instance variable declarations

    public void measurementsChanged() {
        float temp = getTemperature();
        float humidity = getHumidity();
        float pressure = getPressure();

        currentConditionsDisplay.update(temp, humidity, pressure);
        statisticsDisplay.update(temp, humidity, pressure);
        forecastDisplay.update(temp, humidity, pressure);
    }

    // other WeatherData methods here
}

What’s wrong with it?

Look at it through Chapter 1’s glasses. Almost every line is a principle violation:

  • We code to concrete implementations. WeatherData now names three specific display classes. A fourth display means editing this method.
  • Every new display changes this code. The class that holds the data is the class that keeps growing.
  • No adding or removing at runtime. The list of displays is hardcoded in a method body.
  • Nothing here is encapsulated. “The part that changes” is the set of displays — and it is sitting in the middle of WeatherData.

One thing it does get right: all three displays happen to have an update(temp, humidity, pressure) method, so at least it talks to them through a common shape. Chapter 2 turns that accident into an actual interface.

Exercise (book, page 42): which apply?

Based on the first implementation, which of the following apply? (Choose all that apply.)

The book’s answer: A, B, C and E. D is tempting but the code does use a uniform update() signature — it just never declares an interface. F is a red herring: WeatherData’s own fields are still private. The encapsulation problem is that change (which displays exist) was never pulled out.
Part 3meet the pattern

Publisher + subscribers = Observer

Forget code for a moment. You already know this pattern — you have subscribed to a newspaper, a channel or a mailing list.

  1. 1
    A newspaper publisher goes into business and begins publishing newspapers.
  2. 2
    You subscribe to a particular publisher, and every time there’s a new edition it gets delivered to you. As long as you remain a subscriber, you get new newspapers.
  3. 3
    You unsubscribe when you don’t want papers anymore, and they stop being delivered.
  4. 4
    While the publisher stays in business, people, hotels, airlines and other businesses constantly subscribe and unsubscribe.

Rename the roles and you have the pattern: the publisher is the SUBJECT, the subscribers are the OBSERVERS. The subject owns the data; the observers ask to be told when it changes; nobody has to know anybody’s name.

A day in the life of the pattern

Three moves: register, notify, remove. Everything else in this chapter is detail.

Look at what the arrows actually say: the Duck’s request is labelled “register/subscribe me”, the subject then pushes its new value — the int 8 — to every observer in the list, and when the Mouse gets tired of receiving ints it asks to be removed, the subject takes it off the list, and the next notification goes to everyone except the Mouse. No recompiling, no flags, no “is the mouse still interested?” checks sprinkled through the subject. That is loose coupling in one picture.

The rest of the skit (pages 49–50)

The headhunter notifies every observer when a Java job appears. Jill takes the job and asks to be taken off the list — an observer removing itself at runtime. The headhunter is furious; the pattern does not care.

Two weeks later: Lori is still an observer, but she now keeps her own call list and notifies her own observers. She is a subject and an observer at the same time. Nothing in the pattern forbids it: the interfaces are roles, not a hierarchy.

☯
The Observer Pattern

The Observer Pattern defines a one-to-many dependency between objects so that when one object changes state, all of its dependents are notified and updated automatically.

The class diagram

Most implementations of the pattern look like this: a Subject interface and an Observer interface, plus concrete classes that implement them.

Q: Where does “one-to-many” come from? The subject is the one object that contains the state and controls it. The observers use the state — many of them, all relying on the subject to tell them when it changes. One subject, many dependents.
Q: Is Publish-Subscribe the same thing? No, though they are related. Publish-Subscribe is a more complex pattern: subscribers can express interest in different types of messages, and publishers are separated further from subscribers. Observer is the simpler, in-process version.
Part 4why the pattern is worth it

The power of loose coupling

Observer’s real gift is not notifications — it is that the subject and its observers know almost nothing about each other. Head First makes the point with a guru, a woven basket, and the chapter’s one new design principle.

☯
Design Principle · the fourth one

Strive for loosely coupled designs between objects that interact.

Loosely coupled objects still interact — they just know very little about each other. The Observer Pattern is the textbook example, and the book lists exactly why:

  • The subject only knows the interface. It knows an observer implements Observer; not its concrete class, not what it does with the data.
  • Add observers at any time. New observers just register; the subject keeps working, even if you swap an observer mid-flight.
  • Never modify the subject for a new observer type. Implement the interface, register, done.
  • Reuse either side independently. A subject is useful without these particular observers; an observer is useful with a different subject.
  • Changes stay local. Either side can change as long as it honors the interface.

The guru’s definition is the one to remember: “A loosely coupled object doesn’t know or care too much about the details of another object” — and that is exactly the relationship between WeatherData and a display it has never heard of.

The book puts the payoff plainly: loosely coupled designs let us build flexible OO systems that handle change, because they minimize the interdependency between objects. You will see this principle again in almost every pattern that follows.

Part 5designing the weather station

Cubicle conversation → class diagram

Mary and Sue work it out the way you should: start from the definition, map the roles onto the problem, then look for the common interface.

How the conversation goes

Mary: the WeatherData class is the “one” — it has the state (temperature, humidity, pressure). The displays are the “many”. When the measurements change we notify all of them.

Sue: so the displays register themselves with WeatherData. And since every display is different, they need a common interface, so WeatherData knows how to send them the measurements.

Mary: every display gets an update() method, defined in a common interface that all the elements implement.

The design in one sentence: WeatherData implements Subject; the displays implement Observer (and DisplayElement); the subject keeps a list of Observers and pushes new measurements to all of them.
What is still undecided: how the measurements travel. The displays all have an update() method, but should the subject hand over its values, or let each display ask for what it needs? That question returns on page 68 as the push-vs-pull debate — and it is the reason the Observer interface has two possible signatures.

Three interfaces

Subject.java · Observer.java · DisplayElement.javapage 58
public interface Subject {
    public void registerObserver(Observer o);
    public void removeObserver(Observer o);
    public void notifyObservers();
}

public interface Observer {
    public void update(float temp, float humidity, float pressure);
}

public interface DisplayElement {
    public void display();
}

registerObserver() and removeObserver() take the observer to add or drop; notifyObservers() is called when the subject’s state changes. update() is the one method every observer must have, and display() is the one method every display must have — that is the whole contract.

Implementing Subject in WeatherData

WeatherData.javathe subject
public class WeatherData implements Subject {
    private List<Observer> observers;
    private float temperature;
    private float humidity;
    private float pressure;

    public WeatherData() {
        observers = new ArrayList<Observer>();
    }

    public void registerObserver(Observer o) {
        observers.add(o);
    }

    public void removeObserver(Observer o) {
        observers.remove(o);
    }

    public void notifyObservers() {
        for (Observer observer : observers) {
            observer.update(temperature, humidity, pressure);
        }
    }

    public void measurementsChanged() {
        notifyObservers();
    }

    // test harness for the displays
    public void setMeasurements(float temperature,
                                float humidity,
                                float pressure) {
        this.temperature = temperature;
        this.humidity = humidity;
        this.pressure = pressure;
        measurementsChanged();
    }

    public float getTemperature() { return temperature; }
    public float getHumidity()    { return humidity; }
    public float getPressure()    { return pressure; }
}

What changed, and why it matters

  • WeatherData now implements the Subject interface, so any observer can rely on the three methods existing.
  • An ArrayList<Observer> replaces the three named display fields. It is created in the constructor.
  • registerObserver() appends; removeObserver() removes. Both happen at runtime.
  • notifyObservers() is the fun part: because every element is an Observer, we know it has update(), so we can call it on all of them without knowing what they are.
  • setMeasurements() is not in the station’s real API — it is the test harness the book adds because the publisher would not ship a weather station with each copy.
Book’s footnote: the listings omit import and package statements on purpose; the complete source is on the book’s companion site, wickedlysmart.com.

The display elements

CurrentConditionsDisplay.javaobserver + display element
public class CurrentConditionsDisplay implements Observer, DisplayElement {
    private float temperature;
    private float humidity;
    private WeatherData weatherData;

    public CurrentConditionsDisplay(WeatherData weatherData) {
        this.weatherData = weatherData;
        weatherData.registerObserver(this);
    }

    public void update(float temperature, float humidity, float pressure) {
        this.temperature = temperature;
        this.humidity = humidity;
        display();
    }

    public void display() {
        System.out.println("Current conditions: " + temperature
            + "F degrees and " + humidity + "% humidity");
    }
}

The constructor is the registration: the display is handed the subject and immediately puts itself on the list. update() stores what it needs and calls display(). display() prints. That is a complete observer.

Two good questions from the book: is update() the best place to call display()? Not really — MVC will fix that properly. And why keep the weatherData reference? So the display can un-register itself later.
The other two displays, in the book’s source download

The statistics display keeps running min/max/sum/numReadings and prints Avg/Max/Min temperature = 80.0/82.0/78.0. The forecast display keeps lastPressure and currentPressure: pressure rising means “Improving weather on the way!”, falling means “Watch out for cooler, rainy weather”, unchanged means “More of the same”. Both are ordinary observers — same update(), different display().

public class HeatIndexDisplay implements Observer, DisplayElement {
    private float heatIndex = 0.0f;
    private WeatherData weatherData;

    public HeatIndexDisplay(WeatherData weatherData) {
        this.weatherData = weatherData;
        weatherData.registerObserver(this);
    }

    public void update(float t, float rh, float pressure) {
        heatIndex = computeHeatIndex(t, rh);
        display();
    }

    public void display() {
        System.out.println("Heat index is " + heatIndex);
    }

    private float computeHeatIndex(float t, float rh) {
        float index = 16.923f + 0.185212f * t + 5.37941f * rh
            - 0.100254f * t * rh + 0.00941695f * t * t
            + 0.00728898f * rh * rh + 0.000345372f * t * t * rh
            - 0.000814971f * t * rh * rh
            - 0.000038646f * t * t * t + 0.0000291583f * rh * rh * rh
            + 0.00000142721f * t * t * t * rh
            + 0.000000197483f * t * rh * rh * rh
            - 0.0000000218429f * t * t * t * rh * rh
            + 0.000000000843296f * t * t * rh * rh * rh
            - 0.0000000000481975f * t * t * t * rh * rh * rh;
        return index;
    }
}

Do not type the formula — the book says copy it from heatindex.txt. The point of the exercise is that a brand-new display needs zero changes to WeatherData: implement Observer and DisplayElement, register in the constructor, done.

The pattern’s payoff, in one screenshot: adding a display meant adding a class. The subject’s code stayed exactly as it was — which is precisely the “open for extension” behavior Weather-O-Rama is selling.

Push vs. pull: the fireside chat (pages 63–64)

Subject and Observer argue about the right way to hand over state. Push: the subject sends all its state in every notification. Pull: the subject only says “something changed”, and each observer asks for what it needs through getters.

The Subject’s case for push: “I have to send my state with my notifications so all you lazy Observers will know what happened.” One notification, everything included — convenient.
The Observer’s case for pull: “There are so many different kinds of us — just let us come to you for the state we need.” Add wind speed tomorrow and push forces every observer to change its update() signature; pull changes only the subject.

The book agrees with the Observer, cautiously: whether you push or pull is an implementation detail, but in a lot of cases it makes sense to let observers retrieve the data they need. So it takes a second pass at the design.

Observer.java · WeatherData.javaswitching to pull
public interface Observer {
    public void update();          // no arguments!
}

// in WeatherData
public void notifyObservers() {
    for (Observer observer : observers) {
        observer.update();
    }
}

// in CurrentConditionsDisplay
public void update() {
    this.temperature = weatherData.getTemperature();
    this.humidity = weatherData.getHumidity();
    display();
}
Three small edits: (1) notifyObservers() calls update() with no arguments, (2) the Observer interface’s update() loses its parameters, (3) each concrete observer pulls the values it wants through the subject’s getters.

Part 6the pattern in the wild

You have already used Observer today

Observer is one of the most common patterns in libraries and frameworks: JavaBeans, Swing, JavaScript events, Cocoa and Swift’s key-value observing. Knowing the pattern means recognizing the design motivation in code you did not write.

Swing is Observer with buttons

JButton inherits a pile of add…Listener / remove…Listener methods from AbstractButton. Those listeners are observers: you register one, and the button notifies it when something happens. Instead of update(), the callback is actionPerformed().

SwingObserverExample.javainner-class listeners
public class SwingObserverExample {
    JFrame frame;

    public void go() {
        frame = new JFrame();
        JButton button = new JButton("Should I do it?");
        button.addActionListener(new AngelListener());
        button.addActionListener(new DevilListener());
        // set frame properties here
    }

    class AngelListener implements ActionListener {
        public void actionPerformed(ActionEvent event) {
            System.out.println("Don't do it, you might regret it!");
        }
    }

    class DevilListener implements ActionListener {
        public void actionPerformed(ActionEvent event) {
            System.out.println("Come on, do it!");
        }
    }
}
SwingObserverExample.javalambda observers (Java 8+)
button.addActionListener(event ->
     System.out.println("Don't do it, you might regret it!"));
button.addActionListener(event ->
     System.out.println("Come on, do it!"));

A lambda creates a function object that is the observer. Java checks that its signature matches actionPerformed(), the single method in ActionListener. Same pattern, less ceremony.

“Didn’t Java ship an Observer/Observable for this?” It did — java.util.Observer and java.util.Observable provided the subject plumbing for free. They were deprecated in Java 9: teams prefer the basic pattern in their own code, or something more robust. JavaBeans still offers PropertyChangeEvents/PropertyChangeListener, and the Flow API covers asynchronous publisher/subscriber streams.
“Can I rely on notification order?” No. The JDK explicitly advises you not to depend on any particular order of notifications. Treat the observer list as a set, not a queue.

Where else you will meet it

  • GUI frameworks of every kind — Swing, JavaFX, Android, .NET events, DOM addEventListener.
  • RxJava / reactive streams — subscribers register for a stream of values; the observable pushes them.
  • JavaBeans — PropertyChangeListener fires when a bean property changes.
  • RMI and messaging middleware — callbacks across process boundaries.
  • Cocoa / Swift — key-value observing (KVO) does the same job with different plumbing.
  • MVC — the next time this book needs Observer, it is the “view updates when the model changes” half of Model-View-Controller.

Part 8one-page recap

Chapter 2 cheat sheet

One object owns the state

WeatherData holds temperature, humidity and pressure, and is told when they change. Everything else is a consumer of that state.

Hardcoding the consumers breaks first

Calling currentConditionsDisplay.update(…) and friends codes to concrete classes, needs a change per display, and forbids runtime add/remove.

Publisher + subscribers

Subject = publisher, observers = subscribers. Observers register, the subject notifies whoever is on its list, observers can leave at any time.

The pattern

Observer defines a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically.

The new principle

Strive for loosely coupled designs between objects that interact. The subject knows only that its observers implement an interface.

Push or pull

Push sends the state in update(temp, humidity, pressure). Pull sends update() and the observer calls getters. Pull survives new data fields; the book calls it more “correct”.

It is everywhere

Swing listeners, JavaBeans PropertyChangeListener, RxJava, RMI, Cocoa/Swift KVO, JavaScript events — and MVC, later in this book. java.util.Observer/Observable were deprecated in Java 9.

The book’s bullet points

  • The Observer Pattern defines a one-to-many relationship between objects.
  • Subjects update Observers using a common interface.
  • Observers of any concrete type can participate as long as they implement the Observer interface.
  • Observers are loosely coupled: the subject knows nothing about them other than that they implement the interface.
  • You can push or pull data from the subject (pull is considered more “correct”).
  • Swing makes heavy use of the pattern, as do many GUI frameworks.
  • You will also find it in RxJava, JavaBeans, RMI, Cocoa, Swift and JavaScript events.
  • It is related to Publish/Subscribe, which handles multiple subjects and/or multiple message types.
  • You will see it again when you learn Model-View-Controller.

Design Principle Challenge (page 73)

For each previous principle, describe how the Observer Pattern uses it. The book’s answers:

PrincipleHow Observer honors it
Encapsulate what variesWhat varies is the subject’s state and the number and types of observers. You can vary the dependent objects without changing the subject.
Program to an interfaceThe subject tracks objects that implement Observer; observers register with, and are notified by, the Subject interface.
Favor compositionThe subject is composed with any number of observers at runtime — not through an inheritance hierarchy.
If you remember one line: when one object changes state and an unknown set of others care, let them subscribe to an interface instead of letting the subject name them.
