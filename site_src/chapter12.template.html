Part 1one simulator, six patterns

The Duck Simulator grows up

It starts as a clean little program: a Quackable interface and four classes that quack. Then a goose wants in, the quackologist wants a quack count, marketing wants duck families, the pond wants flocks, and somebody wants to watch. Every request is answered by a pattern you already know.

GooseAdapter.javaAdapter — p. 498
public class GooseAdapter implements Quackable {
  Goose goose;

  public GooseAdapter(Goose goose) {
    this.goose = goose;
  }

  public void quack() { goose.honk(); }
}
QuackCounter.javaDecorator — p. 500
public class QuackCounter implements Quackable {
  Quackable duck;
  static int numberOfQuacks;

  public QuackCounter(Quackable duck) {
    this.duck = duck;
  }

  public void quack() {
    duck.quack();
    numberOfQuacks++;
  }

  public static int getQuacks() {
    return numberOfQuacks;
  }
}
What just went wrong. The counter only counts the ducks that are wrapped, so main() now has to remember to wrap every single duck — and the simulator has an awful lot of new calls. Encouraging a client to decorate correctly is a creation problem. Enter the factory.
Flock.javaComposite — p. 507
public class Flock implements Quackable {
  List<Quackable> quackers = new ArrayList<Quackable>();

  public void add(Quackable quacker) {
    quackers.add(quacker);
  }

  public void quack() {
    Iterator<Quackable> iterator = quackers.iterator();
    while (iterator.hasNext()) {
      Quackable quacker = iterator.next();
      quacker.quack();
    }
  }

  public void registerObserver(Observer observer) { … }
  public void notifyObservers() { }
}

Safety vs. transparency

Chapter 9’s menus gave add() to leaves as well as composites so the client never had to know the difference. Here the book makes the opposite trade: only Flock has add().

  • Safer: you cannot call add() on a duck, because ducks do not have it.
  • Less transparent: the client must know it is holding a Flock before it can add anything to it.
  • Same rule as ever: composition choices have costs; pick the trade you can live with.
Read the Dumb Questions on the finale page. The book is emphatic: you do not design by “applying patterns until one fits”. The Duck Simulator is a demonstration of cooperation, not a recipe — and some of those solutions were overkill for the problem they solved.
Part 2from a duck pond to a paradigm

What a compound pattern actually is

The duck simulator is patterns working together, not a compound pattern: nobody named it, nobody reuses it. A compound pattern is a set of patterns that has been combined, named and used over and over to solve a general problem. There is one you already use every day — Model-View-Controller.

The definition: a compound pattern combines two or more patterns into a solution that solves a recurring or general problem. Ordinary code can use several patterns at once — a compound pattern is the one that has been named, reused and written down.
MVC partPatternWhy
Model → ViewObserverthe model announces state changes; any number of views and controllers can listen
View ↔ ControllerStrategythe controller is the view’s interchangeable behaviour; swap it for a different one
Inside the ViewCompositewindows, panels and buttons form a tree; one update() on the top redraws all
Why this matters more than the diagram. Once you see MVC as three familiar patterns, the “architecture” stops being a rule you memorise and becomes a consequence you can derive. That is the whole point of the chapter: compound patterns are patterns you already know, combined in a way that turned out to be reusable enough to deserve a name.
Part 3MVC you can hear

Building a beat machine with MVC

The book’s “DJ View” is a drum machine: a model that plays a beat at a given BPM, a view with a slider and a beat bar, and a controller that wires them together. Build it once and every MVC diagram you have ever squinted at becomes obvious.

BeatModel.javathe model — p. 532
public void initialize() {
  sequencer = new Sequencer();
  sequencer.open();
  sequencer.setTempoInBPM(getBPM());
  sequencer.addMetaEventListener(new MetaEventListener() {
    public void meta(MetaMessage event) {
      if (event.getType() == 47) {
        beat();
      }
    }
  });
}

public void on() {
  sequencer.start();
  setBPM(90);
}

public void off() {
  sequencer.stop();
  setBPM(0);
}

public void setBPM(int bpm) {
  this.bpm = bpm;
  sequencer.setTempoInBPM(this.bpm);
  notifyBPMObservers();
}
BeatController.javathe controller — p. 537
public class BeatController implements ControllerInterface {
  BeatModelInterface model;
  DJView view;

  public BeatController(BeatModelInterface model) {
    this.model = model;
    view = new DJView(model, this);
    view.createView();
    view.createControls();
    view.disableStopMenuItem();
    view.enableStartMenuItem();
    model.initialize();
  }

  public void start() {
    model.on();
    view.disableStartMenuItem();
    view.enableStopMenuItem();
  }

  public void stop() {
    model.off();
    view.disableStopMenuItem();
    view.enableStartMenuItem();
  }

  public void setBPM(int bpm) { model.setBPM(bpm); }
  public void increaseBPM() { model.setBPM(model.getBPM() + 1); }
  public void decreaseBPM() { model.setBPM(model.getBPM() - 1); }
}
Count the patterns. In this one small program: Observer (model notifies view and controller), Strategy (view delegates to a controller interface), Composite (the Swing component tree), Adapter (HeartAdapter), Factory-style assembly in DJTestDrive, and the MVC compound pattern holding them together. That is what “patterns of patterns” means.

Part 5one-page recap

Chapter 12 cheat sheet

Start with a clean simulator

Quackable with one method, four ducks and a duck call. It compiles, it quacks, it is boringly good design.

A goose wants in → Adapter

GooseAdapter implements Quackable and turns quack() into honk(). The goose and the simulator are untouched.

Count the quacks → Decorator

QuackCounter wraps a duck, delegates quack() and counts. Only wrapped ducks count — which is the flaw the factory fixes.

Never miss a wrap → Abstract Factory

DuckFactory returns plain ducks, CountingDuckFactory returns decorated ones. The client asks for a duck and gets the right family.

A pond of ducks → Composite

Flock is a Quackable made of Quackables. Only flocks have add(), trading transparency for safety.

Who quacked? → Observer

Every duck owns an Observable, notifies after quack(), and a Quackologist prints the culprit.

Patterns together ≠ compound pattern

Six patterns cooperating is just good design. A compound pattern is a named, reusable combination that solves a general problem.

MVC is Observer + Strategy + Composite

The model notifies, the controller is the view’s strategy, the view is a composite of widgets. Swap the model with an adapter and nothing else changes.

The book’s bullet points

  • A compound pattern combines two or more patterns into a solution that solves a recurring or general problem.
  • Patterns are often used together and combined within the same design solution.
  • The Model-View-Controller Pattern is a compound pattern consisting of the Observer, Strategy and Composite Patterns.
  • The model uses Observer to keep the views and controllers updated on the latest state changes.
  • The controller implements the behaviour of the view; it is the view’s strategy.
  • The view uses Composite to manage its display components.
  • You do not design by applying patterns to a problem until one fits — that is how you get over-engineered code.
  • Sometimes good OO principles solve the problem without any pattern at all.
  • MVC has been adapted to the web: thin client, single page applications, and everything in between.
