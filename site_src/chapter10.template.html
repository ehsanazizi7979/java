Part 2one class per state

Encapsulating what varies: the state

Judy names the principle out loud — “encapsulate what varies” — and Frank adds the second one: favor composition. The machine keeps a current state object and delegates every action to it.

The five states, in the order you meet them: NoQuarterState → HasQuarterState → SoldState → SoldOutState, plus WinnerState once the contest arrives.
Note what each state must be able to do: answer four actions and move the machine. That means every state class needs a reference back to the GumballMachine.
GumballMachine.java · the delegating threefour if/else chains, gone
public void insertQuarter() { state.insertQuarter(); }
public void ejectQuarter()  { state.ejectQuarter();  }
public void turnCrank() {
    state.turnCrank();
    state.dispense();   // internal action, called here
}
Why turnCrank() calls two methods: the crank is the only public action that triggers an internal one. dispense() stays off the machine’s public interface — the customer cannot ask for a gumball directly.
SoldOutState.java · the answerthe state that can only wait for a refill
public void insertQuarter() {
    System.out.println("You can't insert a quarter, the machine is sold out");
}
public void ejectQuarter() {
    System.out.println("You can't eject, you haven't inserted a quarter yet");
}
public void turnCrank() {
    System.out.println("You turned, but there are no gumballs");
}
public void dispense() {
    System.out.println("No gumball dispensed");
}
Four messages, zero transitions. That is a state doing its job: it describes a situation rather than asking “which situation am I in?”

The State Pattern

allows an object to alter its behavior when its internal state changes. The object will appear to change its class.

State vs. Strategy, in one line each: State is an alternative to a nest of conditionals, and the state objects move the context around themselves. Strategy is an alternative to subclassing, and the client picks the algorithm.
And the shared skeleton: a context holding an interface, delegating to it, with interchangeable implementations. Only the intent distinguishes them — which is exactly why the book ends the chapter with a fireside chat.

Chapter 10 cheat sheet

A spec on stationery

Four states, four actions, five transitions — and a promise of more behavior later. Mel’s kind of change request.

Version one: an int and four branches

Every action checks the state with conditionals. It works, and the test drive passes — 5 → 4 → 2 → 0 gumballs.

The contest breaks it

A new WINNER state means a new branch in every method. The code is open for modification and closed for nothing else.

One class per state

State declares the four actions; each concrete state answers them and moves the machine. The context’s methods become one-liners.

The context holds every state

Four fields (five with WinnerState), created in the constructor, plus setState() and releaseBall() for the states to use.

Same diagram as Strategy

A context, an interface, interchangeable implementations. What differs is intent: State moves itself, Strategy is handed to the context.

The contest is two lines

nextInt(10) returns 0 and there is more than one gumball left → WinnerState instead of SoldState.

Refill needs a new action

refill() joins the State interface; four states do nothing, SoldOutState transitions back to NoQuarterState.

The book’s bullet points

  • The State Pattern allows an object to have many different behaviors that are based on its internal state.
  • Unlike a procedural state machine, the State Pattern represents each state as a full-blown class.
  • The Context gets its behavior by delegating to the current state object it is composed with.
  • By encapsulating each state into a class, we localize any changes that will need to be made.
  • The State and Strategy Patterns have the same class diagram, but they differ in intent.
  • The Strategy Pattern typically configures Context classes with a behavior or algorithm.
  • The State Pattern allows a Context to change its behavior as the state of the Context changes.
  • State transitions can be controlled by the State classes or by the Context classes.
  • Using the State Pattern will typically result in a greater number of classes in your design.
  • State classes may be shared among Context instances.
