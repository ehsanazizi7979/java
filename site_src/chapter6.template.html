Chapter 6 the Command Pattern

Encapsulating Invocation

Every pattern so far has encapsulated an object. This one encapsulates a method call — packaging a receiver, an action (or a set of actions) and the argument list into a single object you can pass around, put in a queue, log to disk, and undo. The chapter’s vehicle is a seven-slot Home Automation remote control; its mental model is the Objectville Diner.

Part 1home automation or bust

Seven slots, seven vendors, no common interface

The brief is deliberately impossible-looking: build one remote that can drive lights, fans, stereos, hot tubs and garage doors — whose vendor classes share nothing but the fact that they are Java objects — and keep working when next year’s vendor classes arrive.

What the brief actually asks for

  • Seven slots, each with an on and an off button — and the device in a slot must be replaceable without touching the remote code.
  • One global undo that reverses the last button press.
  • Every vendor class, present and future, without a giant if/else chain over device types.
The trap: the vendor classes have nothing in common — on()/off() for a light, high()/medium()/low() for a fan, up()/down()/stop() for a garage door, jetsOn() and setTemperature() for a hot tub. A remote that knows those method names is a remote you rewrite every time a vendor ships a class.
Part 2meanwhile, back at the diner

The Objectville Diner, as a design pattern

The chapter’s teaching device is the diner from Chapter 1 — because a waitress, an order slip and a short-order cook are already a decoupled request pipeline, and everybody already knows how a restaurant works.

Who is who, and who is decoupled

  • The Order Slip is the command: one method, orderUp(), and a reference to the object that will do the work.
  • The Waitress is the invoker: she holds slips and calls orderUp() whenever she gets to the counter. She is parameterised with a different slip every time.
  • The Short-Order Cook is the receiver: the only object that knows how to cook.
  • The Customer is the client: creates the slip and hands it over.
Why the metaphor earns its pages: nothing in the waitress changes when a customer orders something new, and nothing in the cook changes when a new waitress is hired. Swap the slip for a command object and you have the pattern.

Part 3the first command object

Build it bottom-up

The chapter writes the smallest possible pieces first — one interface, one command, a one-slot remote — and only then scales up to seven slots and a null object.

Command.java · LightOnCommand.javathe whole contract
public interface Command {
    public void execute();
}

public class LightOnCommand implements Command {
    Light light;

    public LightOnCommand(Light light) {
        this.light = light;      // the receiver is bound at construction
    }

    public void execute() {
        light.on();              // ...and invoked here, later
    }
}
Two lines do all the work: the constructor captures which light, and execute() captures what to do to it. Change either and you have a different command — that is what “parameterising an object with a request” means.
SimpleRemoteControl.javathe invoker, in 9 lines
public class SimpleRemoteControl {
    Command slot;

    public void setCommand(Command command) {
        slot = command;
    }

    public void buttonWasPressed() {
        slot.execute();
    }
}

The invoker has no idea what is in slot. It does not know it is a light, a fan or a hot tub — it knows that whatever is there answers to execute(). That is the decoupling, in one line.

The exercise, solved

GarageDoorOpenCommand.javathe book’s answer, page 235

Command Pattern defined

The Command Pattern

encapsulates a request as an object, thereby letting you parameterize other objects with different requests, queue or log requests, and support undoable operations.

RemoteControl.javathe seven-slot invoker
public class RemoteControl {
    Command[] onCommands;
    Command[] offCommands;

    public RemoteControl() {
        onCommands = new Command[7];
        offCommands = new Command[7];

        Command noCommand = new NoCommand();
        for (int i = 0; i < 7; i++) {
            onCommands[i] = noCommand;
            offCommands[i] = noCommand;
        }
    }

    public void setCommand(int slot, Command onCommand,
                              Command offCommand) {
        onCommands[slot] = onCommand;
        offCommands[slot] = offCommand;
    }

    public void onButtonWasPushed(int slot) {
        onCommands[slot].execute();
    }

    public void offButtonWasPushed(int slot) {
        offCommands[slot].execute();
    }
}
Part 4the undo button

Undo, and the state it needs

“Aren’t you forgetting one little thing the customer asked for? LIKE THE UNDO BUTTON?!” Undo is the first place where the pattern pays for itself — because the invoker only has to remember one command, and each command knows how to reverse itself.

LightOnCommand.java · the undo halfexecute() and its mirror
public class LightOnCommand implements Command {
    Light light;

    public LightOnCommand(Light light) { this.light = light; }

    public void execute() { light.on(); }   // turn it on
    public void undo()    { light.off(); }  // ...so undo turns it off
}

For a two-state device, undo is just the other method. That is why the Light is the warm-up: it needs no remembered state.

RemoteControlWithUndo.java · the parts that matterone field, two assignments
Command undoCommand;

public RemoteControlWithUndo() {
    // ... slots as before
    undoCommand = noCommand;          // safe before any press
}

public void onButtonWasPushed(int slot) {
    onCommands[slot].execute();
    undoCommand = onCommands[slot];   // remember it
}

public void offButtonWasPushed(int slot) {
    offCommands[slot].execute();
    undoCommand = offCommands[slot];
}

public void undoButtonWasPushed() {
    undoCommand.undo();               // one command, one call
}

When undo needs memory

CeilingFanHighCommand.javaundo with local state
public class CeilingFanHighCommand implements Command {
    CeilingFan ceilingFan;
    int prevSpeed;                       // ← the memory

    public void execute() {
        prevSpeed = ceilingFan.getSpeed();  // record before acting
        ceilingFan.high();
    }

    public void undo() {
        if (prevSpeed == CeilingFan.HIGH)        ceilingFan.high();
        else if (prevSpeed == CeilingFan.MEDIUM)  ceilingFan.medium();
        else if (prevSpeed == CeilingFan.LOW)     ceilingFan.low();
        else if (prevSpeed == CeilingFan.OFF)     ceilingFan.off();
    }
}

The book’s console run (page 224): medium → off → undo returns to medium; high → undo returns to medium again. The command remembered prevSpeed each time, so each undo restores exactly one step.

Party mode: commands of commands

MacroCommand.javaone button, four devices
public class MacroCommand implements Command {
    Command[] commands;

    public MacroCommand(Command[] commands) {
        this.commands = commands;
    }

    public void execute() {
        for (int i = 0; i < commands.length; i++) {
            commands[i].execute();
        }
    }

    public void undo() {
        for (int i = commands.length - 1; i >= 0; i--) {
            commands[i].undo();          // reverse order!
        }
    }
}

The trap in macro undo: order matters. execute() runs 0 → n, so undo() must run n → 0. If the macro’s body does something order-dependent (dim the lights after turning them on), a forward-order undo leaves the room in a state that never existed.
Why not a PartyCommand? The book’s own answer: you could hard-code the four calls inside one command, “however, you’d essentially be hardcoding the party mode into PartyCommand. With MacroCommand you can decide dynamically which Commands you want to go into PartyCommand.”
Part 5beyond the remote

Queues, logs, and the two-pattern example

Once a request is an object, it can be stored. That single fact gives you thread pools, schedulers, transactional logs and crash recovery — and it turns out you have already used the Command Pattern in this book, in Chapter 2.

Smart commands vs. dumb commands. The book’s Q&A: “In general, we strive for ‘dumb’ command objects that just invoke an action on a receiver; however, there are many examples of ‘smart’ command objects that implement most, if not all, of the logic needed to carry out a request.” The cost of “smart” is the decoupling you were buying.
An undo history. For multi-step undo, keep a stack instead of a single reference: pop on undo. The pattern does not change; the invoker’s memory does.

Part 7one-page recap

    
Chapter 6 cheat sheet


    

      
The problem is a method call, not an object
The remote has to press buttons that turn on lights, fans and hot tubs whose classes share no interface — and keep working for vendor classes that do not exist yet.

      
The diner is the model
Customer → Client, Waitress → Invoker, Order Slip → Command, Cook → Receiver, orderUp() → execute(), takeOrder() → setCommand().

      
A command binds a receiver to actions
The constructor captures the receiver; execute() captures the actions. One interface, one method — that is the entire contract.

      
The invoker only knows execute()
Seven slots of Command references. onButtonWasPushed(slot) calls execute(); it never mentions a device class.

      
NoCommand removes the null check
Every slot starts loaded with a null object, so the invoker never tests for null — and pressing an unprogrammed button does nothing at all.

      
Undo is a second method
undo() mirrors execute(). The invoker stores one command reference; commands with state (the fan) remember their previous state themselves.

      
Macros are commands of commands
An array of commands, executed in order and undone in reverse order. The invoker does not change; slot 0 just holds a MacroCommand.

      
Requests can be stored
Because a request is an object, you can queue it (thread pools, schedulers) or log it (crash recovery, transactional replay).

    


    

      

        
The book’s bullet points

        
    
          
  • The Command Pattern decouples an object making a request from the one that knows how to perform it.
    • 
          
  • A Command object is at the center of this decoupling and encapsulates a receiver with an action (or set of actions).
    • 
          
  • An invoker makes a request of a Command object by calling its execute() method, which invokes those actions on the receiver.
    • 
          
  • Invokers can be parameterized with Commands, even dynamically at runtime.
    • 
          
  • Commands may support undo by implementing an undo() method that restores the object to its previous state before the execute() method was last called.
    • 
          
  • MacroCommands are a simple extension of the Command Pattern that allow multiple commands to be invoked. Likewise, MacroCommands can easily support undo().
    • 
          
  • In practice, it’s not uncommon for “smart” Command objects to implement the request themselves rather than delegating to a receiver.
    • 
          
  • Commands may also be used to implement logging and transactional systems.
    •
