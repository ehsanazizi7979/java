Chapter 1 intro to design patterns

Welcome to Design Patterns

A duck pond simulator, an executive whim, and one very bad use of inheritance. This is how Chapter 1 of Head First Design Patterns turns a flying rubber duck into your first design pattern: Strategy.

Part 1the problem

It started with a simple SimUDuck app

Joe’s company ships SimUDuck, a pond simulator that shows “a large variety of duck species swimming and making quacking sounds.” The original design is textbook object orientation: one Duck superclass, and a subclass per species.

Duck.javathe original design
public abstract class Duck {
    public void quack() { System.out.println("Quack"); }
    public void swim()  { System.out.println("All ducks float, even decoys!"); }

    // each duck subtype looks different
    public abstract void display();
}

public class MallardDuck extends Duck {
    public void display() {
        System.out.println("I'm a real Mallard duck");
    }
}

This works beautifully — right up until the requirements change. Which, as the chapter points out, they always do.

Then the executives wanted the ducks to fly

A week-long off-site “brainstorming session over golf” produces a big idea for the Maui shareholders meeting: flying ducks. Joe’s boss promises it will take a week — “he’s an OO programmer… how hard can it be?”

Duck.java“what Joe added”
public abstract class Duck {
    public void quack() { System.out.println("Quack"); }
    public void swim()  { System.out.println("All ducks float, even decoys!"); }
    public void fly()   { System.out.println("I'm flying!!"); }   // ← the famous mistake

    public abstract void display();
}

// Joe's "fix" for the bug he is about to create:
public class RubberDuck extends Duck {
    public void quack()  { System.out.println("Squeak"); }
    public void display(){ System.out.println("I'm a rubber duckie"); }
    public void fly()    { /* override to do nothing */ }
}

What went wrong?

Joe failed to notice that not all subclasses of Duck should fly. Adding behavior to the superclass added it to every subclass — including inanimate ones. He now has flying rubber ducks in the program.

And rubber ducks don’t quack either, so quack() had to be overridden to squeak. Then wooden decoy ducks arrive: they neither fly nor quack, so they override both to do nothing. The class hierarchy is filling up with “do nothing” methods.

The smell: every new duck species forces you to audit every inherited behavior, and every change to a behavior has to be repeated in dozens of subclasses. Overriding is a band-aid, not a design.

✏️ Sharpen your pencil

Which of the following are disadvantages of using inheritance to provide Duck behavior? (Choose all that apply.)

Book’s answer: A, B, D and F. Duplicated code, hard runtime changes, hidden behavior spread across subclasses, and changes that leak into unrelated ducks. C and E are red herrings (though dancing ducks would be fun).

Attempt #2: interfaces

Joe’s next idea is smarter but still incomplete: pull fly() out of Duck, add a Flyable interface with fly(), plus a Quackable interface. Only ducks that really fly implement Flyable.

It fixes the flying rubber duck, but it destroys code reuse: interfaces have no implementation, so the flying code gets copy-pasted into all 48 flying duck classes. Change the flying behavior once and you must change it 48 times.

Two failed extremes: inheritance (reuse, but rigid) versus interfaces (flexible, but duplicated). Chapter 1 needs a third option.
Part 2the design principles

The one constant in software development

Before offering a pattern, the book offers a mindset. No matter what you build, in what language, for whom: an application must grow and change, or it will die. Every pattern in the book is a strategy for coping with change.

Things that force you to change code

  • Customers decide they want something else — new functionality.
  • Your company switches database vendor, or buys data from a supplier using a different format.
  • Technology moves on, and your code has to speak new protocols.
  • You learn enough building the system that you want to go back and do it better.

So the real question is not “how do I write this class?” but “what in here is going to change, and how do I keep that change from leaking into everything else?”

☯
Design principle 1

Identify the aspects of your application that vary and separate them from what stays the same.

In other words: take what varies and encapsulate it so it won’t affect the rest of your code. Fewer unintended consequences, more flexibility. Nearly every design pattern is a variation on this theme.

☯
Design principle 2

Program to an interface, not an implementation.

Use an interface to represent each behavior — FlyBehavior and QuackBehavior — and let classes whose whole reason for existing is a behavior implement it. The duck then holds a reference to a behavior interface instead of inheriting a behavior.

Program to an implementationlocked in
Dog d = new Dog();
d.bark();                 // we coded to a concrete class
Program to an interface / supertypepolymorphic
Animal animal = new Dog();
animal.makeSound();       // Dog, but used as an Animal

animal = getAnimal();     // even better: decide at runtime
animal.makeSound();

“Program to an interface” really means “program to a supertype”. The supertype can be an abstract class or an interface — what matters is that the variable’s declared type is the abstraction and the concrete object is supplied later.

Part 3the redesign

Designing the duck behaviors

Two behavior interfaces, five behavior classes, and one small change to Duck: hold a behavior and delegate to it. That is the whole trick.

FlyBehavior.java / QuackBehavior.javathe two behavior interfaces
public interface FlyBehavior {
    public void fly();
}

public interface QuackBehavior {
    public void quack();
}
FlyWithWings.java · FlyNoWay.javaflying implementations
public class FlyWithWings implements FlyBehavior {
    public void fly() {
        System.out.println("I'm flying!!");
    }
}

public class FlyNoWay implements FlyBehavior {
    public void fly() {
        System.out.println("I can't fly");
    }
}
Quack.java · Squeak.java · MuteQuack.javaquacking implementations
public class Quack implements QuackBehavior {
    public void quack() { System.out.println("Quack"); }
}

public class Squeak implements QuackBehavior {
    public void quack() { System.out.println("Squeak"); }
}

public class MuteQuack implements QuackBehavior {
    public void quack() { System.out.println("<< Silence >>"); }
}

Integrating: the Duck delegates

Remove fly() and quack() from Duck. Add two instance variables typed as the behavior interfaces, and replace the old methods with performFly() and performQuack() that delegate.

Duck.javadelegation
public abstract class Duck {
    FlyBehavior flyBehavior;       // declare as the INTERFACE
    QuackBehavior quackBehavior;   // type, never the concrete class

    public void performFly()   { flyBehavior.fly(); }
    public void performQuack() { quackBehavior.quack(); }

    public void swim() { System.out.println("All ducks float, even decoys!"); }

    public abstract void display();

    // dynamic behavior: swap the algorithm at runtime
    public void setFlyBehavior(FlyBehavior fb)     { flyBehavior = fb; }
    public void setQuackBehavior(QuackBehavior qb) { quackBehavior = qb; }
}
MallardDuck.javapick behaviors in the constructor
public class MallardDuck extends Duck {
    public MallardDuck() {
        quackBehavior = new Quack();          // a real quack
        flyBehavior   = new FlyWithWings();  // wings, obviously
    }

    public void display() {
        System.out.println("I'm a real Mallard duck");
    }
}
“Wait — didn’t you say not to program to an implementation?” Yes, and the constructor does instantiate concrete behavior classes. That’s fine for initialization: the variables are still interface-typed, so any other implementation can be substituted at runtime (and later patterns will make the instantiation itself flexible).

Testing it: MiniDuckSimulator

MiniDuckSimulator.javathe book’s test program
public class MiniDuckSimulator {
    public static void main(String[] args) {
        Duck mallard = new MallardDuck();
        mallard.performQuack();
        mallard.performFly();
    }
}
% java MiniDuckSimulator Quack I'm flying!!

The inherited performQuack() asks the duck’s quackBehavior to quack; performFly() does the same with flyBehavior. MallardDuck never implements a single line of flying or quacking code.

Setting behavior dynamically

The best part: because the behavior lives in an object behind an interface, you can change it while the program runs. Add a ModelDuck that starts grounded, then hand it a rocket.

ModelDuck.java · FlyRocketPowered.javanew ducks, new behaviors
public class ModelDuck extends Duck {
    public ModelDuck() {
        flyBehavior   = new FlyNoWay();  // begins life grounded
        quackBehavior = new Quack();
    }
    public void display() { System.out.println("I'm a model duck"); }
}

public class FlyRocketPowered implements FlyBehavior {
    public void fly() {
        System.out.println("I'm flying with a rocket!");
    }
}
MiniDuckSimulator.javabehavior swap at runtime
Duck mallard = new MallardDuck();
mallard.performQuack();
mallard.performFly();

Duck model = new ModelDuck();
model.performFly();                          // FlyNoWay
model.setFlyBehavior(new FlyRocketPowered()); // voilà!
model.performFly();
% java MiniDuckSimulator Quack I'm flying!! I can't fly I'm flying with a rocket!
The punchline: the model duck changed its flying behavior at runtime without touching a single class. You can’t do that if the implementation lives inside Duck.
Part 4the pattern

Meet the Strategy Pattern

Look at the finished structure and the relationships: ducks extend Duck (IS-A), ducks have behaviors (HAS-A), and behavior classes implement behavior interfaces (IMPLEMENTS). Each family of behaviors is a family of interchangeable algorithms.

MallardDuck —▷ Duck = IS-A (extends) Duck → FlyBehavior = HAS-A (composition) FlyWithWings ⇢ FlyBehavior = IMPLEMENTS
🏅
The Strategy Pattern

Defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from clients that use it.

Use Strategy when…Watch out for…
many related classes differ only in behaviormore classes and objects than a simple inheritance tree
you need different variants of an algorithmclients must know how strategies differ to pick one
an algorithm uses data clients shouldn’t know aboutcommunication overhead between context and strategy
a class defines many behaviors as big conditionals— but you gain runtime swapping for free
☯
Design principle 3

Favor composition over inheritance.

Composition lets you encapsulate a family of algorithms into their own set of classes and change behavior at runtime, as long as the object you compose with implements the right interface. As the book’s guru puts it: more time is spent maintaining software than writing it, so design for maintainability and extensibility, not just reuse.

HAS-A can be better than IS-A

Each duck has a FlyBehavior and a QuackBehavior and delegates to them. The duck gets behavior by being composed with the right behavior object.

Because behaviors are ordinary objects, anything can reuse them. A duck call is not a duck — but it can have a quack behavior. That’s the “Brain Power” exercise on page 23, and it’s what the demo at the bottom of this page lets you build.

Part 5why patterns

Patterns are experience reuse

Patterns don’t go directly into your code — they go into your brain first. Then you recognize the places where they apply.

A shared vocabulary

At a diner, “a cream cheese with jelly on white bread, a chocolate soda with vanilla ice cream…” is the same order as “a C.J. White, a black & white…”. Flo has a shared vocabulary with the cook; Alice makes the cook remember every detail.

Patterns do the same for developers: saying “we’re using Strategy to implement the duck behaviors” communicates not just a name but a whole set of qualities, constraints and design decisions.

  • Say more with less.
  • Stay “in the design” longer instead of dropping into implementation details.
  • Turbo-charge a team; junior developers get up to speed faster.

The chapter’s bullet points

  • 1Knowing the OO basics does not make you a good OO designer.
  • 2Good OO designs are reusable, extensible and maintainable.
  • 3Patterns show you how to build systems with good OO design qualities.
  • 4Patterns are proven object-oriented experience.
  • 5Patterns don’t give you code — they give general solutions you adapt.
  • 6Patterns aren’t invented, they are discovered.
  • 7Most patterns and principles address issues of change.
  • 8Most patterns let some part of a system vary independently of the rest.
  • 9We often try to take what varies in a system and encapsulate it.
  • 10Patterns provide a shared language that maximizes the value of communication.

SimUDuck.jsthe strategy pattern in JavaScript — what this page runs
// Behavior interfaces become “duck typing” + a shared shape
class FlyWithWings { fly() { return "I'm flying!!"; } }
class FlyNoWay     { fly() { return "I can't fly"; } }
class FlyRocketPowered { fly() { return "I'm flying with a rocket!"; } }

class Quack     { quack() { return "Quack"; } }
class Squeak    { quack() { return "Squeak"; } }
class MuteQuack { quack() { return "<< Silence >>"; } }

class Duck {
  constructor(name) { this.name = name; }
  performFly()   { return this.flyBehavior.fly(); }       // delegate
  performQuack() { return this.quackBehavior.quack(); }
  setFlyBehavior(fb)     { this.flyBehavior = fb; }       // swap at runtime
  setQuackBehavior(qb)   { this.quackBehavior = qb; }
}

What to try

  • Select ModelDuck, press performFly() → “I can’t fly”. Then set flyBehavior to FlyRocketPowered and press it again — exactly the page-21 trick.
  • Give RubberDuck FlyWithWings — the pigeonhole problem from the book, now a deliberate choice instead of an inheritance accident.
  • Set DecoyDuck to MuteQuack + FlyNoWay: a wooden decoy that behaves like a wooden decoy.
  • Press Run book’s MiniDuckSimulator to reproduce the exact console output from page 21.
Why the demo matters: every duck in the pond is assembled from the same classes as the book. The duck never knows how it flies or quacks — only that it can. That’s the Strategy Pattern in one sentence.
Part 7one-page recap

Chapter 1 cheat sheet

Start with inheritance → it breaks

Duck.fly() gives every subclass wings, including rubber ducks and decoys. Localised change, non-local side effect.

Try interfaces → duplication

Flyable/Quackable fix the wrong-behavior bug but lose all code reuse and runtime flexibility.

Principle 1 — encapsulate what varies

Pull flying and quacking out of Duck into their own families of classes.

Principle 2 — program to an interface

Declare flyBehavior as FlyBehavior, never FlyWithWings. Supply the concrete object at runtime.

Principle 3 — favor composition

A duck HAS-A behavior and delegates to it. Behavior can be swapped, even mid-flight.

The pattern — Strategy

Define a family of algorithms, encapsulate each one, make them interchangeable; the algorithm varies independently from the clients that use it.

Why it matters

Patterns are experience reuse and a shared vocabulary — and they don’t go into your code, they go into your brain first.

ApproachReuseFlexible at runtime?Right behavior for every duck?
InheritanceYesNoNo — flying rubber ducks
Interfaces onlyNoSort ofYes, but duplicated code
Strategy (composition)YesYesYes
If you remember one line: identify what varies, encapsulate it behind an interface, and compose your object with it so you can change the algorithm without changing the client.
