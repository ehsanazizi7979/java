Chapter 8 the Template Method Pattern

Encapsulating Algorithms

We have encapsulated object creation, method invocation and whole interfaces. Now we encapsulate the shape of an algorithm: a method in a superclass that fixes the order of the steps and lets subclasses fill in a few of them — and a design principle borrowed from Hollywood that explains why that is a good idea.

Part 1two recipes, one algorithm

It’s time for some more caffeine

Starbuzz is back, this time with a training manual. The coffee recipe and the tea recipe are almost the same four steps — and that is all the invitation the book needs to start pulling an algorithm out of two classes.

The smell: two classes, one algorithm, four methods each, two of them identical. Every future beverage would copy all four.
The first instinct — and the book’s first cut — is to pull the two shared methods up into an abstract CaffeineBeverage and leave prepareRecipe() abstract in each subclass. It removes the duplication and solves nothing: each subclass still owns the recipe, so the algorithm is still duplicated.

Part 2the pattern, and hooks

Template Method defined

The definition is short, and the class diagram is short — the interesting part is the vocabulary the book adds next: primitive operations, concrete operations, and hooks, the do-nothing methods that a subclass may override if it feels like it.

☯
The Template Method Pattern

defines the skeleton of an algorithm in a method, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm’s structure.

Three kinds of method, one abstract class: the template method (usually final) fixes the sequence; primitive operations are abstract and must be implemented; concrete operations are implemented here, sometimes final so nobody can replace them.

No “Adding Sugar and Milk” line: the hook said no. The algorithm never changed — that is the whole trick.

Abstract method or hook? “Use abstract methods when your subclass MUST provide an implementation of the method or step in the algorithm. Use hooks when that part of the algorithm is optional.”
Hooks have three jobs in the book’s account: implement an optional part of the algorithm, react to a step that is about to happen or just happened (e.g. justReorderedList()), and make a decision on behalf of the abstract class — which is exactly what customerWantsCondiments() does.
Part 3don’t call us, we’ll call you

The Hollywood Principle

Template Method has a principle attached to it, and the principle explains why the base class gets to call the shots: high-level components decide when low-level components are needed — never the reverse.

☯
The Hollywood Principle

don’t call us, we’ll call you.

PatternDescription
Template MethodSubclasses decide how to implement steps in an algorithm.
StrategyEncapsulate interchangeable behaviors and use delegation to decide which behavior to use.
Factory MethodSubclasses decide which concrete classes to create.
Two patterns in one sentence: Factory Method is a specialization of Template Method — the primitive operation is “create an object”. Which is why the book says the Hollywood Principle shows up in Factory Method and Observer too.

Part 5one-page recap

Chapter 8 cheat sheet

Duplication is the smell

Coffee and Tea share two identical methods and two analogous ones. Shared code goes up; the algorithm should go up too.

Generalise the step names

brewCoffeeGrinds()/steepTeaBag() → brew(); addSugarAndMilk()/addLemon() → addCondiments(). Same shape, different implementations.

The template method owns the order

final void prepareRecipe() calls the four steps. Subclasses cannot reorder or skip them — only supply the abstract ones.

Three method flavours

Primitive operations (abstract, mandatory), concrete operations (implemented, optionally final), and hooks (empty default, optional).

Hooks buy conditional flow

if (customerWantsCondiments()) addCondiments(); — the subclass influences the algorithm without controlling it.

The Hollywood Principle

“Don’t call us, we’ll call you.” The high-level component decides when low-level components are needed, which is what prevents dependency rot.

In the wild, it rarely looks textbook

Arrays.sort() is static and uses Comparable instead of inheritance; JFrame.paint() is a hook; AbstractList.subList() leans on get() and size().

Template Method vs. Strategy

Both encapsulate an algorithm. Template Method does it with inheritance and a fixed skeleton; Strategy does it with composition and lets you swap at runtime.

The book’s bullet points

  • A template method defines the steps of an algorithm, deferring to subclasses for the implementation of those steps.
  • The Template Method Pattern gives us an important technique for code reuse.
  • The template method’s abstract class may define concrete methods, abstract methods, and hooks.
  • Abstract methods are implemented by subclasses.
  • Hooks are methods that do nothing or default behavior in the abstract class, but may be overridden in the subclass.
  • To prevent subclasses from changing the algorithm in the template method, declare the template method as final.
  • The Hollywood Principle guides us to put decision making in high-level modules that can decide how and when to call low-level modules.
  • You’ll see lots of uses of the Template Method Pattern in real-world code, but don’t expect it all to be designed “by the book”.
  • The Strategy and Template Method Patterns both encapsulate algorithms, the first by composition and the other by inheritance.
  • Factory Method is a specialization of Template Method.
