Part 2one object standing in for another

Proxy defined — and the RMI detour

Before the definition the book drags you through Java RMI, because the remote proxy is the variant that needs the most machinery: a remote interface, an implementation, a registry, a server and a client. It is worth the detour — the stub is the proxy.

MyRemote.javastep 1 — the remote interface
import java.rmi.*;

public interface MyRemote extends Remote {
  public String sayHello() throws RemoteException;
}
MyRemoteImpl.javastep 2 — extends UnicastRemoteObject
public class MyRemoteImpl extends UnicastRemoteObject
                       implements MyRemote {
  public MyRemoteImpl() throws RemoteException { }
  public String sayHello() {
    return "Server says 'Hey!'";
  }
  public static void main(String[] args) {
    try {
      Naming.rebind("Remote Hello", new MyRemoteImpl());
    } catch (Exception ex) { ex.printStackTrace(); }
  }
}
Proxy.javathe pattern in nine lines
public class Proxy implements Subject {
  RealSubject realSubject;        // the object we stand in for

  public void request() {
    // ...control access here: lazy-create, check rights,
    //     forward over the network, count references...
    realSubject.request();
  }
}
Four r’s, one pattern. Remote proxy — the subject lives in another JVM. Virtual proxy — the subject is expensive to create. Protection proxy — the subject needs access rights. Smart reference — the subject needs housekeeping (counting, locking, caching). Same diagram every time.
Part 3a stand-in while the real thing loads

The virtual proxy: album covers that load themselves

A CD-cover browser hangs on the network: every cover is a megabyte of JPEG, and ImageIcon fetches it in the constructor. The virtual proxy swaps the order around — show a placeholder now, fetch the picture later, paint it when it arrives.

ImageProxy.javathe book’s virtual proxy, transcribed
public class ImageProxy implements Icon {
  ImageIcon imageIcon;     // the real subject
  URL imageURL;
  Thread retrievalThread;
  boolean retrieving = false;

  public ImageProxy(URL url) { imageURL = url; }

  public int getIconWidth() {
    if (imageIcon != null) return imageIcon.getIconWidth();
    return 800;                       // stand-in size
  }
  public int getIconHeight() {
    if (imageIcon != null) return imageIcon.getIconHeight();
    return 600;
  }

  public void paintIcon(final Component c, Graphics g,
                        int x, int y) {
    if (imageIcon != null) {
      imageIcon.paintIcon(c, g, x, y);
    } else {
      g.drawString("Loading album cover, please wait...",
                   x + 300, y + 190);
      if (!retrieving) {
        retrieving = true;
        retrievalThread = new Thread(new Runnable() {
          public void run() {
            try {
              imageIcon = new ImageIcon(imageURL,
                                           "CD Cover");
              c.repaint();
            } catch (Exception e) { e.printStackTrace(); }
          }
        });
        retrievalThread.start();
      }
    }
  }
}

Why each line is there

  • It implements Icon. The viewer paints Icons. It does not know, and cannot know, that this one is a proxy.
  • The constructor is cheap. It stores a URL. No network, no blocking, no megabyte.
  • 800×600 is a lie with a purpose. Before the real image exists the proxy reports the size the layout should reserve.
  • paintIcon() starts the fetch. The real work happens on the paint thread’s second pass, not in the constructor.
  • retrieving is a latch. paintIcon() is called dozens of times; the thread must start once.
  • c.repaint() is the hand-off. When the image arrives the component repaints and now paints the real icon.
The client is unchanged. ImageProxyTestDrive still calls new ImageIcon(...)-shaped code through the Icon interface. The virtual proxy is invisible by construction.
The answer to the puzzle. Two states, two conditional branches, and a behaviour that changes when the image arrives — that is the State Pattern from Chapter 10. Give ImageProxy an ImageNotLoaded state and an ImageLoaded state; paintIcon() delegates and the state object decides. The pattern you learned three chapters ago is the refactor for the one you just learned.
Part 4access rights, checked at call time

The protection proxy: Elroy needs a bodyguard

Objectville’s dating service lets any client call any Person method, so anyone can change anyone’s interests or vote for themselves. A protection proxy wraps the person and refuses the calls the caller is not allowed to make — and Java can build it at runtime, without a class per person.

OwnerInvocationHandler.javathe rights check, in full
import java.lang.reflect.*;

public class OwnerInvocationHandler implements InvocationHandler {
  Person person;

  public OwnerInvocationHandler(Person person) {
    this.person = person;
  }

  public Object invoke(Object proxy, Method method, Object[] args)
      throws IllegalAccessException {
    try {
      if (method.getName().startsWith("get")) {
        return method.invoke(person, args);
      } else if (method.getName().equals("setGeekRating")) {
        throw new IllegalAccessException();
      } else if (method.getName().startsWith("set")) {
        return method.invoke(person, args);
      }
    } catch (InvocationTargetException e) {
      e.printStackTrace();
    }
    return null;
  }
}

Same code, mirrored

NonOwnerInvocationHandler is the same class with the branches swapped: any set method throws IllegalAccessException except setGeekRating, which is the one thing a non-owner is allowed to do.

  • The subject never changes. PersonImpl has no idea a proxy exists; its methods are still public.
  • Rights live in the handler. Change the policy, change one invoke().
  • Refusal is an exception. IllegalAccessException is thrown from the handler, not from PersonImpl.
  • The proxy is generated. No OwnerPersonProxy class exists on disk — Proxy.newProxyInstance() invents it.
MatchMakingTestDrive.javathe factories
public Person getOwnerProxy(Person person) {
  return (Person) Proxy.newProxyInstance(
      person.getClass().getClassLoader(),
      person.getClass().getInterfaces(),
      new OwnerInvocationHandler(person));
}

public Person getNonOwnerProxy(Person person) {
  return (Person) Proxy.newProxyInstance(
      person.getClass().getClassLoader(),
      person.getClass().getInterfaces(),
      new NonOwnerInvocationHandler(person));
}

Chapter 11 cheat sheet

One more request from the corner office

Monitor every gumball machine without leaving the desk. The monitor works — it just has to reach objects in other JVMs.

Remote proxy

A local stand-in for a remote object. It forwards calls and returns results; the client thinks the object is local.

RMI in five steps

Remote interface → implementation extends UnicastRemoteObject → rmiregistry → Naming.rebind() → Naming.lookup().

The stub is the proxy

Six steps per call: client → stub → wire → skeleton → service → and back. The registry is used once, at lookup time.

Making the machine remote

GumballMachineRemote declares the three getters; every State extends Serializable; the stub reference is transient.

Virtual proxy

ImageProxy reports 800×600, paints a loading message, fetches on a thread and repaints. “Expensive to create” now costs nothing up front.

Protection proxy

An InvocationHandler checks the method name: getters always pass, setGeekRating only for non-owners, other setters only for owners.

Dynamic proxy

Proxy.newProxyInstance(loader, interfaces, handler) generates the proxy class at runtime; rights live in the handler, not in a class.

The book’s bullet points

  • The Proxy Pattern provides a representative for another object in order to control the client’s access to it.
  • A Remote Proxy manages interaction between a client and a remote object.
  • A Virtual Proxy controls access to an object that is expensive to create.
  • A Protection Proxy controls access to an object based on access rights.
  • There are many other variants: firewall, caching, synchronization, copy-on-write, complexity-hiding.
  • Proxy and Decorator have the same class diagram but different intent: Decorator adds behaviour, Proxy controls access.
  • Proxy and Adapter both wrap, but Adapter changes the interface while Proxy keeps it the same.
  • Proxy and Facade both sit in front of something, but a Facade hides a subsystem behind a simpler interface.
  • Java’s dynamic proxy creates a proxy class at runtime from an interface list and an InvocationHandler.
  • A proxy can also be a smart reference: counting references, locking, or caching on the client’s behalf.

The book’s matching solution: Decorator — wraps another object and provides additional behaviour. Facade — wraps a bunch of objects to simplify their interface. Proxy — wraps an object to control access to it. Adapter — wraps another object and provides a different interface to it.
