Chapter 7 the Adapter and Facade Patterns

Being Adaptive

Two patterns that wrap things for the sake of the interface rather than the object: an Adapter converts one interface into the one a client expects, and a Facade replaces a crowd of interfaces with one simple one. Same wrapping trick as Decorator — completely different intent.

Part 1square peg, round hole

Adapters, all around us

The chapter opens with the most familiar adapter in the world: the power brick that lets a US laptop plug into a British outlet. The pattern is the same move in code — a class that sits between your client and an incompatible interface and translates.

The Adapter Pattern

converts the interface of a class into another interface the clients expect. Adapter lets classes work together that couldn’t otherwise because of incompatible interfaces.

A real adapter: Enumeration → Iterator

EnumerationIterator.javaan imperfect adapter, documented
public class EnumerationIterator implements Iterator<Object> {
    Enumeration<?> enumeration;

    public EnumerationIterator(Enumeration<?> enumeration) {
        this.enumeration = enumeration;
    }

    public boolean hasNext() {
        return enumeration.hasMoreElements();
    }

    public Object next() {
        return enumeration.nextElement();
    }

    public void remove() {
        throw new UnsupportedOperationException();
    }
}
The lesson in the last method: an adapter can be imperfect. When the adaptee cannot support part of the target interface, the honest options are to throw a documented runtime exception (as here) or to accept degraded behaviour. What you must not do is silently do the wrong thing.
The book’s Q&A on scope: “Does an adapter always wrap one and only one class?” — No. “You may well have situations where an adapter holds two or more adaptees that are needed to implement the target interface.” That answer is also the setup for the second half of the chapter.
Part 2and now for something different

The Facade Pattern

Adapter changes an interface so a client can use it. Facade changes an interface so a client can survive it: one class, a handful of obvious methods, and a subsystem of seven components behind it.

PatternWrapsIntent
Decoratorone objectdoesn’t alter the interface, adds responsibility
Adapterone or more objectsconverts one interface into another
Facadea subsystemmakes an interface simpler
The book’s own warning about telling them apart by size: “The difference between the two is not in terms of how many classes they ‘wrap’, it is in their intent.” An adapter may adapt several classes; a facade may simplify a single complicated class.

Home Sweet Home Theater

Why this is the classic “before” picture: the client is coupled to six concrete classes, has to know the correct order, has to duplicate all thirteen calls to turn things off, and breaks when the projector is replaced.

The facade answer is one class with four methods. Everything the client needed to know about the subsystem — order, preconditions, “turn the popper on before you pop” — moves into the facade, where it can be written once and tested.

What a facade is not: it does not hide the subsystem. The components stay public and directly usable; the facade is a convenience, not a lock.
HomeTheaterFacade.java · the two methods that matterdelegation, in the right order
public void watchMovie(String movie) {
    System.out.println("Get ready to watch a movie...");
    popper.on();
    popper.pop();
    lights.dim(10);
    screen.down();
    projector.on();
    projector.wideScreenMode();
    amp.on();
    amp.setStreamingPlayer(player);
    amp.setSurroundSound();
    amp.setVolume(5);
    player.on();
    player.play(movie);
}

public void endMovie() {
    System.out.println("Shutting movie theater down...");
    popper.off();
    lights.on();
    screen.up();
    projector.off();
    amp.off();
    player.stop();
    player.off();
}
A facade is allowed to be smart: it knows the popper must be on before it can pop, and that the amp needs the player reference before surround sound. “A facade is free to add its own ‘smarts’ in addition to making use of the subsystem.”

The Facade Pattern

provides a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.

Part 3a new principle

The Principle of Least Knowledge

The facade is not just a convenience; it is the shape a design takes when you decide that objects should have as few friends as possible. The book calls that “talk only to your immediate friends” — and it has teeth.

☯
Principle of Least Knowledge

talk only to your immediate friends.

Concretely: from any method, invoke only methods that belong to

  • the object itself,
  • objects passed in as a parameter,
  • any object the method creates or instantiates,
  • any component (instance variable) of the object.
The rule that catches most code: never call a method on an object returned from another method. station.getThermometer().getTemperature() is the canonical violation.
Why the facade belongs here: the client of a facade has exactly one friend. Everything it needs is on the facade; the seven subsystem classes are the facade’s friends, not the client’s.
And the cost: “applying this principle results in more ‘wrapper’ classes being written to handle method calls to other components. This can result in increased complexity and development time as well as decreased runtime performance.” Principles are trade-offs, not laws.
Also called the Law of Demeter. The book prefers “Principle of Least Knowledge” because “Law” implies you must always apply it — and no principle is a law.

Part 5one-page recap

Chapter 7 cheat sheet

An adapter is a translator, not a decorator

It implements the interface the client expects, holds the object with the wrong interface, and converts every call. The client and the adaptee never meet.

Translation can reshape the call

quack() → gobble(); fly() → five short flights. An adapter may add, split or drop calls — the interface is what is preserved, not the semantics.

Object adapters use composition; class adapters need multiple inheritance

Java only gets the object adapter — which is also the flexible one, because it can adapt any subclass of the adaptee.

An imperfect adapter is legitimate

EnumerationIterator.remove() throws UnsupportedOperationException because an Enumeration is read-only. Document it and move on.

A facade simplifies a subsystem

It composes the components and delegates to them in the right order. It does not hide them: the subsystem stays available to clients that need low-level access.

A facade may be smart

It knows the popper must be on before it pops and the amp needs the player before surround sound. That domain knowledge is exactly what it is saving its clients from.

Principle of Least Knowledge

Talk only to your immediate friends: self, parameters, things you create, and your own components. No calling methods on objects returned by other methods.

And its price

More wrapper classes, more indirection, slower calls. Principles are trade-offs; the book calls this one a principle rather than a law precisely because of that.

The book’s bullet points

  • When you need to use an existing class and its interface is not the one you need, use an adapter.
  • When you need to simplify and unify a large interface or complex set of interfaces, use a facade.
  • An adapter changes an interface into one a client expects.
  • A facade decouples a client from a complex subsystem.
  • Implementing an adapter may require little work or a great deal of work depending on the size and complexity of the target interface.
  • Implementing a facade requires that we compose the facade with its subsystem and use delegation to perform the work of the facade.
  • There are two forms of the Adapter Pattern: object and class adapters. Class adapters require multiple inheritance.
  • You can implement more than one facade for a subsystem.
  • An adapter wraps an object to change its interface, a decorator wraps an object to add new behaviors and responsibilities, and a facade “wraps” a set of objects to simplify.
