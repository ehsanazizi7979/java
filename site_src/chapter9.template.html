Chapter 9 the Iterator and Composite Patterns

Well-Managed Collections

Two patterns for the same problem — collections you have to walk through. Iterator gives clients a way to step over your objects without seeing how you store them; Composite lets a menu contain menus, so a whole restaurant can be treated as one object. Along the way, the book hands out its most quotable principle: a class should have only one reason to change.

Part 1two menus, two loops

The merger, and the loop problem

Objectville’s Diner and Pancake House merge. Mel stores his menu in an array, Lou stores his in an ArrayList, and neither will change — so the waitress is about to be written against both concrete types, with two loops, forever.

The book’s own checklist of what is wrong here: A — coding to concrete classes; C — a new menu type forces waitress changes; D — the waitress knows each menu’s internal collection, which violates encapsulation; E — duplicate iteration code, one loop per menu type. (B and F are the jokes.)
The move that fixes it is the one the whole book keeps making: encapsulate what varies. What varies is the iteration, so put it in its own object.
Two responsibilities, one for each class: the menu manages menu items, the iterator knows how to walk them. That separation is what makes the client code polymorphic.
And the leftover smell: the waitress still calls printMenu() once per menu, so every new restaurant means opening her class. The book fixes that twice: first with a List<Menu>, then with a tree.
Part 2the pattern, and one responsibility

Iterator defined

The definition, the class diagram, and the design principle the pattern is really about: give the traversal its own object, and the aggregate gets to have exactly one reason to change.

☯
The Iterator Pattern

provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation.

☯
Single Responsibility Principle

a class should have only one reason to change.

Applied to the menus: a class that both holds a collection and knows how to walk it changes when the collection changes and again when the traversal changes. Two reasons, two classes.

Related word to know: cohesion — high when a class is built around a set of related functions. Classes that follow this principle tend to have high cohesion.
Iterator vs. Iterablewhy the for-each loop is a bonus, not a fix
// explicit iterator — always works, needs an Iterator
Iterator<MenuItem> it = menu.createIterator();
while (it.hasNext()) {
    MenuItem item = it.next();
}

// for-each — only for Iterable (Collections), not arrays
for (MenuItem item : menu) { ... }
“Not so fast; Arrays are not Iterables.” If the waitress takes an Iterable, the Diner’s array cannot be passed in. That is exactly why the pattern’s own interface is Iterator and not Iterable.
What the cafeteria bought: adding the Café cost one new class and three lines in the waitress. That is what “program to an interface” looks like when you measure it.
What it didn’t buy: the waitress still has three createIterator() calls and three printMenu() calls, so the class still changes every time a restaurant arrives. Hence the next two pages — and then the composite.
Part 3menus within menus

The Composite Pattern

A dessert submenu breaks the iterator design: a Menu cannot be put inside a MenuItem[]. The answer is to make menus and items the same type, and let print() recurse.

☯
The Composite Pattern

allows you to compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.

Menu.java · the recursive five linesthe whole pattern in one for-each
public void print() {
    System.out.print("\n" + getName());
    System.out.println(", " + getDescription());
    System.out.println("---------------------");

    for (MenuComponent menuComponent : menuComponents) {
        menuComponent.print();
    }
}
Why this is the payoff: the loop does not care which kind of component it finds. If it is a MenuItem, print() prints one line; if it is another Menu, print() starts another loop. That is “treat individual objects and compositions uniformly”.

Part 5one-page recap

Chapter 9 cheat sheet

The merger exposes the coupling

Mel’s array and Lou’s ArrayList force the waitress into two loops and two concrete types — and she sees how each menu stores its items.

Encapsulate the iteration

createIterator() returns an object with hasNext()/next(). The client stops caring which structure is underneath.

Iterator moves a responsibility

Traversal leaves the aggregate and lives in the iterator, so the aggregate has one job — managing its collection.

Program to the Menu interface

One method, createIterator(), is enough to free the waitress from PancakeHouseMenu, DinerMenu and then CafeMenu.

Single Responsibility Principle

“A class should have only one reason to change.” Two reasons means two classes, and usually two kinds of change arriving at once.

remove() is optional

If your iterator cannot remove, throw UnsupportedOperationException — that is what the Java API documents and what the code magnets exercise does.

Iterable is a different interface

Iterable gives you iterator() (and the for-each loop). Arrays implement neither — which is why the pattern is built on Iterator.

Composite makes parts equal wholes

Menus (nodes) and menu items (leaves) share MenuComponent, so print() on the root prints the entire tree by recursion.

And it trades safety for transparency

A leaf inherits add()/remove(), which do not make sense; the default implementations throw. That is a deliberate trade, not an accident.

The book’s bullet points

  • An Iterator allows access to an aggregate’s elements without exposing its internal structure.
  • An Iterator takes the job of iterating over an aggregate and encapsulates it in another object.
  • When using an Iterator, we relieve the aggregate of the responsibility of supporting operations for traversing its data.
  • An Iterator provides a common interface for traversing the items of an aggregate, allowing you to use polymorphism when writing code that makes use of the items of the aggregate.
  • The Iterable interface provides a means of getting an iterator and enables Java’s enhanced for loop.
  • We should strive to assign only one responsibility to each class.
  • The Composite Pattern allows clients to treat composites and individual objects uniformly.
  • A Component is any object in a Composite structure. Components may be other composites or leaves.
  • There are many design tradeoffs in implementing Composite. You need to balance transparency and safety with your needs.
