Chapter 3 the Decorator Pattern

Decorating Objects

Inheritance sets behavior at compile time, and it hands every subclass the same behavior whether it wants it or not. Decorator replaces that with wrapping: you take an object, put another object around it, and get new behavior at runtime — without touching the class of the thing you wrapped.

Part 1the starbuzz story

Coffee, condiments, and a class explosion

Starbuzz Coffee is the fastest-growing coffee chain around — so fast that their ordering system is already out of date. They started with four drinks and a clean little hierarchy. Then the condiments arrived.

Beverage.java · Espresso.javathe design before condiments
public abstract class Beverage {
    String description = "Unknown Beverage";

    public String getDescription() { return description; }

    public abstract double cost();
}

public class Espresso extends Beverage {
    public Espresso() { description = "Espresso"; }
    public double cost() { return 1.99; }
}

Then customers asked for milk, soy, mocha and whip

Starbuzz charges for each condiment, so every combination has to be priced. Their first instinct is the one every inheritance-trained designer has: make a subclass for every drink × condiment combination.

Attempt two: the boolean flags

“Can’t we just use instance variables and inheritance in the superclass to keep track of the condiments?” So Beverage grows four booleans, four has…() getters, four set…() setters, and a cost() that adds up whatever is switched on. Subclasses call super.cost() and add their own price.

Beverage.javaattempt two
public double cost() {
    double condimentCost = 0.0;
    if (hasMilk())  { condimentCost += milkCost; }
    if (hasSoy())   { condimentCost += soyCost; }
    if (hasMocha()) { condimentCost += mochaCost; }
    if (hasWhip())  { condimentCost += whipCost; }
    return condimentCost;
}

What breaks first (book page 84)

  • Price changes for condiments force us to alter existing code.
  • New condiments force us to add new methods and alter cost() in the superclass.
  • New beverages inherit things that don’t apply: iced tea gets hasWhip() whether it likes it or not.
  • Double mocha? A single boolean mocha can’t count to two.
Two principles violated, in a big way. The superclass is modified every time a condiment changes (nothing is closed for modification), and we cannot extend the menu with a new topping without editing existing code (nothing is open for extension). It is Chapter 1’s lesson again: behavior is being decided by the class, not by the object.

The idea in one sentence

Instead of asking “which subclass is this drink?”, ask “what is wrapped around this drink?”. A Mocha object that also is a Beverage can stand in for the drink it wraps, add 20¢ to its cost(), and append “, Mocha” to its description — and you can stack as many as the customer orders.

The catch, stated up front: the decorator has the same type as the thing it decorates, and it holds one. So there is still inheritance in the design — used for type matching, not for behavior. Behavior comes from composition.

That is the whole trick: type comes from inheritance, behavior comes from composition and delegation.

Part 2the principle behind the pattern

The Open-Closed Principle

☯
Design Principle · the fifth one

Classes should be open for extension, but closed for modification.

Our goal is to allow classes to be easily extended to incorporate new behavior without modifying existing code. Get that right and you get designs that are resilient to change and flexible enough to take on new functionality — which is exactly the thing that coffee shops, weather stations and every other client keep asking for.

Dumb questions (book page 87)

“Open for extension and closed for modification? That sounds contradictory.” It does — but OO gives us techniques for extending a system without editing the underlying code. Chapter 2 was already an example: you extend a Subject by adding Observers, and the Subject never changes.

“How do I design something to be extensible yet closed?” That is what patterns are for. Most patterns supply a means of extension that keeps the core code untouched — this chapter’s Decorator is the clearest example.

“Can I make every part of my design follow it?” Usually not, and you shouldn’t try. Following the principle adds abstraction, and abstraction adds complexity. Apply it where change is likely, not everywhere.

How you will use it: pick the area that varies (here: condiments and their prices), put a stable interface around it, and extend by adding new classes instead of editing old ones.
Part 3meet the pattern

Wrap the drink, don’t subclass it

Decorating means exactly what it sounds like: start with a beverage, then wrap it in condiment objects, one layer at a time, at runtime.

  1. 1
    Start with a DarkRoast object.
  2. 2
    Decorate it with a Mocha object.
  3. 3
    Decorate it with a Whip object.
  4. 4
    Call the cost() method and rely on delegation to add up the condiment costs.

What the book tells us about decorators

  • Decorators have the same supertype as the objects they decorate.
  • You can use one or more decorators to wrap an object.
  • Because the types match, you can pass a decorated object in place of the original.
  • The decorator adds its own behavior before and/or after delegating to the object it decorates.
  • Objects can be decorated at any time — as many decorators as you like, at runtime.

Cubicle conversation (page 93): “I thought we weren’t going to use inheritance?” — We use inheritance only to get the right type, so a Mocha can stand in for a Beverage. The behavior comes from composition: each decorator wraps a component and adds to what it delegates to.
Why not an interface for Beverage? Starbuzz already had an abstract class, and the chapter’s rule is not to alter working code (“don’t ‘fix’ it if the abstract class will work just fine”). An interface would work equally well in a new design.

Part 4writing the starbuzz code

Four decorators, four drinks, one interface

The component and the abstract decorator first, then the drinks, then the condiments — and finally the test harness that orders three coffees.

Beverage.javathe component — unchanged
public abstract class Beverage {
    String description = "Unknown Beverage";

    public String getDescription() {
        return description;
    }

    public abstract double cost();
}
CondimentDecorator.javathe abstract decorator
public abstract class CondimentDecorator extends Beverage {
    Beverage beverage;

    public abstract String getDescription();
}

Two things to notice: CondimentDecorator extends Beverage (so a decorator can stand in for a drink) and holds a Beverage (so it can wrap one). Every condiment is required to re-implement getDescription() so it can append its own name to the drink it wraps.

Espresso.java · HouseBlend.javaconcrete components
public class Espresso extends Beverage {
    public Espresso() { description = "Espresso"; }
    public double cost() { return 1.99; }
}

public class HouseBlend extends Beverage {
    public HouseBlend() { description = "House Blend Coffee"; }
    public double cost() { return .89; }
}

// DarkRoast  -> "Dark Roast Coffee", .99
// Decaf      -> "Decaf Coffee",      1.05
Mocha.javaa concrete decorator
public class Mocha extends CondimentDecorator {

    public Mocha(Beverage beverage) {
        this.beverage = beverage;
    }

    public String getDescription() {
        return beverage.getDescription() + ", Mocha";
    }

    public double cost() {
        return beverage.cost() + .20;
    }
}

Starbuzz adds sizes (page 99 exercise)

Tall, grande and venti — and condiments now charge by size, with soy at 10¢, 15¢ and 20¢. The fix requires no change to the base classes beyond adding the size state; each decorator asks the object it wraps how big it is.

Beverage.javawith size state
public abstract class Beverage {

    public enum Size { TALL, GRANDE, VENTI };

    Size size = Size.TALL;
    String description = "Unknown Beverage";

    public String getDescription() { return description; }

    public void setSize(Size size) { this.size = size; }
    public Size getSize() { return this.size; }

    public abstract double cost();
}
Soy.javasize-aware decorator
public double cost() {
    double cost = beverage.cost();
    if (beverage.getSize() == Size.TALL)   cost += .10;
    if (beverage.getSize() == Size.GRANDE) cost += .15;
    if (beverage.getSize() == Size.VENTI)  cost += .20;
    return cost;
}

The size lives on the component, so the decorator reads it through the object it wraps — beverage.getSize(). Decorators can ask their component questions, not just call its methods.

Three things people worry about

“What if code depends on a concrete type — say, a discount for HouseBlend?” Then decorators break it, exactly as the book warns. Once the drink is wrapped, the client holds a Beverage, not a HouseBlend. Keep client code written against the abstract component and decorating stays transparent.
“Could I accidentally hold an inner decorator?” Yes — you have more objects to manage, so it is easier to end up with a reference to the Soy instead of the Whip and lose the outer layers. In practice you create decorated objects through a factory or builder, which encapsulates the wrapping (Factory is next chapter).
“Can a decorator see the other decorations?” Not by design. When you need to look several layers in, you are pushing the pattern past its intent. The book’s escape hatch is a separate CondimentPrettyPrint decorator that reformats “Mocha, Whip, Mocha” as “Whip, Double Mocha”.
Part 5decorators in the wild

Java I/O is the Decorator Pattern

If java.io ever looked like an unreasonably large pile of classes, this is why: it is a decorator-heavy API. FileInputStream is a component; BufferedInputStream and ZipInputStream are decorators that wrap it.

LowerCaseInputStream.javayour own I/O decorator
public class LowerCaseInputStream extends FilterInputStream {

    public LowerCaseInputStream(InputStream in) {
        super(in);
    }

    public int read() throws IOException {
        int c = in.read();
        return (c == -1 ? c : Character.toLowerCase((char)c));
    }

    public int read(byte[] b, int offset, int len)
            throws IOException {
        int result = in.read(b, offset, len);
        for (int i = offset; i < offset + result; i++) {
            b[i] = (byte)Character.toLowerCase((char)b[i]);
        }
        return result;
    }
}
InputTest.javawrapping a file stream
InputStream in =
    new LowerCaseInputStream(
        new BufferedInputStream(
            new FileInputStream("test.txt")));

while ((c = in.read()) >= 0) {
    System.out.print((char)c);
}
The cost of all this wrapping: decorator-heavy APIs produce a lot of small classes, which is why java.io intimidates people. The pattern’s power and its main downside come from the same place.

Part 7one-page recap

Chapter 3 cheat sheet

Subclassing every combination explodes

Four drinks × four condiments is dozens of classes, and each new topping multiplies the tree. Nobody maintains that.

Boolean flags are no better

hasMilk()/setWhip() put every topping into the base class, can’t count a double mocha, and force a change to Beverage whenever the menu changes.

The Open-Closed Principle

Classes should be open for extension, but closed for modification. Apply it where change is likely — not everywhere.

The pattern

Attach additional responsibilities to an object dynamically. Decorators give a flexible alternative to subclassing for extending functionality.

How it works

A decorator has the same supertype as the component it wraps (for type) and holds a reference to it (for behavior). It delegates, adding its own work before and/or after.

It composes at runtime

You can wrap a component with any number of decorators, in any order, whenever you like — the client just sees a Beverage.

Its price

Many small objects and a lot of wrapping code. It breaks clients that depend on concrete component types. java.io is the famous example of both the power and the confusion.

The book’s bullet points

  • Inheritance is one form of extension, but not necessarily the best way to achieve flexibility.
  • Designs should allow behavior to be extended without modifying existing code.
  • Composition and delegation can add new behaviors at runtime.
  • Decorator provides an alternative to subclassing for extending behavior.
  • Decorator classes wrap concrete components and mirror their type.
  • Decorators change behavior by adding functionality before and/or after (or in place of) calls to the component.
  • You can wrap a component with any number of decorators.
  • Decorators are transparent to the client — unless the client depends on the concrete type.
  • Decorators can result in many small objects; overuse is complex.
