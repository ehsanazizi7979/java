Chapter 4 the Factory Patterns

Baking with OO Goodness

Three chapters in, the New-operator question is still open: we are told to program to an interface, yet every object we ever use has to be created somewhere, concretely, with new. This chapter takes that one line of code — the instantiation — and shows how to move it out of the places that should not care about it. Simple Factory, Factory Method, and Abstract Factory are three ways of doing it; Dependency Inversion is the principle that explains why it works.

Part 1the pizza problem

When you see “new”, think “concrete”

The chapter opens with the objection that has been sitting on the reader’s shoulder since page 1: if we are supposed to code to an interface, why is every other line a new? The answer is that new is not a bug — it is a dependency. And dependencies on concrete classes are exactly what the whole book keeps telling us to reduce.

Objectville PizzaStore, version 1

A pizza shop starts, as every pizza shop does, with one class and one method. Every pizza is prepared, baked, cut, and boxed the same way — so orderPizza() is written once.

PizzaStore.java · v1the pizza shop before it had a menu
Pizza orderPizza() {
    Pizza pizza = new Pizza();   // “we really want this to be an abstract class
                                          //  or interface, but we can’t instantiate either”
    pizza.prepare();
    pizza.bake();
    pizza.cut();
    pizza.box();
    return pizza;
}

Then the menu grows: cheese, Greek, pepperoni. Now the method has to decide which class to instantiate, and the decision is written directly into the ordering logic.

PizzaStore.java · v2the version that starts to hurt
Pizza orderPizza(String type) {
    Pizza pizza;

    if (type.equals("cheese"))        { pizza = new CheesePizza(); }
    else if (type.equals("greek"))      { pizza = new GreekPizza(); }
    else if (type.equals("pepperoni"))  { pizza = new PepperoniPizza(); }

    pizza.prepare();
    pizza.bake();
    pizza.cut();
    pizza.box();
    return pizza;
}
Nothing is “closed for modification” here. Every new pizza reopens this method; every removed pizza leaves dead code behind. When the same instantiation logic gets copy-pasted into a kiosk, a website, and a phone app, all three copies have to be found and fixed.
The fix, in the book’s words: “take all the parts of your application that instantiate concrete classes and separate or encapsulate them from the rest of your application.” The rest of the chapter is three increasingly sophisticated ways to do exactly that.

Encapsulate the creation

The creation code does not disappear — it moves. Pull it out of orderPizza(), drop it into an object whose only job is making pizzas, and let the store ask that object for one.

Part 2the honorable mention

Simple Factory: one class, one job

The factory holds the if/else chain that orderPizza() used to hold, and hands back a Pizza. The store no longer mentions a single concrete pizza class — it only knows the abstract type. Head First is careful to say that this is not a design pattern: it is a programming idiom, and it earns only an Honorable Mention.

SimplePizzaFactory.javathe creation code, corralled
public class SimplePizzaFactory {

    public Pizza createPizza(String type) {
        Pizza pizza = null;

        if (type.equals("cheese"))        { pizza = new CheesePizza(); }
        else if (type.equals("veggie"))    { pizza = new VeggiePizza(); }
        else if (type.equals("clam"))      { pizza = new ClamPizza(); }
        else if (type.equals("pepperoni")) { pizza = new PepperoniPizza(); }

        // pizza.prepare(); pizza.bake(); pizza.cut(); pizza.box();
        return pizza;
    }
}
PizzaStore.javacomposed with the factory
public class PizzaStore {
    SimplePizzaFactory factory;

    public PizzaStore(SimplePizzaFactory factory) {
        this.factory = factory;
    }

    public Pizza orderPizza(String type) {
        Pizza pizza = factory.createPizza(type);   // ask the factory

        pizza.prepare();
        pizza.bake();
        pizza.cut();
        pizza.box();
        return pizza;
    }
}
Why it isn’t a pattern. The book is blunt: “The Simple Factory actually isn’t a Design Pattern; it’s more of a programming idiom.” A pattern earns the name by giving you a general, reusable solution to a recurring design problem. Simple Factory is just good practice: put creation in one place. It also sits still while the shop grows — when the shops start differing by region, one factory cannot serve them all.

The franchises arrive

Objectville PizzaStore franchises. Each new store wants the same ordering code but its own local style of pizza: New York thin crust, Chicago deep dish, California whatever California wants. The obvious move — three factories, composed into one PizzaStore — works, but it means the store still has to be handed the right factory, and the store class is still the place where the choice lives.

If you keep the factory as a parameter

“If we take our SimplePizzaFactory and create three different factories — NYPizzaFactory, ChicagoPizzaFactory, and CaliforniaPizzaFactory — then we can just compose the PizzaStore with the appropriate factory and a franchise is good to go.” It is a legitimate approach, and the book acknowledges it before moving on: the factory object is no longer hard-wired, but somebody outside the store still has to pick it.

Two caveats worth remembering. First, a factory class usually has no state, so its create method is often declared static — but a static factory cannot be subclassed and its behavior cannot be changed by overriding. Second, even a good factory does not remove the dependency; it relocates it to one place you can control. That relocation is the whole trick, and it is what the Dependency Inversion Principle will later explain.
Part 3a framework for the pizza store

Let the subclasses decide

Here is the move that turns this into a pattern. Put createPizza() back inside PizzaStore — but make it abstract. The superclass writes the ordering algorithm and knows nothing about which pizza it is working on; every regional subclass supplies the one method that knows.

PizzaStore.javathe abstract creator
public abstract class PizzaStore {

    public Pizza orderPizza(String type) {
        Pizza pizza;

        pizza = createPizza(type);   // the factory method

        pizza.prepare();
        pizza.bake();
        pizza.cut();
        pizza.box();
        return pizza;
    }

    abstract Pizza createPizza(String type);
}
Notice what stayed. Preparing, baking, cutting and boxing are identical in every franchise, so they live in the superclass once. Only the choice of pizza is deferred. That is a framework: the superclass controls the algorithm, the subclass controls one step of it.

    }
}

Ethan, Joel, and the four steps of an order

  • 1Each customer needs a store: Joel instantiates a ChicagoPizzaStore, Ethan a NYPizzaStore.
  • 2With the store in hand, both call orderPizza() and pass the type they want — "cheese", "veggie", and so on.
  • 3orderPizza() calls createPizza(), which is defined in the subclass. The NY store instantiates a NY-style pizza; the Chicago store instantiates a Chicago-style one. Either way a Pizza comes back.
  • 4orderPizza() has no idea what kind of pizza it received — only that it is a Pizza — and prepares, bakes, cuts and boxes it.
The decision moved. It used to be an if inside the store. Now it is “which subclass did you instantiate?” — a decision made once, outside the ordering code, and impossible to forget because the compiler requires every concrete store to implement createPizza().

Part 4meet the pattern

Factory Method, at last

What started as a refactoring of orderPizza() turns out to be the general solution to “a class cannot know which class it needs to instantiate.” The book names it, draws it twice, and then sits the reader down with the guru.

☯
The Factory Method Pattern

defines an interface for creating an object, but lets subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses.

Read the last sentence twice. The creator does not go looking for a product and it does not receive one; it defers. The superclass says “I need a pizza here”, and the answer arrives from whichever subclass was instantiated.

That is why the book warns about the word “decide”: the subclass does not choose per order — the choice was made when somebody instantiated the store. “Decide” means “the decision is expressed by which subclass is in use.”

What the pattern buys you. The creator is decoupled from the concrete products: it depends on the Pizza abstraction only. Add a California store and no existing class changes — you add a creator subclass and a family of products.

Three questions people ask here

“The factory still instantiates concrete classes. Did we gain anything?” Yes: one place instead of many, and clients that depend only on the abstraction. The dependency did not vanish; it was moved to a single, controlled corner.

“Isn’t this just inheritance again?” It uses inheritance, but not to reuse behavior in the products — to defer a decision. The algorithm in the creator is written once; the product choice varies per subclass.

“Why not a constructor parameter or a factory object?” Both work (that is Simple Factory). Factory Method makes the choice structural: the compiler forces every new store to answer it, and no caller can pass the wrong factory.

Look familiar? orderPizza() is a template: fixed steps with one hole. The book points out that Factory Method is a specialization of the Template Method idea — the hook is simply “create something”.
Part 5the principle behind the pattern

The Dependency Inversion Principle

Before this chapter, the PizzaStore knew every pizza by name. That is a dependency, and dependencies point in a direction. DIP is the principle that says the arrows should point at abstractions — and it is the reason the factory patterns work.

The exercise on page 167

“Let’s pretend you’ve never heard of an OO factory”: here is a DependentPizzaStore with no factory at all. Count the concrete pizza classes it depends on.

DependentPizzaStore.javathe before picture
public class DependentPizzaStore {

    public Pizza createPizza(String style, String type) {
        Pizza pizza = null;

        if (style.equals("NY")) {
            if (type.equals("cheese"))         { pizza = new NYStyleCheesePizza(); }
            else if (type.equals("veggie"))    { pizza = new NYStyleVeggiePizza(); }
            else if (type.equals("clam"))      { pizza = new NYStyleClamPizza(); }
            else if (type.equals("pepperoni")) { pizza = new NYStylePepperoniPizza(); }
        } else if (style.equals("Chicago")) {
            // … four more Chicago-style pizzas …
        } else {
            System.out.println("Error: invalid type of pizza");
            return null;
        }

        pizza.prepare();  pizza.bake();  pizza.cut();  pizza.box();
        return pizza;
    }
}
Answer (page 166): 8. Add California and it is 12 — four more noodles in the same bowl of spaghetti. Meanwhile the factory version of PizzaStore depends on exactly one thing: the Pizza abstraction.

Why “inversion”?

In a naive design, the high-level policy (a pizza store) depends on the low-level details (cheese pizza, clam pizza). The arrow points down from policy to detail.

Invert it: both the store and every pizza now depend on the Pizza abstraction. The arrow from the store points at an abstraction the details also implement, and the details become plugins.

Every Java program violates these guidelines. The book says so. The point is not purity; it is knowing when you are breaking the rule and why. If a class is unlikely to change, new is fine. If it is likely to change, put a factory in front of it.
Where the chapter goes next. Factory Method inverts one dependency. But a pizza in New York is made of New York ingredients, and a Chicago pizza of Chicago ones — and the pizzas themselves are now the thing that knows which families exist. That is the second half of the chapter.
Part 6families of ingredients

Abstract Factory: built from ingredients

The pizza store is franchised, decoupled, and DIP-compliant. Then somebody points out the obvious: the pizzas themselves are full of regional details. New York uses thin crust, marinara and Reggiano; Chicago uses thick crust, plum tomato sauce and mozzarella. If each pizza hard-codes its ingredients, the store is decoupled but the products are not.

The book’s move is to give the pizzas a factory, not a region. Every pizza class receives a PizzaIngredientFactory in its constructor, and its prepare() asks that factory for dough, sauce, cheese and clams. The pizza never knows whether it is being made in New York or Chicago — and because the pizzas are now identical apart from their ingredients, the four × two regional pizza classes collapse into four.

public interface PizzaIngredientFactory {

    public Dough     createDough();
    public Sauce     createSauce();
    public Cheese    createCheese();
    public Veggies[] createVeggies();
    public Pepperoni createPepperoni();
    public Clams     createClam();

}

☯
The Abstract Factory Pattern

provides an interface for creating families of related or dependent objects without specifying their concrete classes.

The difference from Factory Method is the unit of creation. Factory Method creates one product, and the choice is made by subclassing. Abstract Factory creates a family of products, and the choice is made by composing the client with one factory object.

Notice the two levels of factory here. PizzaIngredientFactory is the abstract factory. Each of its create…() methods is a factory method in the loose sense — and the book points out that in practice they are very often implemented as factory methods. The patterns compose.

The pizzas, rewired

Two classes now replace eight: CheesePizza and ClamPizza are the same in every region. The regional difference lives entirely in the factory that was passed in.

Abstract Factory’s cost. Its interface has one method per product. Add a new kind of ingredient and every concrete factory — including ones written by other teams — must implement the new method. It also adds classes fast: here, four pizzas plus two factories plus about a dozen ingredient classes.
Its payoff. Products from one factory are guaranteed to belong together (no marinara on a deep-dish pizza), clients never mention a concrete product class, and swapping a whole regional family is a single-line change — the same line the demo below lets you click.

Part 8one-page recap

Chapter 4 cheat sheet

new is a dependency, not a sin

Every instantiation names a concrete class. When that choice is sprinkled through the code, every new pizza type reopens every place that orders one.

Encapsulate what varies — the creation

Move the if/else chain into one object. That is Simple Factory: an idiom, not a pattern, but it decouples every client from the concrete pizzas.

Factory Method defers to subclasses

Make createPizza() abstract and let NYPizzaStore and ChicagoPizzaStore implement it. The ordering algorithm stays in the superclass, unchanged and shared.

Dependency Inversion explains why it works

Depend upon abstractions, not concrete classes. High-level policy and low-level details both point at the abstraction; the details become plugins.

Abstract Factory makes families

When the products come in related sets — dough, sauce, cheese, clams — put a factory interface in front of the set and inject one factory per region.

Composition vs inheritance, again

Factory Method uses inheritance to decide which class; Abstract Factory uses object composition to decide which family. Both keep clients away from concrete types.

The book’s bullet points

  • All factories encapsulate object creation.
  • Simple Factory, while not a bona fide design pattern, is a simple way to decouple your clients from concrete classes.
  • Factory Method relies on inheritance: object creation is delegated to subclasses, which implement the factory method to create objects.
  • Abstract Factory relies on object composition: object creation is implemented in methods exposed in the factory interface.
  • All factory patterns promote loose coupling by reducing the dependency of your application on concrete classes.
  • The intent of Factory Method is to allow a class to defer instantiation to its subclasses.
  • The intent of Abstract Factory is to create families of related objects without having to depend on their concrete classes.
  • The Dependency Inversion Principle guides us to avoid dependencies on concrete types and to strive for abstractions.
  • Factories are a powerful technique for coding to abstractions, not concrete classes.

And the one that isn’t a pattern: Simple Factory — “more of a programming idiom” — still earns a Head First Pattern Honorable Mention because it is the first, simplest way to take creation out of the code that uses the thing created.

Choose all that apply.

Chapter 4 in the book’s words: “All factories encapsulate object creation.” Simple Factory does it with one class; Factory Method does it by giving the job to subclasses; Abstract Factory does it by handing the client a factory for an entire family. The Dependency Inversion Principle is the reason all three work: the code that uses a product, and the code that makes it, both point at the abstraction instead of at each other.
