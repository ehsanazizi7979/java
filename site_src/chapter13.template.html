Part 1a solution to a problem in a context

What a pattern really is

You have used thirteen of them. Now the book asks the harder question: what makes a description of a solution a pattern, and why does the name matter more than the code?

Why the name matters. A pattern name is a handle for a design conversation: “let’s put a proxy in front of it” conveys an interface, an access policy and a class diagram in six words. That is the real deliverable of this book — not the code, the vocabulary.
Part 2purpose, scope, and when not to

Organizing the catalog

Thirteen patterns is already too many to hold as a flat list. The catalog is indexed two ways — by purpose and by scope — and knowing the grid is how you find the one you want without rereading the book.

The warning the book puts in a box. Overuse of design patterns can lead to code that is downright overengineered. Every pattern you add is a class, an indirection and a thing a colleague has to learn. If a plain interface would do, use a plain interface.
Three questions before you apply one. Can I name the problem? Can I name the forces? Can I name the change this protects me from — with a straight face? If any answer is “no”, you are decorating, not designing.

Part 5one-page recap

Chapter 13 cheat sheet

A pattern is a solution to a problem in a context

Problem, forces, solution, consequences. A one-off solution is not a pattern until it recurs and can be handed to someone else.

The catalog entry is the unit

Name, intent, motivation, applicability, structure, participants, consequences, implementation, sample code, known uses, related patterns.

Two ways to index them

By purpose (creational, structural, behavioral) and by scope (class or object).

Keep it simple

Patterns are not a magic bullet. Overuse produces overengineered code — the book prints that warning in a box.

Use one when you expect change

You know you need a pattern when you can name the change it protects you from. Otherwise, don’t.

The vocabulary is the point

One name replaces a paragraph of design discussion — and five habits spread it: discussions, pairing, a notebook, comments, stand-ups.

Anti-patterns keep it honest

The Golden Hammer is the classic: one tool, every problem looks like a nail. Documented anti-patterns stop a team repeating its mistakes.

Class vs. object, in one line: class patterns fix the relationship at compile time through inheritance; object patterns wire it at runtime through composition. That is why almost everything here is an object pattern.

The book’s closing bullet points

  • Let design patterns emerge in your designs; don’t force them in for the sake of using a pattern.
  • Design patterns aren’t set in stone; adapt and tweak them to meet your needs.
  • Always pull the problem, forces and solution into your design notebook.
  • Don’t let a pattern take over your design.
  • Design patterns are a shared vocabulary — use it.
  • A pattern is a solution to a problem in a context.
  • Patterns are discovered, not invented.
  • Watch for anti-patterns, and don’t let them take root.
  • The catalog is a beginning, not an end.
