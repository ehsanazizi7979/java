Chapter 5 the Singleton Pattern

One-of-a-Kind Objects

Some objects should exist exactly once — a thread pool, a cache, a registry, a boiler. Singleton is the simplest pattern in the book by class count (its class diagram holds a single class) and one of the hardest to get right: a private constructor, one static field, and a static method look harmless until two threads walk through the same if statement.

Part 1one and only one

“An entire chapter about how to instantiate just ONE object?”

Yes. Every new you have written so far was a promise that this object can exist as many times as anybody feels like. Singleton is the pattern that lets a class break that promise — and the chapter is mostly about the ways that promise sneaks back in.

The little Singleton

The chapter’s Socratic warm-up — a dialogue in the style of The Little Lisper — builds the pattern one question at a time. It starts from the only two facts you need: any public class can be instantiated any number of times, and a constructor can be made private.

the answer to the exerciseone instance, ever
public class Singleton {
    private static Singleton uniqueInstance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (uniqueInstance == null) {
            uniqueInstance = new Singleton();
        }
        return uniqueInstance;
    }
}

The static field holds the one object; the private constructor blocks everyone else; getInstance() is the only door.

Part 2the classic implementation

Dissecting the classic Singleton

Three pieces do all the work: a static variable, a private constructor, and a static method that creates the instance only if it does not exist yet. The book calls that last part lazy instantiation — and it is also the part that will break.

Why each line is there

  • private static Singleton uniqueInstance; — one slot, shared by the whole class, not by an object.
  • private Singleton() {} — no other class can call new Singleton(). The compiler enforces the pattern.
  • public static Singleton getInstance() — a class method, callable from anywhere without an instance. That is the “global access point”.
  • if (uniqueInstance == null) — create on first use only. If nobody ever asks, the object is never made.
A singleton is still a normal class. It has its own fields and methods; it just happens to manage its own single instance. That is also why it is criticized: managing the instance is a second responsibility bolted onto whatever the class was really for (more on that in Part 5).

The three claims the interview makes

There is only one. There is no public constructor and no other way in, so the class controls its own cardinality.

Everyone shares it. Every object in the application that asks for it gets the same instance — which is exactly what you want for registry settings, a connection pool or a boiler.

It is created late. “If we never need the instance, it never gets created.” A global variable cannot promise that; a lazily initialised static can.

What the interview does not mention: threads. Two threads can both find uniqueInstance == null before either assigns it, and then you have two singletons. That is the rest of the chapter.
Part 3the chocolate factory

Choc-O-Holic, Inc.

A chocolate boiler takes in milk and chocolate, boils them, and passes them on. It must not be filled twice, boiled twice, or drained before boiling — so the controller is careful. What it never checks is how many boilers exist.

The failure, spelled out

Two controllers each call new ChocolateBoiler(). Controller A fills its boiler and starts the boil. Controller B, which has never heard of A’s boiler, fills its boiler — and the plant now has two batches, two sets of flags, and one drain pipe.

That is the class of bug the pattern exists to prevent: not a wrong line of code, but a wrong number of objects. The fix has two halves:

  • make the constructor private, so nobody outside can create one;
  • hand out the only instance through a static getInstance().
And the fix looks perfect — on a single thread. The two-boiler problem is gone: no other class can call new ChocolateBoiler(), and everyone who asks gets the one instance. Keep that in mind for Part 4, where the plant adds threads and the same code produces two boilers anyway.

Singleton Pattern defined

☯
The Singleton Pattern

ensures a class has only one instance, and provides a global point of access to it.

Two promises, and they are independent. The single instance part is the private constructor plus the static field. The global access part is the static method — the thing a global variable also gives you, without the guarantee.

Note what the pattern does not say: nothing about laziness, nothing about threads, nothing about class loaders. All of that is implementation, and all of it is where the chapter spends its remaining pages.

Part 4hershey, pa, we have a problem

Two threads, one if

The plant adds “some optimizations” that use multiple threads. The Singleton code has not changed — and the boiler fills while a batch is already boiling. Nothing in the class is wrong; the interleaving is.

Thread One checks: uniqueInstance == null → true

No instance yet. Thread One is about to create one — but the JVM may switch away between the check and the assignment.

Thread Two checks: uniqueInstance == null → true

Still null, because Thread One has not assigned anything yet. Thread Two now believes it must create the instance too.

Both threads run uniqueInstance = new ChocolateBoiler()

Two objects are constructed; the second assignment overwrites the field. Each thread returns the boiler it made.

Result: two boilers, one field

Two controllers, two sets of empty/boiled flags, one plant. This is exactly the two-boiler bug the pattern was supposed to prevent.

Which one does the book pick for the boiler? Page 190: either synchronized or eager works (“we don’t seem to have any performance concerns with the chocolate boiler”), while double-checked locking is “overkill” and would force at least Java 5.

The book’s own answers (page 190)

Synchronize getInstance(): “a straightforward technique that is guaranteed to work. We don’t seem to have any performance concerns with the chocolate boiler, so this would be a good choice.”

Use eager instantiation: “we are always going to instantiate the chocolate boiler in our code, so statically initializing the instance would cause no concerns” — though it is perhaps “less obvious to a developer familiar with the standard pattern.”

Double-checked locking: “given we have no performance concerns, double-checked locking seems like overkill. In addition, we’d have to ensure that we are running at least Java 5.”

The lesson to keep: there is no single “correct” Singleton. There is the implementation whose cost you can afford for the traffic you actually have — and a documented reason for choosing it.
Part 5enum and the fine print

The one-line Singleton

Everything the last two pages worried about — synchronization, class loading, reflection, serialization — is handled for you if the singleton is an enum with a single constant.

Singleton.java · the enum versionthe whole pattern
public enum Singleton {
    UNIQUE_INSTANCE;
    // more useful fields here
}

public class SingletonClient {
    public static void main(String[] args) {
        Singleton singleton = Singleton.UNIQUE_INSTANCE;
        // use the singleton here
    }
}

Why it works: enum constants are created by the JVM during class initialisation, which is guaranteed to happen once and to be visible to every thread. There is no constructor call to guard and no field to check.

Why the book still teaches the hard way. “We did that so you really, truly understand how Singleton works.” The classic version is also the answer to the interview question “how do you implement a Singleton without using enum?”

The fine print: “Dubious Questions” (pages 184–185)

  • Why not just static methods and variables? Fine for a self-contained utility, but Java’s static initialisation order makes it fragile once several classes are involved.
  • Class loaders. Each loader defines its own namespace, so the same class can be loaded twice — and a Singleton loaded twice is two singletons. Specify the loader if this matters.
  • Reflection and serialization. Both can create a second instance behind the pattern’s back; the enum form closes those doors.
  • Loose coupling. Every object that uses the Singleton is tightly coupled to that specific object — a common and fair criticism.
  • Single Responsibility. The class now manages its own instance and does its real job. Some designers factor the singleton-ness out.
  • Subclassing. A private constructor cannot be extended. Make it protected and you no longer have a Singleton; the static instance would also be shared by all subclasses.
  • Global variables. A global variable gives you access but not uniqueness, and it encourages namespace pollution. Singleton gives you both — and can still be abused.
  • Use sparingly. “If you are using a large number of Singletons in your application, you should take a hard look at your design.”

Part 7one-page recap

    
Chapter 5 cheat sheet


    

      
A Singleton is about cardinality, not convenience
Thread pools, caches, registries, logging, device drivers: a second instance causes inconsistent state or wasted resources, not just extra objects.

      
Two promises
One instance (private constructor + static field) and a global point of access (static getInstance()). A global variable gives you only the second.

      
The classic implementation is lazy — and racy
Two threads can both see uniqueInstance == null and both create an instance; the second assignment silently overwrites the first.

      
Three fixes
synchronized getInstance() (simple, locks every call), eager static initialiser (JVM-safe, always created), double-checked locking (lock only the first time, needs Java 5 + volatile).

      
The enum shortcut
One enum constant is created once by the JVM. It also survives reflection and serialization, which the class-based versions do not.

      
Know its costs
Tight coupling to a concrete global, two responsibilities in one class, hard to subclass, and painful to test in isolation. Use it sparingly.
