Chapter 1 — Introduction

Why concurrency at all? This chapter is the book's argument: threads are an inescapable feature of Java, they buy you throughput, simpler code and responsive UIs — and in exchange they hand you three new classes of bugs: safety, liveness and performance hazards.

📖 pp. 1–9 🧩 4 sections · 2 listings · 1 figure ⏱️ ~10 min read

Chapter in one paragraph

TL;DR — the five things worth remembering

  1. Concurrency exists because of hardware and human nature. Processes were invented for resource utilization, fairness and convenience; threads were invented for exactly the same three reasons, but inside a process.
  2. Threads buy you three things: use of multiple processors (throughput), a simpler sequential-looking model for asynchronous work, and a UI that does not freeze.
  3. Safely hazard: race conditions. value++ is not one operation but three (read, add, write). Without synchronization, two threads can read the same value and produce duplicate results.
  4. Liveness hazards: safety means nothing bad ever happens; liveness means something good eventually happens. Deadlock, starvation and livelock are the ways "eventually" never arrives.
  5. Thread-safety is contagious. Even if you never call new Thread(), Timer, servlets, RMI, Swing/AWT and the JVM itself will call your code from threads you do not own.

1.1A (Very) Brief History of Concurrency

From bare metal → processes → threads: every step was about not wasting an expensive machine.

The sequence-only machine

Early computers had no operating system at all. They ran one program from beginning to end, and that program had direct access to every resource of the machine. Writing for the bare metal was hard, and running one program at a time was a terrible use of hardware that was expensive and scarce.

Processes: isolation with coarse-grained sharing

Operating systems evolved to run several programs at once, each in its own process — an isolated, independently executing program to which the OS allocates resources such as memory, file handles and security credentials. When processes needed to talk to each other, they used deliberately coarse-grained mechanisms: sockets, signal handlers, shared memory, semaphores and files.

⚙️
Resource utilization

Programs must wait for I/O and can do no useful work while waiting. Better to run someone else in that gap.

⚖️
Fairness

Multiple users and programs may have equal claims on the machine. Time-slicing beats "run to completion, then the next one".

🧰
Convenience

Writing several small single-task programs that coordinate is often easier than writing one program that does everything.

The sequential programming model

Each process in an early timesharing system was effectively a virtual von Neumann computer: a memory space holding instructions and data, instructions executed one after another per the machine language semantics, and interaction with the outside world through OS I/O primitives. For every instruction executed there is a well-defined "next instruction". Nearly every language in use today follows this model, so the specification tells you exactly "what comes next" after any action.

The model is intuitive because it mirrors how people work: get out of bed, put on your bathrobe, go downstairs, start the tea. Each of those is itself a sequence of finer actions — and one of them, waiting for the water to boil, is inherently asynchronous. While the kettle heats you can wait, or start the toast, or fetch the newspaper, while staying aware that your attention will soon be needed. The kettle and toaster "know" they are used asynchronously, so they signal audibly when done. The same balance of sequentiality and asynchrony characterises efficient people — and efficient programs.

Threads: concurrency inside a single process

The same three motivations — utilization, fairness, convenience — drove the move from processes to threads. Threads let multiple streams of control flow coexist within a process. They share process-wide resources (memory, file handles), but each thread has its own program counter, stack and local variables. They are the natural decomposition for exploiting hardware parallelism, and most modern OSs schedule threads, not processes — hence the nickname "lightweight processes".

⚠️

The catch, stated in the first page: without explicit coordination, threads run simultaneously and asynchronously. A thread may modify variables that another thread is in the middle of using, with unpredictable results. That single sentence is the whole book.

1.2Benefits of Threads

Used properly, threads lower development and maintenance cost and raise performance.

Threads make it easier to model how humans actually work by turning asynchronous workflows into mostly sequential ones, and they turn convoluted code into straight-line code that is easier to write, read and maintain. They help GUI applications stay responsive, help server applications with utilization and throughput, and even simplify the JVM itself — the garbage collector usually runs in one or more dedicated threads. Most non-trivial Java applications depend on threads for their organization.

1.2.1Exploiting multiple processors

Multiprocessors were once exotic; now even low-end servers and mid-range desktops have several cores, and the trend only accelerates — clock rates are getting harder to scale, so manufacturers add cores per chip instead.

Because the basic unit of scheduling is the thread, a single-threaded program can use at most one processor: on a 2-core machine it leaves half the CPU idle, on a 100-core machine it gives up 99%. A well-designed multithreaded program can execute on many cores at once and improve throughput. Threads also help on a single-processor machine: when one thread blocks on synchronous I/O the CPU would sit idle, but another thread can run — like reading the newspaper while the water boils instead of waiting for it first.

1.2.2Simplicity of modeling

One type of task ("fix these twelve bugs") is easier to manage than five types with competing priorities; context switching between them costs you. Software is the same: a program that processes one kind of task sequentially is simpler to write, less error-prone and easier to test than one juggling many at once. Assigning a thread to each type of task — or to each element of a simulation — gives the illusion of sequentiality and insulates your domain logic from scheduling details, interleaved operations, asynchronous I/O and resource waits.

Frameworks such as servlets and RMI exploit exactly this: the framework handles request management, thread creation and load balancing, and calls your component at the right point in the workflow. The servlet author does not have to think about how many other requests are in flight or whether the socket streams block — the service method can process its request synchronously, as if it were a single-threaded program.

1.2.3Simplified handling of asynchronous events

A server accepting connections from many clients is much easier to write when each connection gets its own thread and may use straightforward synchronous I/O, instead of a single loop multiplexing non-blocking channels. Historically OSes capped threads per process at a few hundred, which is why multiplexed I/O (select, poll) and java.nio exist. Modern OS thread support has improved dramatically — the NPTL package in Linux was designed for hundreds of thousands of threads — so the thread-per-client model is practical far more often than it used to be.

1.2.4More responsive user interfaces

Old GUIs were single-threaded: you either polled for events everywhere (messy and intrusive) or ran all application code through a "main event loop". Any slow code called from that loop froze the interface, because later events could not be processed until control returned.

AWT and Swing replace the main event loop with an event dispatch thread (EDT). Most GUI frameworks are single-threaded subsystems, so the loop is effectively still there — it just runs in a thread owned by the toolkit rather than by your application. Short-lived tasks keep the UI responsive; a long-running task in the EDT (spell-checking a big document, fetching over the network) ruins responsiveness — and worse, the user cannot even cancel it, because the cancel button's event is queued behind the very task it would cancel. Move the long task to another thread and the event thread stays free.

💡

All four benefits are really one idea: threads let you write straight-line, synchronous-looking code while the world stays asynchronous. The cost of that illusion is paid in the next section.

1.3Risks of Threads

A double-edged sword: Java's language support, library support and formal memory model make portable concurrent code possible — and make every mainstream developer responsible for it.

1.3.1Safety hazards

Thread safety is unusually subtle because, without sufficient synchronization, the ordering of operations across threads is unpredictable — and sometimes surprising. UnsafeSequence (Listing 1.1) is supposed to return a unique value on every call. It is perfectly correct single-threaded, and broken multi-threaded.

DON'T DO THIS Listing 1.1 · Non-thread-safe Sequence Generator 
@NotThreadSafe
public class UnsafeSequence {
    private int value;

    /** Returns a unique value. */
    public int getNext() {
        return value++;
    }
}

With unlucky timing two threads call getNext() and receive the same value. value++ looks atomic but is three operations: read the value, add one, write the new value. Both threads can read the same value, both add one, both write — and one increment vanishes. Figure 1.1 shows exactly this interleaving.

Interleaving diagrams like this one always depict time running left to right, one row per thread, and usually show the worst case, to warn against assuming things happen in a particular order. As the book notes in a footnote, the real worst case can be even worse than these diagrams suggest, because of reordering (Chapter 3).

Annotations you will meet all over this book

@NotThreadSafe, @ThreadSafe and @Immutable are custom, documentation-only annotations (Appendix A) that describe a class's concurrency contract; @GuardedBy (Section 2.4) records which lock protects a field. They help three audiences: users can trust @ThreadSafe classes, maintainers know which guarantees must be preserved, and analysis tools can flag violations.

UnsafeSequence demonstrates a race condition: whether the specification is honoured depends on how the runtime happens to interleave operations — which is not a state of affairs you want to ship. Making getNext synchronized fixes it (Listing 1.2), for reasons that occupy Chapters 2 and 3.

THREAD-SAFE Listing 1.2 · Thread-safe Sequence Generator 
@ThreadSafe
public class Sequence {
    @GuardedBy("this") private int nextValue;

    public synchronized int getNext() {
        return nextValue++;
    }
}

Without synchronization the compiler, the hardware and the runtime may take substantial liberties with the timing and ordering of actions — caching variables in registers or processor-local caches where they are temporarily (or permanently) invisible to other threads. These tricks exist for performance and are generally desirable, but they put the burden on you to identify clearly where data is shared across threads. Chapter 16 has the gory details of the JMM; follow the rules in Chapters 2 and 3 and you can skip them.

1.3.2Liveness hazards

Safety is not negotiable. But safety is only half of correctness. In a single-threaded program, an accidental infinite loop means the code after the loop never runs; with threads you get entire new failure modes.

ConcernSloganFailure looks like
Safety "Nothing bad ever happens." Wrong results — corrupted counts, duplicate sequence numbers, half-updated objects.
Liveness "Something good eventually happens." Permanent inability to make progress: deadlock (Ch. 10.1), starvation (10.3.1), livelock (10.3.3).
Performance "…and it happens quickly." Poor service time, responsiveness, throughput, resource consumption or scalability.

If thread A waits forever for a resource that thread B holds exclusively and never releases, A makes no progress. Like most concurrency bugs, liveness failures depend on the relative timing of events in different threads, so they are elusive — they routinely escape development and testing.

1.3.3Performance hazards

A well-designed concurrent application is a net performance win, but threads have real runtime costs:

  • Context switches — the scheduler suspends the running thread so another can run: saving and restoring execution context, loss of locality, and CPU time spent scheduling instead of running.
  • Synchronization — can inhibit compiler optimizations, flush or invalidate memory caches, and create traffic on the shared memory bus. Chapter 11 covers measuring and reducing these costs.

1.4Threads are Everywhere

You do not have to create a thread to be writing multithreaded code.

Frameworks create threads on your behalf, and code called from those threads must be thread-safe. That places a real design burden on developers, because thread-safe classes need more care and analysis than non-thread-safe ones. Every Java application uses threads: when the JVM starts it creates housekeeping threads (garbage collection, finalization) plus a main thread for main().

⏲️
Timer

TimerTasks run in a thread owned by the Timer, not by your application. Any state a task touches must be safe for every other path that touches it — usually achieved by making the shared objects themselves thread-safe.

🌐
Servlets & JSP

The spec requires a servlet to be callable from multiple threads at once. Even a one-request-at-a-time servlet shares ServletContext and HttpSession state with filters and other servlets.

📡
RMI

Remote calls arrive on RMI-managed threads. The same remote method on the same object can be invoked concurrently. Remote objects must guard their own state too, not just state shared with others.

🖥️
Swing & AWT

Swing components such as JTable are not thread-safe. Safety comes from confinement to the event thread; to touch the GUI from elsewhere, hand the work to the event thread.

When a framework introduces concurrency it is usually impossible to confine the concurrency-awareness to framework code, because frameworks make callbacks into application components that in turn touch application state. Thread safety is contagious: it starts with the framework entry point and ripples through every code path that reaches shared state.

🔁

The ripple, in one line: framework thread → your component → shared application state → every other code path that reads or writes that same state.

“It would be nice to believe that concurrency is an ‘optional’ or ‘advanced’ language feature, but the reality is that nearly all Java applications are multithreaded.” — Chapter 1, Section 1.4

1The hazard, in full

RACE CONDITION UnsafeSequence — annotated walkthrough 
@NotThreadSafe
public class UnsafeSequence {
    private int value;

    /**
     * Returns a unique value.
     *
     * Looks atomic, is not. value++ compiles to three actions:
     *   1. read  value      (both threads may read 9)
     *   2. add   1          (both threads compute 10)
     *   3. write value      (both threads store 10 -> one increment lost)
     *
     * The class is correct single-threaded and incorrect multi-threaded.
     */
    public int getNext() {
        return value++;
    }
}

2Reproducing it — a runnable main

Race conditions are probabilistic: a single run may look fine, so loop many times with several threads. When you see two threads receive the same number, or a final count smaller than the number of calls, you have caught it.

DEMO RaceDemo — two threads, many calls 
public class RaceDemo {

    public static void main(String[] args) throws InterruptedException {
        for (int attempt = 0; attempt < 20; attempt++) {
            UnsafeSequence seq = new UnsafeSequence();
            int callsPerThread = 10_000;

            Thread t1 = new Thread(() -> { for (int i = 0; i < callsPerThread; i++) seq.getNext(); });
            Thread t2 = new Thread(() -> { for (int i = 0; i < callsPerThread; i++) seq.getNext(); });

            t1.start();
            t2.start();
            t1.join();
            t2.join();

            int expected = 2 * callsPerThread;
            // getNext() is private about its counter; expose a getter or read the
            // value through reflection/Instrumentation to compare. Typical output:
            //   expected 20000, got 19674  -> lost updates
            System.out.println("attempt " + attempt + ": expected " + expected);
        }
    }
}

In practice, value++ is fast enough that lost updates are easy to miss; that is precisely why the book calls these bugs subtle. Adding a tiny amount of work between the read and the write — or simply running on more cores — makes them far more likely.

3Fix A — the book's answer: synchronized

SAFE Sequence — mutual exclusion via the intrinsic lock 
@ThreadSafe
public class Sequence {

    // @GuardedBy("this"): every read and write of nextValue happens with
    // this object's monitor held. Documentation, not enforcement.
    @GuardedBy("this") private int nextValue;

    public synchronized int getNext() {
        return nextValue++;
    }
}

synchronized makes the read-modify-write atomic with respect to other threads holding the same lock, and it adds the memory-visibility guarantees that stop the compiler, hardware and runtime from hiding the update in a register (Chapters 2, 3 and 16).

4Fix B — the library alternative: AtomicInteger

Chapter 2's pattern: when a class already implements the atomicity you need, use it instead of hand-rolling a lock. No blocking, and the intent is obvious to a reader.

SAFE AtomicSequence — lock-free counter 
import java.util.concurrent.atomic.AtomicInteger;

@ThreadSafe
public class AtomicSequence {
    private final AtomicInteger value = new AtomicInteger();

    /** Returns a unique value; getAndIncrement is atomic, so no lost updates. */
    public int getNext() {
        return value.getAndIncrement();
    }
}

Chapter 2 — Thread Safety

Concurrent programming isn't really about threads or locks — any more than civil engineering is about rivets and I-beams. It is about managing access to shared, mutable state. This chapter builds the vocabulary: correctness, atomicity, race conditions, intrinsic locks, guarding, and the trade-off between safety and concurrency.

Brian Goetz, with Tim Peierls, Joshua Bloch, Joseph Bowbeer, David Holmes & Doug Lea

📖 Pages 11–22 🧩 5 sections · 8 listings · 1 figure ⏱️ ~14 min read 🏷️ Part I — Fundamentals

Chapter in one paragraph

TL;DR — the six things worth remembering

  1. State, not code. An object's state is any data that can affect its externally visible behaviour. Thread safety is about protecting shared mutable state, and whether a class needs it depends on how it is used, not what it does.
  2. Define it by correctness. A class is thread-safe if it behaves correctly when accessed from multiple threads, regardless of scheduling or interleaving, with no extra coordination by callers.
  3. Stateless objects are always thread-safe. StatelessFactorizer has no fields, so two threads cannot interfere — it is as if each had its own instance.
  4. Adding one state variable breaks it. ++count is read-modify-write, not atomic. Fix: hand the state to a thread-safe object such as AtomicLong.
  5. Adding two reveals the real problem: invariants. lastNumber and lastFactors must change together, so each atomic reference alone is useless — compound actions need a lock.
  6. Locks: all or nothing, on the same lock. Guard every access with the same lock; guard every variable in an invariant with the same lock; but hold locks for as short a time as correctness allows — or lose concurrency (Figure 2.1).

§State is the whole story

"Writing thread-safe code is, at its core, about managing access to state — and in particular to shared, mutable state."

🗃️
State

An object's data, in state variables such as instance or static fields — including fields of dependent objects (HashMap state lives partly in Map.Entry objects). Anything that can affect externally visible behaviour.

🤝
Shared

A variable that could be accessed by multiple threads — not whether it is today, but whether it could be.

🔁
Mutable

Its value could change during its lifetime. Shared + mutable + no coordination = a broken program.

⚠️

The rule, with no exceptions: whenever more than one thread accesses a given state variable and one of them might write to it, they all must coordinate their access using synchronization. A program that omits it "might appear to work, passing its tests and performing well for years, but it is still broken and may fail at any moment."

The good news: the same object-oriented techniques that make code maintainable — encapsulation, data hiding, clear specification of invariants — are exactly what make it thread-safe. The less code that can touch a variable, the easier it is to ensure every access holds the right lock. Java won't force you to encapsulate state (public fields are legal), but well-encapsulated state is the difference between a feasible and an impossible thread-safety argument.

💡

Sometimes design and performance collide, and encapsulation must give way — but make it right first, then make it fast, and only if measurements demand it. In concurrent code this discipline matters even more, because a tiny performance gain on a cold path can be dwarfed by the risk of a field failure.

Thread safety is a property of code that encapsulates its state — an object, or a whole program. A program built entirely from thread-safe classes need not be thread-safe, and a thread-safe program may contain unsafe classes; composition is a topic in Chapter 4.

2.1What is Thread Safety?

Every informal definition ("can be called from multiple threads without unwanted interactions") is circular: it amounts to "a class is thread-safe if it can be used safely from multiple threads."

At the heart of any reasonable definition is correctness. Correctness means a class conforms to its specification; a good specification defines invariants constraining state and post-conditions describing the effects of operations. Since we rarely write such specifications, "we know it when we see it" is as close as many of us get — but granting that, thread safety can be stated without circularity:

A class is thread-safe if it behaves correctly when accessed from multiple threads, regardless of the scheduling or interleaving of the execution of those threads by the runtime environment, and with no additional synchronization or other coordination on the part of the calling code. — Chapter 2, Section 2.1

Two consequences. First, since any single-threaded program is also a valid multithreaded program, a class that is not correct single-threaded cannot be thread-safe. Second, no sequence of operations — calls, reads, writes — should be able to violate invariants or post-conditions, and no interleaving of such operations may put an instance into an invalid state. And crucially: thread-safe classes encapsulate their own synchronization, so clients need not provide any.

2.1.1Example: a stateless servlet

Thread-safety requirements usually arrive not from a decision to use threads, but from a decision to use a framework — here, a servlet-based factorization service that we extend step by step, keeping it safe.

THREAD-SAFE Listing 2.1 · A Stateless Servlet 
@ThreadSafe
public class StatelessFactorizer implements Servlet {
    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        BigInteger[] factors = factor(i);
        encodeIntoResponse(resp, factors);
    }
}

Like most servlets it is stateless: no fields, and no references to fields of other classes. The transient state of a computation lives only in local variables, stored on the thread's stack and reachable only by the executing thread. One thread cannot influence another thread's computation, because they share nothing — it is as if each had its own instance.

✅

Stateless objects are always thread-safe. That is why most servlets are easy to keep safe — trouble starts only when a servlet wants to remember something between requests.

2.2Atomicity

Add one field — a hit counter — and a working class becomes a broken one.

@NotThreadSafe

    private long count = 0;

    public long getCount() { return count; }

    public void service(ServletRequest req, ServletResponse resp) {

++count looks like one action because of its compact syntax, but it is shorthand for three discrete operations: fetch the current value, add one, write the new value back. A read-modify-write operation derives its result from the previous state — so if two threads read 9, both write 10, and a hit is lost forever (Figure 1.1, Chapter 1).

"A slightly inaccurate hit counter is acceptable" you might think — and sometimes it is. But when the same number generates sequences or unique object identifiers, returning the same value twice causes serious data integrity problems. Incorrect results that depend on unlucky timing have a name: a race condition.

2.2.1Race conditions

A race condition occurs when correctness depends on the relative timing or interleaving of multiple threads — when getting the right answer relies on lucky timing. The most common variety is check-then-act: a potentially stale observation decides what to do next.

🔍

Race condition ≠ data race. A data race arises when synchronization is not used to coordinate all access to a shared non-final field; code with data races has no useful defined semantics under the Java Memory Model. Not all race conditions are data races and vice versa — but UnsafeCountingFactorizer has both. Details in Chapter 16.

2.2.2Race conditions in lazy initialization

Lazy initialization is the canonical check-then-act idiom: defer creating an object until it is needed, while making sure it is initialized only once.

DON'T DO THIS Listing 2.3 · Race Condition in Lazy Initialization 
@NotThreadSafe
public class LazyInitRace {
    private ExpensiveObject instance = null;

    public ExpensiveObject getInstance() {
        if (instance == null)              // check
            instance = new ExpensiveObject();  // act
        return instance;
    }
}

Threads A and B both call getInstance. A sees null and starts building an ExpensiveObject. B checks instance: whether it is null depends unpredictably on timing — scheduling vagaries, and how long A takes to construct the object and assign the field. If it is still null, two callers receive two different instances even though the method promises one. A registry would lose registrations; two components would see inconsistent views of the registered set.

Read-modify-write is the other family: the new state is derived from the old, so you must know the previous value and be sure nobody else changes it mid-update. Like most concurrency errors, these need unlucky timing — so they don't always fail. That is what makes them dangerous.

2.2.3Compound actions

Both examples are sequences of operations that must be atomic — indivisible — relative to other operations on the same state. We need to stop other threads from using a variable while we are mid-modification, so they can observe or modify it only before we start or after we finish.

Definitions worth memorising

Atomic with respect to each other: from the perspective of a thread executing A, when another thread executes B, either all of B has executed or none of it has.
Atomic operation: atomic with respect to all operations, including itself, on the same state.
Compound actions: check-then-act and read-modify-write sequences that must execute atomically to remain thread-safe.

Fix the counter by delegating its state to an existing thread-safe class:

public class CountingFactorizer implements Servlet {
    private final AtomicLong count = new AtomicLong(0);

    public long getCount() { return count.get(); }

✅

Rule of thumb: when a single element of state is added to a stateless class, the result is thread-safe if that state is entirely managed by a thread-safe object. Where practical, use existing thread-safe objects like AtomicLong — it is easier to reason about their states and transitions than about arbitrary variables. But going from one state variable to two is not as simple as going from zero to one.

2.3Locking

Two related state variables, one invariant — and atomic references are not enough.

Suppose we cache the most recent result, in case two consecutive clients ask for the same number. We must remember two things: the last number factored, and its factors. Can we just use two AtomicReferences?

DON'T DO THIS Listing 2.5 · Caching without adequate atomicity 
@NotThreadSafe
public class UnsafeCachingFactorizer implements Servlet {
    private final AtomicReference<BigInteger> lastNumber
        = new AtomicReference<BigInteger>();
    private final AtomicReference<BigInteger[]> lastFactors
        = new AtomicReference<BigInteger[]>();

    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        if (i.equals(lastNumber.get()))
            encodeIntoResponse(resp, lastFactors.get());
        else {
            BigInteger[] factors = factor(i);
            lastNumber.set(i);
            lastFactors.set(factors);
            encodeIntoResponse(resp, factors);
        }
    }
}

Each reference is individually thread-safe, yet the servlet can return the wrong answer. Its invariant is that the product of the factors in lastFactors equals the value in lastNumber. When several variables participate in one invariant they are not independent: updating one constrains the others, so they must be updated in a single atomic operation. Between lastNumber.set(i) and lastFactors.set(factors) there is a window in which another thread sees the invariant broken — and the two values cannot be fetched simultaneously either.

🔗

To preserve state consistency, update related state variables in a single atomic operation.

2.3.1Intrinsic locks

Java's built-in mechanism for enforcing atomicity is the synchronized block. It has two parts: a reference to the object that will serve as the lock, and the block of code guarded by it. A synchronized method is shorthand for a block spanning the whole method body, with the object on which the method is invoked as the lock; static synchronized methods use the Class object.

SYNTAX The synchronized block 
synchronized (lock) {
    // Access or modify shared state guarded by lock
}

Every Java object can implicitly act as a lock. These built-in locks are intrinsic locks or monitor locks. A thread automatically acquires the lock on entering a synchronized block and automatically releases it on leaving — by the normal control path or by an exception thrown out of the block. There is no other way to acquire it.

Intrinsic locks act as mutexes (mutual exclusion locks): at most one thread owns the lock. When thread A asks for a lock held by B, A blocks until B releases it — and if B never releases it, A waits forever. Because only one thread at a time executes code guarded by a given lock, synchronized blocks guarded by the same lock execute atomically with respect to one another: in the transactional sense, a group of statements appears to execute as one indivisible unit, and no thread can observe another in the middle of such a block.

SAFE BUT SLOW Listing 2.6 · Correct, but unacceptably poor concurrency 
@ThreadSafe
public class SynchronizedFactorizer implements Servlet {
    @GuardedBy("this") private BigInteger lastNumber;
    @GuardedBy("this") private BigInteger[] lastFactors;

    public synchronized void service(ServletRequest req,
                                     ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        if (i.equals(lastNumber))
            encodeIntoResponse(resp, lastFactors);
        else {
            BigInteger[] factors = factor(i);
            lastNumber = i;
            lastFactors = factors;
            encodeIntoResponse(resp, factors);
        }
    }
}

This is thread-safe, but extreme: it stops multiple clients from using the servlet at all. That is a performance problem, not a safety problem, and Section 2.5 fixes it.

2.3.2Reentrancy

When a thread requests a lock another thread holds, it blocks. But if a thread requests a lock it already holds, the request succeeds — intrinsic locks are reentrant. Reentrancy means locks are acquired per-thread, not per-invocation (unlike the default behaviour of pthreads mutexes). It is implemented by associating an acquisition count and an owner with each lock: zero means unheld; a first acquisition records the owner and sets the count to one; the same thread acquiring again increments it; each exit from the synchronized block decrements it, and at zero the lock is released.

Reentrancy facilitates encapsulation of locking behaviour, which is why the natural-looking subclass code below works instead of deadlocking:

REENTRANCY Listing 2.7 · Code that would deadlock if intrinsic locks were not reentrant 
public class Widget {
    public synchronized void doSomething() {
        ...
    }
}

public class LoggingWidget extends Widget {
    public synchronized void doSomething() {
        System.out.println(toString() + ": calling doSomething");
        super.doSomething();
    }
}

Both doSomething methods are synchronized, so each tries to acquire the lock on the Widget before proceeding. Without reentrancy, the call to super.doSomething() would never acquire the lock — it is "already held" — and the thread would permanently stall waiting for a lock it can never get. Reentrancy saves us from deadlock here.

2.4Guarding State with Locks

Locks serialize access to the code paths they guard — so use them to build protocols, and follow the protocols consistently.

Holding a lock for the entire duration of a compound action can make it atomic. But merely wrapping the action in a synchronized block is not sufficient:

🔐

If synchronization is used to coordinate access to a variable, it is needed everywhere that variable is accessed — and the same lock must be used everywhere it is accessed. It is a common mistake to think synchronization matters only for writes; it does not (Section 3.1 explains why).

The guarding rule

For each mutable state variable that may be accessed by more than one thread, all accesses to that variable must be performed with the same lock held. We then say the variable is guarded by that lock. @GuardedBy documents the lock; nothing enforces it.

There is no inherent relationship between an object's intrinsic lock and its state: fields need not be guarded by their owner's intrinsic lock, though that convention is common and perfectly valid. Acquiring a lock prevents exactly one thing: other threads acquiring that same lock. It does not stop them touching the object. Every object having a built-in lock is just a convenience so you needn't create lock objects — arguably a design decision the book calls "probably a bad one", since it forces JVM implementers to trade off object size against locking performance.

Every shared, mutable variable should be guarded by exactly one lock — and make it clear to maintainers which one. The common convention (used by Vector and the other synchronized collections) is to encapsulate all mutable state in the object and guard every path with the object's intrinsic lock. But nothing about it is special, neither compiler nor runtime enforces it, and it is easily subverted by adding a method that forgets to synchronize. Tools like FindBugs can flag a variable that is frequently but not always accessed under a lock.

Only mutable data accessed from multiple threads needs guarding. That qualification is where programs get into trouble: adding one TimerTask that snapshots program state every ten minutes brings a second thread into contact with all that state — so the task and every other code path that touches the same data now needs synchronization. What required none now requires it everywhere.

Invariants force shared locks

When a class has invariants involving more than one state variable, there is an additional requirement: each variable participating in the invariant must be guarded by the same lock, so they can be read or updated in one atomic operation. SynchronizedFactorizer obeys this: the cached number and the cached factors share the servlet's intrinsic lock.

Why not synchronize everything?

Indiscriminate synchronized is simultaneously too much and too little. Too little:

STILL RACY Put-if-absent on a Vector — both methods are atomic, the pair is not 
if (!vector.contains(element))
    vector.add(element);

Two synchronized methods, one compound action, still a race. Synchronizing methods makes individual operations atomic; a compound action needs additional locking (see Section 4.4 for safe ways to add atomic operations to thread-safe classes). And too much: synchronizing every method invites the liveness and performance problems of SynchronizedFactorizer.

2.5Liveness and Performance

Caching bought us a need for state; state bought us a need for synchronization; the coarse lock we chose then destroyed concurrency.

Because service is synchronized in SynchronizedFactorizer, one thread at a time runs it. That subverts the servlet framework's purpose — handling multiple requests simultaneously — and with high load it leaves users waiting. Short requests that hit the cache must still wait behind long ones, and on multi-CPU systems processors sit idle. Figure 2.1 shows the requests queueing up: the number of simultaneous invocations is limited not by available processing resources but by the structure of the application. This is what the book calls poor concurrency.

The fix is to narrow the scope of the synchronized block — while being careful not to make it so small that an operation which should be atomic gets split across blocks. Excluding long-running operations that do not touch shared state is exactly the right trade.

THREAD-SAFE + CONCURRENT Listing 2.8 · Servlet that Caches its Last Request and Result 
@ThreadSafe
public class CachedFactorizer implements Servlet {
    @GuardedBy("this") private BigInteger lastNumber;
    @GuardedBy("this") private BigInteger[] lastFactors;
    @GuardedBy("this") private long hits;
    @GuardedBy("this") private long cacheHits;

    public synchronized long getHits() { return hits; }
    public synchronized double getCacheHitRatio() {
        return (double) cacheHits / (double) hits;
    }

    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        BigInteger[] factors = null;
        synchronized (this) {                 // short block: cache check + counters
            ++hits;
            if (i.equals(lastNumber)) {
                ++cacheHits;
                factors = lastFactors.clone();
            }
        }
        if (factors == null) {
            factors = factor(i);              // long, expensive, NOT holding the lock
            synchronized (this) {             // short block: publish both fields together
                lastNumber = i;
                lastFactors = factors.clone();
            }
        }
        encodeIntoResponse(resp, factors);
    }
}

Two short synchronized blocks: one guards the check-then-act test and the counters, the other guards updating both cached values together. Everything outside them works only on local (stack) variables, which are not shared and need no synchronization. Note the use of clone(): the cached array must not be handed out, or a caller could mutate the cache's state from outside the lock.

The book also drops AtomicLong here: it would be safe, but since synchronized blocks are already needed for the compound actions, mixing two synchronization mechanisms would be confusing with no safety or performance benefit.

⚖️

The balance. Acquiring and releasing a lock costs something, so don't shred synchronized blocks either (splitting ++hits into its own block gains nothing and is not worth it). Hold the lock while accessing state variables and for the duration of compound actions; release it before long-running or potentially blocking work. Safety first — resist sacrificing simplicity for performance — then simplicity and performance can usually be balanced, as CachedFactorizer shows.

Avoid holding locks during lengthy computations or operations at risk of not completing quickly, such as network or console I/O. A lock held long, whether for CPU-bound work or because it wraps a blocking call, is an invitation to liveness and performance failure.

Chapter 3 — Sharing Objects

Chapter in one paragraph

TL;DR — the six things worth remembering

  1. Synchronization is not only about atomicity. It is also about memory visibility: without it, a thread may never see another thread's writes, or may see them out of order (reordering).
  2. Stale data is not all-or-nothing. A thread can see an up-to-date ready and a stale number — so NoVisibility can print 0 or never terminate.
  3. Locking does double duty. Everything a thread did before releasing a lock is visible to the next thread that acquires that same lock — which is why reads need the lock too.
  4. volatile gives visibility and ordering, not atomicity. Use it for flags and for publishing immutable objects; it cannot make count++ atomic.
  5. Escape defeats confinement. Publishing an object — even through an inner-class listener or a constructor — publishes everything reachable from it. Never let this escape during construction.
  6. Immutability is the end-run. Immutable objects (unmodifiable state, all fields final, proper construction) are always thread-safe and get initialization safety — and mutable objects must be safely published and either thread-safe or lock-guarded.

3.1Visibility

"In a single-threaded environment, if you write a value and later read it with no intervening writes, you get the same value back. When the reads and writes occur in different threads, this is simply not the case."

It is a common misconception that synchronized is only about atomicity, or about demarcating critical sections. Synchronization has a second, subtler role: memory visibility. We want not only to stop one thread modifying an object while another uses it, but to guarantee that when a thread does modify state, other threads can actually see the change. Without synchronization, there is no guarantee that a reading thread sees a write on a timely basis — or at all.

DON'T DO THIS Listing 3.1 · Sharing Variables without Synchronization 
public class NoVisibility {
    private static boolean ready;
    private static int number;

    private static class ReaderThread extends Thread {
        public void run() {
            while (!ready)
                Thread.yield();
            System.out.println(number);
        }
    }

    public static void main(String[] args) {
        new ReaderThread().start();
        number = 42;
        ready = true;
    }
}

It looks obvious that this prints 42. It is not: it may print zero, or never terminate at all. The reader may never observe ready becoming true — and even if it does, it may see the write to ready before the write to number. That is reordering: nothing guarantees that operations in one thread happen in the order written, as long as the reordering is undetectable from within that thread — even when it is glaringly obvious to other threads.

🌀

This is not a bug in Java, it is a deliberate trade for speed: the JMM lets the compiler reorder operations and cache values in registers, and lets CPUs reorder operations and cache values in processor-specific caches (Chapter 16). Reasoning about the "must happen" order of memory actions in insufficiently synchronized programs will almost certainly be incorrect.

NoVisibility is about as simple as a concurrent program gets — two threads, two variables — and it is still easy to be wrong about whether it terminates. The way out is not cleverness: always use proper synchronization whenever data is shared across threads.

3.1.1Stale data

Unless synchronization is used every time a variable is accessed, it is possible to see a stale value. Worse, staleness is not all-or-nothing: a thread can see an up-to-date value of one variable and a stale value of another that was written first. Stale data is behind some of the nastiest failures — unexpected exceptions, corrupted data structures, inaccurate computations and infinite loops. With object references (say, links in a list) it can be catastrophic.

3.1.2Non-atomic 64-bit operations

An unsynchronized read may be stale, but at least it sees some value actually placed there by some thread — never a random one. This guarantee is called out-of-thin-air safety. It applies to every variable with one exception: 64-bit numerics (long and double) that are not volatile. The JMM requires fetch and store to be atomic, but for non-volatile long/double the JVM may split a 64-bit access into two 32-bit operations — so you can read the high half of one value and the low half of another. Hence: never share mutable long/double fields unless they are volatile or lock-guarded.

3.1.3Locking and visibility

Intrinsic locking guarantees that one thread sees another's effects predictably. When A executes a synchronized block and B later enters a block guarded by the same lock, every value visible to A before it released the lock is guaranteed visible to B after acquiring it. In the book's phrasing: everything A did in or prior to a synchronized block is visible to B when it executes a synchronized block guarded by the same lock.

This gives the other reason for the rule from Chapter 2 — all threads must synchronize on the same lock when touching a shared mutable variable. Locking is not just about mutual exclusion; it is also about memory visibility. A reader that doesn't hold the lock may see a stale value.

3.1.4Volatile variables

volatile is a weaker form of synchronization that ensures updates to a variable are propagated predictably. Declaring a field volatile puts the compiler and runtime on notice that the variable is shared and that operations on it must not be reordered with other memory operations. Volatile variables are never cached where other processors cannot see them, so a read always returns the most recent write by any thread.

Three useful ways to think about volatile

1. As SynchronizedInteger. Reads and writes behave roughly like calls to the synchronized get/set — but with no locking, so the thread never blocks.
2. As a fence for surrounding state. Everything visible to A before writing a volatile is visible to B after reading it. Writing a volatile is like exiting a synchronized block; reading it is like entering one.
3. As a one-way door. It guarantees visibility only — never atomicity.

Do not lean on volatile for the visibility of arbitrary state: code that does is more fragile and harder to understand than code that uses locking. Good uses are narrow — ensuring visibility of the variable's own state, of the object it refers to, or signalling a lifecycle event such as initialization or shutdown.

TYPICAL USE Listing 3.4 · Counting Sheep — a volatile status flag 
volatile boolean asleep;
...
    while (!asleep)
        countSomeSheep();

Without volatile, the loop might never notice that another thread set asleep. A locking version would also work, but would be more cumbersome. (Debugging tip from the book: always run the -server JVM even in development — a server JIT can hoist the flag test out of the loop and turn this into an infinite loop, whereas the client JVM might not, hiding the bug until production.)

🧾

Use volatile only when all three hold: (1) writes do not depend on the current value, or only one thread ever updates it; (2) the variable does not participate in invariants with other state variables; and (3) locking is not needed for any other reason while it is accessed. Locking gives visibility and atomicity; volatile gives only visibility.

3.2Publication and Escape

Publishing means making an object available to code outside its current scope — and every escape route publishes more than you think.

Publishing an object means making it available outside its current scope: storing a reference where other code can find it, returning it from a non-private method, or passing it to a method in another class. Publishing internal state compromises encapsulation and makes invariants hard to preserve; publishing an object before it is fully constructed compromises thread safety. An object published when it should not have been has escaped.

PUBLICATION Listing 3.5 · Publishing an Object 
public static Set<Secret> knownSecrets;

public void initialize() {
    knownSecrets = new HashSet<Secret>();
}

The most blatant form of publication is a public static field, visible to every class and thread. And publishing one object may publish others: add a Secret to knownSecrets and any code can iterate the set and get a reference to it. More generally, any object reachable from a published object by following non-private fields and method calls is also published.

DON'T DO THIS Listing 3.6 · Allowing Internal Mutable State to Escape 
class UnsafeStates {
    private String[] states = new String[] {
        "AK", "AL" ...
    };
    public String[] getStates() { return states; }
}

The array was supposed to be private; now any caller can modify its contents. It has escaped. Passing an object to an alien method — one whose behaviour is not fully specified by the current class, including methods of other classes and overrideable (non-private, non-final) methods of this one — is also publication: you cannot know whether it stores the reference, or hands it to another thread. Whether anyone actually misuses the reference is beside the point: once an object escapes, assume it may be misused. That is the compelling argument for encapsulation.

DON'T DO THIS Listing 3.7 · Implicitly Allowing the this Reference to Escape 
public class ThisEscape {
    public ThisEscape(EventSource source) {
        source.registerListener(
            new EventListener() {
                public void onEvent(Event e) {
                    doSomething(e);
                }
            });
    }
}

Publishing the anonymous EventListener implicitly publishes the enclosing ThisEscape instance, because inner-class instances hold a hidden reference to their enclosing instance.

3.2.1Safe construction practices

An object is in a predictable, consistent state only after its constructor returns. So publishing it from within its constructor can publish a partially constructed object — even if publication is the last statement in the constructor. If this escapes during construction, the object is not properly constructed.

🏗️

Do not allow the this reference to escape during construction. Two common ways to break this: starting a thread from the constructor (it shares this, explicitly or implicitly), and calling an overrideable instance method from the constructor. Creating a thread in a constructor is fine — starting it is not. Expose a start/initialize method instead.

SAFE Listing 3.8 · Factory method prevents this from escaping 
public class SafeListener {
    private final EventListener listener;

    private SafeListener() {
        listener = new EventListener() {
            public void onEvent(Event e) {
                doSomething(e);
            }
        };
    }

    public static SafeListener newInstance(EventSource source) {
        SafeListener safe = new SafeListener();   // fully constructed first
        source.registerListener(safe.listener);   // ...then published
        return safe;
    }
}

3.3Thread Confinement

One way to avoid needing synchronization is to avoid sharing: if data is only ever accessed from one thread, no synchronization is required.

Thread confinement is one of the simplest ways to achieve thread safety, and when an object is confined to a thread, such usage is automatically thread-safe even if the object itself is not. Swing leans on it heavily: the visual components and data models are not thread-safe; safety comes from confining them to the event dispatch thread (with invokeLater to hand work over). Pooled JDBC Connections are another example — the spec does not require them to be thread-safe, yet the "acquire for one request, return it afterwards" pattern confines each connection to one thread.

Nothing in the language enforces confinement — just as nothing enforces that a variable is guarded by a lock. The libraries offer two helpers (local variables and ThreadLocal), but keeping confined objects from escaping remains the programmer's job.

3.3.1Ad-hoc thread confinement

Ad-hoc confinement is when the entire responsibility for confinement rests with the implementation. It is fragile, because no language feature helps — references to confined objects are often held in plain (even public) fields. It usually arises from a design decision to make a subsystem (the GUI, say) single-threaded, which can offer a simplicity benefit that outweighs the fragility, and can help avoid deadlock. A special case: read-modify-write on a volatile is safe if only one thread ever writes it — confinement of the modification plus volatile visibility. Use ad-hoc confinement sparingly; prefer the stronger forms.

3.3.2Stack confinement

Stack confinement means an object is reachable only through local variables. Local variables live on the executing thread's stack, which no other thread can access. For primitives, you cannot violate this even if you try — there is no way to obtain a reference to a primitive variable. For object references, you must simply not publish them.

STACK-CONFINED Listing 3.9 · Thread confinement of local primitive and reference variables 
public int loadTheArk(Collection<Animal> candidates) {
    SortedSet<Animal> animals;
    int numPairs = 0;
    Animal candidate = null;

    // animals confined to method, don't let them escape!
    animals = new TreeSet<Animal>(new SpeciesGenderComparator());
    animals.addAll(candidates);
    for (Animal a : animals) {
        if (candidate == null || !candidate.isPotentialMate(a))
            candidate = a;
        else {
            ark.load(new AnimalPair(candidate, a));
            ++numPairs;
            candidate = null;
        }
    }
    return numPairs;
}

Using a non-thread-safe object within a thread is still thread-safe — but be careful: the requirement that the object stay confined, and the awareness that it is not thread-safe, often exist only in the developer's head. If the assumption is not documented, a future maintainer will happily let it escape.

3.3.3ThreadLocal

A more formal mechanism: ThreadLocal<T> associates a per-thread value with a value-holding object. get returns the most recent value passed to set by the current thread. It is often used to avoid sharing in designs built on mutable singletons or globals — for example, a per-thread JDBC connection instead of one global connection.

THREAD-CONFINED Listing 3.10 · Using ThreadLocal to Ensure Thread Confinement 
private static ThreadLocal<Connection> connectionHolder
    = new ThreadLocal<Connection>() {
        public Connection initialValue() {
            return DriverManager.getConnection(DB_URL);
        }
    };

public static Connection getConnection() {
    return connectionHolder.get();
}

Conceptually a ThreadLocal<T> holds a Map<Thread,T> — though the values actually live in the Thread object itself, so they can be collected when the thread dies. It is also useful for a frequently used temporary object (a buffer): before Java 5.0, Integer.toString used a ThreadLocal for its 12-byte buffer; Java 5.0 replaced it with a fresh allocation, suggesting the win was not worth it.

⚠️

Thread locals are easy to abuse. Treating confinement as a licence for global variables, or as a source of "hidden method arguments", hurts reusability and creates hidden couplings between classes. Frameworks do use them well — a J2EE container keeping the transaction context in a static ThreadLocal for the duration of an EJB call — at the cost of coupling the code to the framework.

3.4Immutability

If an object's state cannot change, then stale values, lost updates and inconsistent observation simply cannot happen.

An immutable object is one whose state cannot change after construction. Immutable objects are inherently thread-safe: their invariants are established by the constructor, and since state cannot change they always hold. They are also simple — only one state, carefully controlled — and safer: passing a mutable object to untrusted code risks it being modified (now or later, from another thread); immutable objects cannot be subverted, so they are safe to share and publish freely with no defensive copies.

An object is immutable if…

1. its state cannot be modified after construction; 2. all its fields are final; and 3. it is properly constructed (the this reference does not escape during construction).

Note that immutability is not the same as "all fields final": final fields can point at mutable objects. Neither the JLS nor the JMM formally defines immutability.

IMMUTABLE Listing 3.11 · Immutable class built out of mutable underlying objects 
@Immutable
public final class ThreeStooges {
    private final Set<String> stooges = new HashSet<String>();

    public ThreeStooges() {
        stooges.add("Moe");
        stooges.add("Larry");
        stooges.add("Curly");
    }

    public boolean isStooge(String name) {
        return stooges.contains(name);
    }
}

The Set is mutable, yet the design makes it impossible to modify after construction: the reference is final and there is no way to reach the set from outside. Don't be tempted to think immutability is of limited use just because program state changes — there is a difference between an object being immutable and the reference to it being immutable. Updated state is stored by replacing the object with a new instance holding the new state.

3.4.1Final fields

final fields cannot be reassigned (though the object they refer to can still change if it is mutable), and they have special semantics under the Java Memory Model: it is the use of final fields that makes initialization safety (Section 3.5.2) possible — the guarantee that lets immutable objects be shared freely without synchronization. Even for a mutable object, marking some fields final restricts its set of possible states and documents intent. Just as fields should be private unless they need to be visible, they should be final unless they need to be mutable.

3.4.2Using volatile to publish immutable objects

Recall the Chapter 2 failure: two AtomicReferences could not provide atomicity for lastNumber + lastFactors — and volatile would fail for the same reason. But an immutable holder can supply a weak form of atomicity: whenever a group of related data must be acted on atomically, put it in an immutable holder class.

IMMUTABLE HOLDER Listing 3.12 · OneValueCache — a number and its factors, atomically 
@Immutable
class OneValueCache {
    private final BigInteger lastNumber;
    private final BigInteger[] lastFactors;

    public OneValueCache(BigInteger i,
                         BigInteger[] factors) {
        lastNumber  = i;
        lastFactors = Arrays.copyOf(factors, factors.length);
    }

    public BigInteger[] getFactors(BigInteger i) {
        if (lastNumber == null || !lastNumber.equals(i))
            return null;
        else
            return Arrays.copyOf(lastFactors, lastFactors.length);
    }
}

The copyOf calls are what make it immutable — without them the array would leak in and out.

THREAD-SAFE, NO LOCKING Listing 3.13 · VolatileCachedFactorizer 
@ThreadSafe
public class VolatileCachedFactorizer implements Servlet {
    private volatile OneValueCache cache =
        new OneValueCache(null, null);

    public void service(ServletRequest req, ServletResponse resp) {
        BigInteger i = extractFromRequest(req);
        BigInteger[] factors = cache.getFactors(i);
        if (factors == null) {
            factors = factor(i);
            cache = new OneValueCache(i, factors);
        }
        encodeIntoResponse(resp, factors);
    }
}

When a thread sets the volatile field to a new OneValueCache, the new cached data becomes immediately visible; the cache operations cannot interfere with each other because the holder is immutable and the field is read exactly once per path. An immutable holder for related state variables, plus a volatile reference for timely visibility, gives thread safety with no explicit locking at all.

3.5Safe Publication

Sometimes we do want to share. Then the reference and the object's state must both become visible — at the same time.

UNSAFE PUBLICATION Listing 3.14 · Publishing an object without adequate synchronization 
// Unsafe publication
public Holder holder;

public void initialize() {
    holder = new Holder(42);
}

This harmless-looking code can fail badly: another thread may see the Holder in an inconsistent state even though the constructor established its invariants — because the reference became visible before the object's fields did.

3.5.1Improper publication: when good objects go bad

AT RISK Listing 3.15 · Class at risk of failure if not properly published 
public class Holder {
    private int n;

    public Holder(int n) { this.n = n; }

    public void assertSanity() {
        if (n != n)
            throw new AssertionError("This statement is false.");
    }
}

n != n looks impossible — yet if a Holder is published unsafely and another thread calls assertSanity, it can throw AssertionError. Two things go wrong with improperly published objects:

  • another thread may see a stale reference — null, or an older value; and
  • worse, it may see an up-to-date reference but stale fields — a partially constructed object.

And to make it less predictable still, a thread may see a stale value on the first read and an up-to-date one on the next — which is exactly how n != n becomes possible. (The default values written by the Object constructor are themselves "stale" values you can observe.)

3.5.2Immutable objects and initialization safety

Because immutable objects matter so much, the JMM gives them a special guarantee: initialization safety. For a properly constructed immutable object — unmodifiable state, all fields final, no this escape — the object can be accessed safely by any thread even when synchronization was not used to publish it. Had Holder been immutable, assertSanity could never have thrown.

🛡️

The guarantee extends to the values of all final fields of properly constructed objects: final fields can be read safely without synchronization. But if a final field refers to a mutable object, synchronization is still required to access the state of that object.

3.5.3Safe publication idioms

To publish an object safely, the reference and the object's state must become visible together. A properly constructed object can be safely published by:

IdiomWhy it works
Initializing a reference from a static initializerClass initialization is internally synchronized by the JVM (JLS 12.4.2) — the easiest and safest option.
Storing the reference in a volatile field or AtomicReferenceThe write is ordered and immediately visible to readers.
Storing the reference in a final field of a properly constructed objectFinal-field semantics give initialization safety.
Storing the reference in a field guarded by a lockLock acquire/release provides the visibility edge (Figure 3.1).
Placing it in a thread-safe collectionThe collection's internal synchronization does the work (this is the lock-guarded case).

That last row is worth spelling out, because the Javadoc barely mentions it: the thread-safe collections offer safe publication guarantees. Putting a key or value into a Hashtable, synchronizedMap or ConcurrentMap safely publishes it to any thread that retrieves it; the same holds for Vector, CopyOnWriteArrayList, CopyOnWriteArraySet, synchronizedList/Set, and for BlockingQueue / ConcurrentLinkedQueue. Future and Exchanger are handoff mechanisms that also count as safe publication.

3.5.4Effectively immutable objects

Safe publication is enough for objects that will not be modified after publication. Objects that are not technically immutable but whose state never changes after publication are effectively immutable. They need not satisfy Section 3.4; the program merely has to treat them as immutable once published. Safely published effectively immutable objects can be used by any thread without additional synchronization.

Date is mutable, but if you never modify a Date after storing it in a synchronizedMap, the map's internal synchronization is sufficient to publish it — and no further synchronization is needed to read it.

3.5.5Mutable objects

If an object may be modified after construction, safe publication guarantees only the visibility of its as-published state. To share mutable objects safely, they must be safely published and be either thread-safe or guarded by a lock. The full rule set:

Kind of objectHow it must be publishedHow it must be accessed afterwards
ImmutableAny mechanismNo synchronization needed — initialization safety
Effectively immutableSafelyNo synchronization needed, provided it is never modified
MutableSafelyEvery access must be synchronized, or the object must be thread-safe

3.5.6Sharing objects safely

Whenever you acquire a reference to an object you should know what you are allowed to do with it: must you hold a lock? May you modify it, or only read? Many concurrency errors come from failing to understand these rules of engagement. When you publish an object, document how it may be accessed.

PolicyWhat it meansWhat you must do
Thread-confinedOwned exclusively by one thread; the owner may modify it.Never publish it; keep it off other threads.
Shared read-onlyImmutable or effectively immutable; may be read concurrently.No synchronization needed — but nobody may modify it.
Shared thread-safeSynchronizes internally; free access through its public interface.No further synchronization by clients.
GuardedAccessible only while a specific lock is held.Acquire that lock for every access — including reads.

These four policies are the vocabulary Chapter 4 builds on: every design decision there is about choosing one of them per object and documenting it.

public class VisibilityFixed {

    // 1. volatile on BOTH shared variables: writes are ordered and visible.
    //    Also fixes the 64-bit tearing problem for long/double.
    static class WithVolatile {
        private volatile boolean ready;
        private volatile int number;

        void publish() { number = 42; ready = true; }

        void await() {
            while (!ready)
                Thread.yield();
            System.out.println(number);      // always 42
        }

    // 2. One lock for the whole read-modify sequence: visibility + atomicity.
    static class WithLock {
        private boolean ready;
        private int number;

        synchronized void publish() { number = 42; ready = true; }

        synchronized int await() {
            while (!ready) {
                try { wait(); } catch (InterruptedException e) { return -1; }
            }
            return number;                    // always 42
        }
    }

        final int number;

    }
    static class WithHolder {
        private volatile Snapshot snapshot;
        void publish() { snapshot = new Snapshot(42); }

  7. If someone steals your password and posts it publicly, that information has escaped: whether or not anyone has used it yet, your account is compromised. Publishing a reference poses the same sort of risk.

Chapter 4 — Composing Objects

Chapters 2 and 3 gave us the primitives. This chapter is about not having to re-derive them for every memory access: how to design a thread-safe class, keep non-thread-safe parts confined, decide when to delegate thread safety to components, add operations without breaking a class, and — the most underused tool of all — document the policy.

📖 pp. 37–50 🧩 5 sections · 16 listings · no figures ⏱️ ~18 min read 🏷️ Part I — Fundamentals

Chapter in one paragraph

TL;DR — the six things worth remembering

  1. Design has three steps: identify the variables that form the state, identify the invariants that constrain them, and establish (and document) a policy for concurrent access.
  2. Invariants dictate atomicity and encapsulation. If some states are invalid, the fields must be private; if some transitions are invalid, the operation must be atomic; if an invariant spans several fields, one lock must cover all of them.
  3. Confinement + locking makes unsafe parts safe. A private HashSet guarded by every method of its owner is thread-safe — and the Java monitor pattern is just this idea taken to its conclusion.
  4. Delegation works only for independent state. ConcurrentHashMap, two CopyOnWriteArrayLists for mouse and key listeners — fine. Two AtomicIntegers for a range with lower <= upper — broken.
  5. Never publish state that participates in invariants. Counter's value must stay private; a temperature reading or a listener list may be published.
  6. To add an atomic operation, prefer composition. Adding to the class > extending it > client-side locking >> a helper class that locks the wrong thing.

4.1Designing a Thread-safe Class

Encapsulation is what makes thread safety analysable: a class that hides its state can be verified without reading the whole program.

You can write a thread-safe program with all its state in public static fields, but verifying it — or keeping it safe as you modify it — is far harder. The design process has three elements:

1️⃣
Identify the state

Start with the fields. If they are all primitives, they are the state — the state of a Point is its (x, y) tuple. With references, the state reaches into the referenced objects: a LinkedList's state includes every link node.

2️⃣
Identify the invariants

Which states are valid? Which state transitions are legal? An invariant that spans fields creates an atomicity requirement; an invalid state that clients could create creates an encapsulation requirement.

3️⃣
Establish the policy

The synchronization policy says what combination of immutability, confinement and locking keeps the invariants — and which variables are guarded by which locks. Write it down.

THREAD-SAFE Listing 4.1 · Simple thread-safe Counter using the Java monitor pattern 
@ThreadSafe
public final class Counter {
    @GuardedBy("this")  private long value = 0;

    public synchronized  long getValue() {
        return value;
    }
    public synchronized  long increment() {
        if (value == Long.MAX_VALUE)
            throw new IllegalStateException("counter overflow");
        return ++value;
    }
}

4.1.1Gathering synchronization requirements

Objects and variables have a state space — the range of states they can take on — and the smaller it is, the easier the class is to reason about. That is one more argument for final fields wherever practical (in the extreme, an immutable object has a single state).

Counter.value is a long, so its raw state space runs from Long.MIN_VALUE to Long.MAX_VALUE; Counter narrows that: negatives are not allowed, and if the current state is 17 the only valid next state is 18. When the next state is derived from the current state, the operation is necessarily a compound action. Not everything works that way — setting the current temperature does not depend on its previous value.

🔗

Multivariable invariants create atomicity requirements. If lower <= upper must always hold, you cannot update one, release the lock, reacquire it and update the other — you would leave the object invalid in between. The lock guarding them must be held for the whole operation.

4.1.2State-dependent operations

Some methods have state-based preconditions — you cannot take an item from an empty queue. Such operations are state-dependent. Single-threaded, a failed precondition means failure; in a concurrent program another thread may make the precondition true shortly, so you can wait for it.

wait/notify are bound tightly to intrinsic locking and are easy to get wrong; it is usually better to use existing library classes (BlockingQueue, Semaphore — Chapter 5) than to build the mechanism yourself (Chapter 14).

4.1.3State ownership

An object's state is a subset of the fields reachable from it: only the data it owns. Ownership is not in the language — it is a design decision. When you allocate and populate a HashMap, the logical state includes the Map.Entry objects and other internals, because the map owns them.

Garbage collection makes it cheap to skip this thinking (in C++ you must decide whether you are transferring, loaning or sharing ownership). Ownership and encapsulation usually go together — the owner gets to choose the locking protocol. But once you publish a reference to a mutable object you no longer have exclusive control; at best you have shared ownership. A class generally does not own the objects handed to its methods or constructors, unless ownership is explicitly transferred (as the synchronized collection wrappers do).

Collections show split ownership: the collection owns its infrastructure, the client owns the objects stored in it. ServletContext is the canonical example — the container must make the context itself thread-safe, but the attributes you put in it are yours, and must be thread-safe, effectively immutable, or explicitly guarded.

4.2Instance Confinement

If an object is not thread-safe, you can still use it safely: confine it to one thread, or guard every access with a lock.

Encapsulation promotes instance confinement: when an object is wrapped inside another, every code path that can reach it is known, so the class can be analysed without reading the whole program. Confined objects must not escape their intended scope — a class instance, a lexical scope, or a thread. Objects don't escape on their own; a developer publishes them.

THREAD-SAFE Listing 4.2 · Using confinement to ensure thread safety 
@ThreadSafe
public class PersonSet {
    @GuardedBy("this")
    private final Set<Person> mySet = new HashSet<Person>();

    public synchronized void addPerson(Person p) {
        mySet.add(p);
    }

    public synchronized boolean containsPerson(Person p) {
        return mySet.contains(p);
    }
}

HashSet is not thread-safe, but mySet is private and never escapes, so it is confined to the PersonSet; the only paths that touch it are synchronized. Result: thread-safe, with no assumptions about Person. (If Person is mutable, callers still need to synchronize when using a Person they retrieved — ideally by making Person thread-safe.)

Instance confinement is one of the easiest routes to thread safety, and it leaves the locking strategy open: PersonSet happens to use its intrinsic lock, but any consistently used lock would do, and different state variables can even be guarded by different locks. The synchronized collection wrappers are the same trick — each method is a synchronized forwarder, safe provided the wrapper holds the only reference to the underlying collection. Escape still breaks it, including escape via iterators or inner-class instances.

4.2.1The Java monitor pattern

Following instance confinement to its logical conclusion gives the Java monitor pattern: an object encapsulates all its mutable state and guards it with its own intrinsic lock. Counter (Listing 4.1) is the canonical example; Vector and Hashtable use it too. Its main advantage is simplicity; when you need finer-grained locking for scalability, Chapter 11 is the reference.

PRIVATE LOCK Listing 4.3 · Guarding state with a private lock 
public class PrivateLock {
    private final Object myLock = new Object();
    @GuardedBy("myLock") Widget widget;

    void someMethod() {
        synchronized(myLock) {
            // Access or modify the state of widget
        }
    }
}

A private lock object is often better than the intrinsic lock: because client code cannot acquire it, clients cannot participate in your synchronization policy — correctly or otherwise. A publicly accessible lock lets them in, and a client that acquires it improperly can cause liveness problems; verifying correct use then requires examining the whole program instead of one class.

4.2.2Example: tracking fleet vehicles

A vehicle tracker — identifiers, (x, y) locations — is a realistic shared data model: a view thread renders it while updater threads push GPS positions into it. Built with the monitor pattern, using the non-thread-safe MutablePoint internally, and copying everything on the way in and out:

MONITOR PATTERN Listing 4.4 · Monitor-based vehicle tracker 
@ThreadSafe
public class MonitorVehicleTracker {
    @GuardedBy("this")
    private final Map<String, MutablePoint> locations;

    public MonitorVehicleTracker(
            Map<String, MutablePoint> locations) {
        this.locations = deepCopy(locations);
    }

    public synchronized Map<String, MutablePoint> getLocations() {
        return deepCopy(locations);
    }

    public synchronized  MutablePoint getLocation(String id) {
        MutablePoint loc = locations.get(id);
        return loc == null ? null : new MutablePoint(loc);
    }

    public synchronized  void setLocation(String id, int x, int y) {
        MutablePoint loc = locations.get(id);
        if (loc == null)
            throw new IllegalArgumentException("No such ID: " + id);
        loc.x = x;
        loc.y = y;
    }

    private static Map<String, MutablePoint> deepCopy(
            Map<String, MutablePoint> m) {
        Map<String, MutablePoint> result =
                new HashMap<String, MutablePoint>();
        for (String id : m.keySet())
            result.put(id, new MutablePoint(m.get(id)));
        return Collections.unmodifiableMap(result);
    }
}
NOT THREAD-SAFE Listing 4.5 · MutablePoint — safe only because it never escapes 
@NotThreadSafe
public class MutablePoint {
    public int x, y;

    public MutablePoint() { x = 0; y = 0; }
    public MutablePoint(MutablePoint p) {
        this.x = p.x;
        this.y = p.y;
    }
}

The tracker is thread-safe even though MutablePoint is not: neither the map nor the points in it are ever published — every return value is a copy. Note that deepCopy cannot just wrap the map in unmodifiableMap (that protects the collection, not the mutable objects inside), and a copy constructor on the map would only copy references. Copying costs something, and it also means callers get a snapshot that does not change underneath them — a benefit or a drawback depending on the requirements.

4.3Delegating Thread Safety

If the components are already thread-safe, do you need to add anything? It depends — on whether the class imposes invariants of its own.

CountingFactorizer (Chapter 2) added an AtomicLong to a stateless class and stayed thread-safe: its state is the state of a thread-safe object, and it adds no validity constraints. It delegates its thread-safety responsibilities. (Note the non-final caveat: if count could be reassigned, the reference itself would need to be safely published — one more reason to make fields final.)

4.3.1Example: vehicle tracker using delegation

Return to the tracker, but store locations in a ConcurrentHashMap of immutable Points. Immutable values can be shared freely, so nothing needs copying.

IMMUTABLE Listing 4.6 · Immutable Point class 
@Immutable
public class Point {
    public final int x, y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
}
DELEGATION Listing 4.7 · Delegating thread safety to a ConcurrentHashMap 
@ThreadSafe
public class DelegatingVehicleTracker {
    private final ConcurrentMap<String, Point> locations;
    private final Map<String, Point> unmodifiableMap;

    public DelegatingVehicleTracker(Map<String, Point> points) {
        locations = new ConcurrentHashMap<String, Point>(points);
        unmodifiableMap = Collections.unmodifiableMap(locations);
    }

    public Map<String, Point> getLocations() {
        return unmodifiableMap;
    }

    public Point getLocation(String id) {
        return locations.get(id);
    }

    public void setLocation(String id, int x, int y) {
        if (locations.replace(id, new Point(x, y)) == null)
            throw new IllegalArgumentException(
                "invalid vehicle name: " + id);
    }
}

No explicit synchronization anywhere: all state access is managed by ConcurrentHashMap, and every key and value is immutable. The behavioural difference from the monitor version is real — this returns an unmodifiable but "live" view, so a thread that fetched the map sees later location changes; the monitor version returned a frozen snapshot. Neither is wrong; they answer different requirements.

SNAPSHOT Listing 4.8 · Returning a static copy instead of a live view 
public Map<String, Point> getLocations() {
    return Collections.unmodifiableMap(
            new HashMap<String, Point>(locations));
}

4.3.2Independent state variables

Delegation also works with several thread-safe state variables — as long as they are independent, i.e. the class imposes no invariant relating them.

DELEGATION Listing 4.9 · Delegating to multiple independent state variables 
public class VisualComponent {
    private final List<KeyListener> keyListeners
        = new CopyOnWriteArrayList<KeyListener>();
    private final List<MouseListener> mouseListeners
        = new CopyOnWriteArrayList<MouseListener>();

    public void addKeyListener(KeyListener listener) {
        keyListeners.add(listener);
    }

    public void addMouseListener(MouseListener listener) {
        mouseListeners.add(listener);
    }

    public void removeKeyListener(KeyListener listener) {
        keyListeners.remove(listener);
    }

    public void removeMouseListener(MouseListener listener) {
        mouseListeners.remove(listener);
    }
}

There is no relationship between the mouse listeners and the key listeners, so the class can hand its thread-safety obligations to two thread-safe lists. CopyOnWriteArrayList is particularly suited to listener lists (Section 5.2.3).

4.3.3When delegation fails

Most composites are not that simple: their state variables are related by invariants. NumberRange keeps two AtomicIntegers and the invariant lower <= upper. Both setters are check-then-act sequences without sufficient locking.

DON'T DO THIS Listing 4.10 · NumberRange — thread-safe parts, unsafe whole 
public class NumberRange {
    // INVARIANT: lower <= upper
    private final AtomicInteger lower = new AtomicInteger(0);
    private final AtomicInteger upper = new AtomicInteger(0);

    public void setLower(int i) {
        // Warning -- unsafe check-then-act
        if (i > upper.get())
            throw new IllegalArgumentException(
                    "can't set lower to " + i + " > upper");
        lower.set(i);
    }

    public void setUpper(int i) {
        // Warning -- unsafe check-then-act
        if (i < lower.get())
            throw new IllegalArgumentException(
                    "can't set upper to " + i + " < lower");
        upper.set(i);
    }

    public boolean isInRange(int i) {
        return (i >= lower.get() && i <= upper.get());
    }
}

This is the same rule as for volatile (Section 3.1.4): a variable may be volatile only if it participates in no invariant with other state. NumberRange needs a common lock over both fields, and must not publish them.

✅

Delegation is safe when the class is composed of multiple independent thread-safe state variables and has no operations with invalid state transitions. If it has compound actions, it must provide its own locking — unless the whole compound action can itself be delegated to a thread-safe component.

4.3.4Publishing underlying state variables

When may you publish delegated state? Again: it depends on the invariants. Counter.value is constrained to positive values and to n → n+1 transitions, so making it public would let clients break the class. A current-temperature field or a "last user to log on" ID has no such constraints, so publishing it would not break thread safety — though it still constrains future evolution and subclassing.

🔓

A state variable may be safely published if it is thread-safe, participates in no invariant constraining its value, and has no prohibited state transitions. That is why VisualComponent's listener lists could be made public.

4.3.5Example: a vehicle tracker that publishes its state

Third variant: publish the map's contents, but make the points mutable and thread-safe — for which we need a getter that returns both coordinates at once.

THREAD-SAFE Listing 4.11 · SafePoint — an atomic (x, y) snapshot 
@ThreadSafe
public class SafePoint {
    @GuardedBy("this") private int x, y;

    private SafePoint(int[] a) { this(a[0], a[1]); }

    public SafePoint(SafePoint p) { this(p.get()); }

    public SafePoint(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public synchronized int[] get() {
        return new int[] { x, y };
    }

    public synchronized void set(int x, int y) {
        this.x = x;
        this.y = y;
    }
}

If get were split into getX() and getY(), the coordinates could change in between and a caller would see a location the vehicle never occupied. The private array constructor exists to dodge the race in this(p.x, p.y) — the private constructor capture idiom.

PUBLISHES SAFELY Listing 4.12 · Vehicle tracker that safely publishes underlying state 
@ThreadSafe
public class PublishingVehicleTracker {
    private final Map<String, SafePoint> locations;
    private final Map<String, SafePoint> unmodifiableMap;

    public PublishingVehicleTracker(
                            Map<String, SafePoint> locations) {
        this.locations
            = new ConcurrentHashMap<String, SafePoint>(locations);
        this.unmodifiableMap
            = Collections.unmodifiableMap(this.locations);
    }

    public Map<String, SafePoint> getLocations() {
        return unmodifiableMap;
    }

    public SafePoint getLocation(String id) {
        return locations.get(id);
    }

    public void setLocation(String id, int x, int y) {
        if (!locations.containsKey(id))
            throw new IllegalArgumentException(
                "invalid vehicle name: " + id);
        locations.get(id).set(x, y);
      }
}

Callers cannot add or remove vehicles, but they can move them by mutating the SafePoints they hold. This is thread-safe precisely because the tracker imposes no constraint on the set of valid locations. If it needed to veto a move or react to one, this approach would be wrong.

"I need a thread-safe List with an atomic put-if-absent." Four ways to get it — three of them safe, ranked by fragility.

4.4.1Client-side locking

For Collections.synchronizedList(new ArrayList<E>()) neither modification nor extension is available: the client doesn't even know the class of the returned object. A helper class looks like the answer — and is a classic trap.

DON'T DO THIS Listing 4.14 · Non-thread-safe attempt at put-if-absent 
@NotThreadSafe
public class ListHelper<E> {
    public List<E> list =
        Collections.synchronizedList(new ArrayList<E>());
    ...
    public synchronized boolean putIfAbsent(E x) {
        boolean absent = !list.contains(x);
        if (absent)
            list.add(x);
        return absent;
    }
}

putIfAbsent is synchronized — on the wrong lock. The list guards its state with its own lock, not the ListHelper's, so the method is not atomic with respect to other list operations. It provides only the illusion of synchronization.

CLIENT-SIDE LOCKING Listing 4.15 · Put-if-absent with client-side locking 
@ThreadSafe
public class ListHelper<E> {
    public List<E> list =
        Collections.synchronizedList(new ArrayList<E>());
    ...
    public boolean putIfAbsent(E x) {
        synchronized (list)  {
            boolean absent = !list.contains(x);
            if (absent)
                list.add(x);
            return absent;
        }
    }
}

Client-side locking means guarding client code with the lock that the object itself uses — which requires knowing that lock. Vector and the synchronized wrappers document (obliquely) that they use the wrapper's intrinsic lock, which makes this work. But it couples unrelated classes to an implementation detail: extension violates encapsulation of implementation, client-side locking violates encapsulation of the synchronization policy.

4.4.2Composition

COMPOSITION Listing 4.16 · Put-if-absent using composition 
@ThreadSafe
public class ImprovedList<T> implements List<T> {
    private final List<T> list;

    public ImprovedList(List<T> list) { this.list = list; }

    public synchronized boolean putIfAbsent(T x) {
        boolean contains = list.contains(x);
        if (contains)
            list.add(x);
        return !contains;
    }

    public synchronized void clear() { list.clear(); }
    // ... similarly delegate other List methods
}

ImprovedList adds a layer of locking with its own intrinsic lock and does not care whether the underlying list is thread-safe — it provides consistent locking of its own, using the Java monitor pattern to encapsulate an existing List. That is guaranteed to be thread-safe so long as it holds the only outstanding reference to the underlying list. The extra synchronization is cheap because it is guaranteed uncontended (Chapter 11), and far less fragile than mimicking someone else's locking strategy.

4.5Documenting Synchronization Policies

"Document a class's thread safety guarantees for its clients; document its synchronization policy for its maintainers."

Documentation is the most powerful — and most underutilised — tool for managing thread safety. Users read it to find out whether a class is safe to share; maintainers read it to understand the strategy so they don't silently break it. Every use of synchronized, volatile or a thread-safe class reflects a synchronization policy; that policy is a design decision, and the best time to write it down is now, while you still remember it.

👥
For clients

Is the class thread-safe? Does it make callbacks with a lock held? Do specific locks affect its behaviour? If you don't support client-side locking, say so.

🔧
For maintainers

Which variables are guarded by which locks — @GuardedBy does the trick. Which are volatile, immutable or confined? Which operations must be atomic?

🚩
Worst case

Don't force clients to guess. Bad assumptions ("it's probably thread-safe", "I'll just grab its lock") give you either silent corruption or only the illusion of safety.

The state of the art is not encouraging: most classes give no clue either way, and specifications such as servlets and JDBC badly under-document their thread-safety promises. SimpleDateFormat — not thread-safe — said nothing about it until JDK 1.4, and plenty of programs share one instance under load.

4.5.1Interpreting vague documentation

When the specification is silent, you have to guess — and one good technique is to read it from the point of view of the implementer. The container creates multiple threads and calls servlets from them, so it must expect concurrent access to HttpSession and ServletContext; a single-threaded context in which they were useful is unimaginable. If client-side locking were required, on which lock? The spec doesn't say — which is absurd — and its own examples use no client-side synchronization. Conclusion: assume they are thread-safe.

The same reasoning applies to DataSource: it represents a pool of connections and would make no sense single-threaded, so assume getConnection needs no extra locking. But that reasoning does not extend to the Connection objects it hands out: they are not meant to be shared until returned to the pool, so an activity spanning several threads must guard the connection itself (in practice most confine it to one thread).

The flip side is ownership: objects you store in ServletContext or HttpSession belong to your application, not the container, and the spec offers no mechanism for coordinating access to attributes. Make them thread-safe or effectively immutable — especially in HttpSession, where the container may serialize them for replication or passivation and cannot possibly know your locking protocol.

  4. Am I delegating to components that are genuinely independent, with no compound actions left over?
  5. If a client wanted a new atomic operation, does my documentation tell them which lock to use?

  1. Thread-safe collections are safe one method at a time, not one action at a time. 5.1Synchronized Collections

A synchronized collection is thread-safe. Your program still may not be.

The synchronized collections are Vector and Hashtable — part of the original JDK — and their JDK 1.2 cousins, the wrappers produced by Collections.synchronizedXxx. They achieve thread safety the crudest way available: they encapsulate their state and synchronize every public method on a single lock, so only one thread at a time touches the collection's state.

5.1.1Problems with synchronized collections

Being thread-safe per method is not the same as being thread-safe per operation. Common compound actions on collections are iteration (fetch elements until exhausted), navigation (find the next element after this one), and conditional operations such as put-if-absent (add a mapping only if the key is absent). With a synchronized collection these are still technically thread-safe without client-side locking — nothing is corrupted — but they may not behave the way the caller expects while another thread modifies the collection.

Listing 5.1 shows two such methods on a Vector. Both are check-then-act: read size, then use the result to fetch or remove the last element.

CONFUSING RESULTS Listing 5.1 · Compound actions on a Vector that may produce confusing results 
public static Object getLast(Vector list) {
    int lastIndex = list.size() - 1;
    return list.get(lastIndex);
}

public static void deleteLast(Vector list) {
    int lastIndex = list.size() - 1;
    list.remove(lastIndex);
}

These methods seem harmless, and in a sense they are: they cannot corrupt the Vector, no matter how many threads call them simultaneously. The caller may have a different opinion. If thread A calls getLast on a Vector with ten elements while thread B calls deleteLast on the same vector, and the operations interleave as in Figure 5.1, getLast throws ArrayIndexOutOfBoundsException: between size and get the vector shrank, and the index computed in the first step is no longer valid. That is perfectly consistent with Vector's specification — it throws if asked for a nonexistent element — but it is not what a caller expects getLast to do, unless the vector was empty to begin with.

Because the synchronized collections commit to a synchronization policy that supports client-side locking, you can build new operations that are atomic with respect to the collection's own operations — as long as you know which lock to use. Each method is guarded by the lock on the collection object itself, so acquiring that lock makes getLast and deleteLast atomic and keeps the size from changing between size and get, as in Listing 5.2.

CLIENT-SIDE LOCKING Listing 5.2 · Compound actions on Vector using client-side locking 
public static Object getLast(Vector list) {
    synchronized (list) {
        int lastIndex = list.size() - 1;
        return list.get(lastIndex);
    }
}

public static void deleteLast(Vector list) {
    synchronized (list) {
        int lastIndex = list.size() - 1;
        list.remove(lastIndex);
    }
}
🔑

The lock is the collection object, not your helper class. That is exactly the property Chapter 4 warned you not to rely on in someone else's class — here it is documented, so the extension is legitimate.

The same risk exists in the plain iteration idiom of Listing 5.3, which relies on a leap of faith that nobody modifies the vector between size and get.

UNRELIABLE Listing 5.3 · Iteration that may throw ArrayIndexOutOfBoundsException 
for (int i = 0; i < vector.size(); i++)
    doSomething(vector.get(i));

In a single-threaded environment the assumption is perfectly valid; with concurrent modification it is not, and an unlucky interleaving throws ArrayIndexOutOfBoundsException. That does not mean Vector isn't thread-safe: its state is still valid and the exception conforms to its specification. It means that "fetching the last element" and "iterating" are compound actions, and compound actions need locking. Listing 5.4 does that — at a cost to scalability, because it also prevents every other thread from touching the collection for the duration.

CLIENT-SIDE LOCKING Listing 5.4 · Iteration with client-side locking 
synchronized (vector) {
    for (int i = 0; i < vector.size(); i++)
        doSomething(vector.get(i));
}

5.1.2Iterators and ConcurrentModificationException

Vector is used for clarity in the book's examples even though it is a "legacy" class. The more modern collections do not eliminate the problem of compound actions: the standard way to iterate a Collection is an Iterator, explicitly or through the for-each loop added in Java 5.0, and using an iterator does not remove the need to lock the collection during iteration if other threads can modify it. The iterators returned by the synchronized collections are not designed for concurrent modification and are fail-fast: if they detect that the collection has changed since iteration began, they throw an unchecked ConcurrentModificationException.

Fail-fast iterators are not foolproof. They are designed to catch concurrency errors on a "good-faith effort" basis, and act as early-warning indicators. They are implemented with a modification count associated with the collection: if it changes during iteration, hasNext or next throws. But the check is performed without synchronization, so there is a risk of reading a stale modification count and missing a modification altogether — a deliberate tradeoff to reduce the cost of the detection code.

⚠️

ConcurrentModificationException can arise in single-threaded code too: it happens whenever elements are removed from the collection directly rather than through Iterator.remove. Seeing it is a symptom, not a proof of a concurrency bug — but its absence proves nothing either.

Listing 5.5 iterates with the for-each syntax. Internally javac generates an Iterator and repeatedly calls hasNext and next; the way to prevent the exception is exactly as before — hold the collection lock for the whole iteration.

MAY THROW CME Listing 5.5 · Iterating a List with an Iterator 
List<Widget> widgetList
    = Collections.synchronizedList(new ArrayList<Widget>());
...
// May throw ConcurrentModificationException
for (Widget w : widgetList)
    doSomething(w);

Locking a collection during iteration is often undesirable, for several reasons. Other threads that need the collection block until the iteration finishes — which may be a long time if the collection is large or the per-element task is slow. Calling doSomething while holding the lock is also a deadlock risk (Chapter 10). And even without starvation or deadlock, holding a lock for a significant period hurts scalability: the longer a lock is held, the more likely it is to be contended (Chapter 11).

The alternative is to clone the collection and iterate the copy. The clone is thread-confined, so nobody can modify it during iteration and ConcurrentModificationException is impossible — though the collection must still be locked during the clone. Cloning has an obvious cost; whether it pays depends on the size of the collection, the work done per element, the ratio of iterations to other operations, and your responsiveness and throughput requirements.

5.1.3Hidden iterators

Locking prevents ConcurrentModificationException only if you remember to lock everywhere a shared collection might be iterated — and iterators are frequently hidden. HiddenIterator in Listing 5.6 contains no explicit iteration, yet the debug statement iterates anyway: string concatenation is compiled into StringBuilder.append(Object), which calls the collection's toString, whose standard implementation iterates the collection and calls toString on every element.

NOT THREAD-SAFE Listing 5.6 · Iteration hidden within string concatenation — don't do this 
public class HiddenIterator {
    @GuardedBy("this")
    private final Set<Integer> set = new HashSet<Integer>();

    public synchronized void add(Integer i) { set.add(i); }
    public synchronized void remove(Integer i) { set.remove(i); }

    public void addTenThings() {
        Random r = new Random();
        for (int i = 0; i < 10; i++)
            add(r.nextInt());
        System.out.println("DEBUG: added ten elements to " + set);
   }
}

addTenThings can throw ConcurrentModificationException because toString iterates the set while preparing a debugging message. The real problem is that HiddenIterator is not thread-safe: the lock should be acquired before using set in the println call — and debugging and logging code commonly neglects exactly that.

Iteration is also invoked indirectly by hashCode and equals, which are called when the collection is used as an element or key of another collection; likewise containsAll, removeAll and retainAll, and the constructors that take collections as arguments. All of these can throw ConcurrentModificationException.

The lesson: the greater the distance between the state and the synchronization that guards it, the more likely someone forgets to synchronize. Had HiddenIterator wrapped the HashSet in a synchronizedSet, encapsulating the synchronization, the error could not occur. Encapsulating synchronization makes it as easy to enforce a synchronization policy as encapsulating state makes it to preserve invariants.

5.2Concurrent Collections

Serializing every access buys safety with throughput. The concurrent collections buy both.

Java 5.0 adds concurrent collection classes that are designed from the start for access by multiple threads. ConcurrentHashMap replaces synchronized hash-based maps; CopyOnWriteArrayList replaces synchronized lists where traversal dominates; the new ConcurrentMap interface adds atomic compound actions such as put-if-absent, replace and conditional remove. Replacing synchronized collections with concurrent ones can offer dramatic scalability improvements with little risk.

Java 5.0 also adds Queue and BlockingQueue. A Queue holds elements temporarily while they await processing; operationally it does not block, and retrieval on an empty queue returns null. Implementations include ConcurrentLinkedQueue (a traditional FIFO queue) and PriorityQueue (non-concurrent, priority-ordered). LinkedList also implements Queue; the Queue classes exist because dropping List's random-access requirement admits much more efficient concurrent implementations.

BlockingQueue extends Queue with blocking insertion and retrieval: retrieval blocks on an empty queue until an element arrives, insertion blocks on a full (bounded) queue until space appears. That is the subject of §5.3. And just as ConcurrentHashMap replaces a synchronized map, Java 6 adds ConcurrentSkipListMap and ConcurrentSkipListSet as concurrent replacements for a synchronized SortedMap/SortedSet.

5.2.1ConcurrentHashMap

Synchronized collection classes hold their lock for the duration of each operation, and some operations do more work than is obvious: HashMap.get or List.contains traverse a bucket or a list calling equals on candidate objects. With a poor hash function a hash table degenerates into a linked list, and traversing it — while holding the collection-wide lock — blocks everyone.

ConcurrentHashMap is a hash-based map with an entirely different locking strategy: lock striping. Instead of synchronizing every method on one lock, it uses finer-grained locking so that arbitrarily many readers can access the map concurrently, readers can access it concurrently with writers, and a limited number of writers can modify it concurrently. The result is far higher throughput under concurrent access, with little penalty for single-threaded access.

It also offers iterators that do not throw ConcurrentModificationException, eliminating the need to lock during iteration. They are weakly consistent rather than fail-fast: they tolerate concurrent modification, traverse elements as they existed when the iterator was constructed, and may (but are not guaranteed to) reflect modifications made afterwards.

The one feature of the synchronized map implementations that ConcurrentHashMap does not offer is the ability to lock the whole map. On the whole this is a reasonable tradeoff: concurrent collections are expected to change continuously. Replacing a synchronized map with ConcurrentHashMap yields only better scalability in most cases; it is inappropriate only if you truly need exclusive access (or are relying on the map's synchronization side effects).

5.2.2Additional atomic map operations

Since a ConcurrentHashMap cannot be locked for exclusive access, you cannot use client-side locking to build new atomic operations on it, as §5.1 did for Vector. Instead the common compound operations — put-if-absent, remove-if-equal, replace-if-equal — are implemented as atomic operations and specified by the ConcurrentMap interface.

    // Insert into map only if no value is mapped from K
    V putIfAbsent(K key, V value);

    // Remove only if K is mapped to V
    boolean remove(K key, V value);

    // Replace value only if K is mapped to oldValue

}

5.2.3CopyOnWriteArrayList

CopyOnWriteArrayList is a concurrent replacement for a synchronized List that offers better concurrency in some common situations and eliminates the need to lock or copy the collection during iteration (CopyOnWriteArraySet is the Set equivalent).

The copy-on-write collections derive their thread safety from the fact that an effectively immutable object needs no further synchronization once it is properly published. They implement mutability by creating and republishing a new copy of the collection on every modification. Iterators keep a reference to the backing array that was current when iteration began; since that array never changes, they synchronize only briefly to ensure visibility of its contents. Multiple threads can therefore iterate without interfering with each other or with writers, no ConcurrentModificationException is possible, and the elements you see are exactly those present when the iterator was created.

Copying the backing array on every write is expensive, especially for a large collection, so copy-on-write is reasonable only when iteration is far more common than modification. That criterion describes many event-notification systems exactly: delivering a notification means iterating the registered listeners and calling each one, while registering or unregistering a listener is comparatively rare.

5.3Blocking Queues and the Producer–Consumer Pattern

A queue that blocks is a queue with a built-in flow-control policy.

Blocking queues provide blocking put and take, plus the timed equivalents offer and poll. If the queue is full, put blocks until space appears; if the queue is empty, take blocks until an element appears. Queues may be bounded or unbounded; an unbounded queue is never full, so put never blocks.

Blocking queues support the producer–consumer design pattern, which separates the identification of work from its execution by putting work items on a "to do" list instead of processing them on the spot. This removes code dependencies between producer and consumer classes and decouples activities that produce and consume at different or variable rates.

Producers place data on the queue as it becomes available; consumers take it when ready to act. Producers need know nothing about the number or identity of consumers — or whether they are the only producer. Consumers need not know who produced the work or where it came from. One of the most common producer–consumer designs is a thread pool coupled with a work queue, which is precisely the Executor framework of Chapters 6 and 8.

🍽️

The dish rack. One person washes and puts dishes in the rack; another takes and dries. The rack is a blocking queue: if it is empty the consumer waits, and if it fills the producer stops washing. The analogy scales to many producers (contending for the sink) and many consumers, each interacting only with the rack. The roles are relative too — drying "consumes" wet dishes and "produces" dry ones, so a third person putting dishes away makes the drier a producer and a consumer, with two queues either of which can block it.

Consumers are easy to write because take blocks. If producers are slow, consumers simply wait — fine for a server with no requests, but a sign you should adjust the producer-to-consumer ratio in something like a web crawler with effectively infinite work. If producers are consistently faster than consumers and the queue is unbounded, the queue grows without limit until the application dies of OutOfMemoryError. With a bounded queue, producers block when it fills, which gives consumers time to catch up: a blocked producer cannot generate more work.

Producer and consumer behaviour is still coupled indirectly, through the shared queue. It is tempting to assume consumers will always keep up and leave work queues unbounded, but that is a prescription for rearchitecting the system later. 5.3.1Example: desktop search

A desktop search agent that scans local drives for documents and indexes them decomposes naturally into producers and consumers. FileCrawler in Listing 5.8 is the producer: it walks a file hierarchy and puts the names of files meeting the indexing criterion on the work queue. Indexer is the consumer: it takes file names and indexes them.

Factoring crawling and indexing into separate activities yields code that is more readable and reusable than a monolithic activity doing both; each has a single task and the blocking queue handles all the flow control. There are performance benefits too: producer and consumer run concurrently, so if one is I/O-bound and the other CPU-bound, running them together beats running them sequentially; and if the two activities parallelize to different degrees, coupling them tightly would reduce parallelism to that of the less parallelizable one.

5.3.2Serial thread confinement

All the blocking queue implementations in java.util.concurrent contain enough internal synchronization to safely publish objects from a producer thread to a consumer thread. For mutable objects, that makes producer–consumer designs a way to hand off ownership: a thread-confined object is owned exclusively by one thread, but ownership can be transferred by publishing it safely where exactly one other thread will gain access, and then never touching it again. Safe publication makes the object's state visible to the new owner; the original owner's silence keeps it confined; and the new owner may then modify it freely.

Object pools exploit this, "lending" an object to a requesting thread. As long as the pool publishes pooled objects safely and clients neither publish the object nor use it after returning it, ownership moves safely from thread to thread. Other publication mechanisms work too, provided only one thread can receive the object: blocking queues make it easy, and with more work you can use ConcurrentMap's atomic remove or AtomicReference.compareAndSet.

5.3.3Deques and work stealing

Java 6 adds Deque ("deck") and BlockingDeque, extending Queue and BlockingQueue with efficient insertion and removal at both ends; implementations include ArrayDeque and LinkedBlockingDeque.

Just as blocking queues lend themselves to producer–consumer, deques lend themselves to work stealing. In a producer–consumer design there is one shared work queue; in work stealing, every consumer has its own deque. If a consumer exhausts its own deque, it steals work from the tail of someone else's. This scales better because workers do not contend for a shared queue — most of the time they touch only their own — and even when they must reach into another's deque they use the tail, where the owner (working at the head) is not.

Work stealing suits problems where consumers are also producers: doing a unit of work tends to identify more work. Processing a page in a web crawler finds new pages; graph exploration such as marking the heap during garbage collection parallelizes well this way. A worker finding new work pushes it onto the end of its own deque; when its deque is empty it looks at the end of someone else's, which keeps every worker busy.

5.4Blocking and Interruptible Methods

InterruptedException is not an annoyance to be swallowed. It is a message from the library: this call can block, and I can stop blocking early if you ask.

Threads block for many reasons: waiting for I/O, waiting to acquire a lock, waiting to wake from Thread.sleep, or waiting for another thread's computation. A blocked thread is suspended in one of the blocked states — BLOCKED, WAITING or TIMED_WAITING. What distinguishes a blocking operation from an ordinary slow one is that the blocked thread must wait for an event beyond its control before it can proceed; when that event happens, the thread returns to RUNNABLE and becomes eligible for scheduling again.

BlockingQueue.put and take throw the checked InterruptedException, as do many other library methods such as Thread.sleep. When a method declares it, it is telling you that it is a blocking method and that, if interrupted, it will make an effort to stop blocking early. Thread.interrupt sets a per-thread boolean interrupted status and can also query it.

🤝

Interruption is cooperative. One thread cannot force another to stop what it is doing. When A interrupts B, A is merely requesting that B stop at a convenient stopping point — if B feels like it. Nothing in the API demands application-level semantics, but the most sensible use of interruption is to cancel an activity; blocking methods that respond to interruption make timely cancellation possible.

If your code calls a method that throws InterruptedException, your method is a blocking method too and must have a plan. For library code there are basically two choices:

↗️
Propagate

Often the most sensible policy: don't catch it, or catch it, do brief activity-specific cleanup, and rethrow. The caller learns that the operation was interrupted, with the stack intact.

♻️
Restore

When you cannot throw it — typically inside a Runnable — catch it and call Thread.currentThread().interrupt() so code higher up the stack still sees that an interrupt was issued.

🚫
Never swallow

Catching and doing nothing deprives callers of the chance to act, because the evidence that the thread was interrupted is gone. The sole exception: you extend Thread and therefore own all the code above.

public class TaskRunnable implements Runnable {
    BlockingQueue<Task> queue;
    ...
    public void run() {
        try {
            processTask(queue.take());

        }

Cancellation and interruption in depth are Chapter 7 — the point here is only that these two policies cover the vast majority of situations, and that swallowing the exception covers none of them.

5.5Synchronizers

Blocking queues are unique among collections: they hold objects and coordinate control flow, because take and put block until the queue reaches the state you need.

A synchronizer is any object that coordinates the control flow of threads based on its state. Blocking queues are synchronizers; so are semaphores, barriers and latches. The platform library provides several; if none fits, you can build your own with the mechanisms of Chapter 14.

🧩

All synchronizers share three structural properties: they encapsulate state that determines whether arriving threads may pass or must wait; they expose methods to manipulate that state; and they offer methods to wait efficiently until the synchronizer enters the desired state. Change the state and you have described every class in this section.

5.5.1Latches

A latch delays the progress of threads until it reaches its terminal state. It is a gate: closed until the terminal state, then open for all threads, and — crucially — it never closes again. Latches are for ensuring one-time activities complete before other activities proceed:

  • A computation must not proceed until the resources it needs are initialized — a binary latch meaning "resource R is ready".
  • A service must not start until the services it depends on have started — one latch per service, waited on before startup and released after.
  • All parties in an activity (say, the players of a multi-player game) must be ready to proceed; the latch reaches its terminal state when the last one arrives.

CountDownLatch is the flexible implementation: a counter initialized to the number of events to wait for. countDown decrements it, await blocks until it reaches zero, the waiting thread is interrupted, or the wait times out.

TestHarness in Listing 5.11 uses two latches, a starting gate initialized to one and an ending gate initialized to the number of worker threads. Every worker waits on the start gate before doing anything, and counts down the end gate when finished, so the master thread can wait efficiently for the last worker rather than polling each in turn.

Why bother, rather than starting threads as they are created? Because the harness measures how long it takes to run a task n times concurrently. Started one by one, early threads get a head start and the degree of contention varies over the run as the number of active threads ramps up and down — you would be timing a moving target.

START + END GATE Listing 5.11 · Using CountDownLatch for starting and stopping threads in timing tests 
public class TestHarness {
    public long timeTasks(int nThreads, final Runnable task)
            throws InterruptedException {
        final CountDownLatch startGate = new CountDownLatch(1);
        final CountDownLatch endGate = new CountDownLatch(nThreads);

        for (int i = 0; i < nThreads; i++) {
            Thread t = new Thread() {
                public void run() {
                    try {
                        startGate.await();
                        try {
                            task.run();
                        } finally {
                            endGate.countDown();
                        }
                    } catch (InterruptedException ignored) { }
                }
            };
            t.start();
        }

        long start = System.nanoTime();
        startGate.countDown();
        endGate.await();
        long end = System.nanoTime();
        return end-start;
    }
}

5.5.2FutureTask

FutureTask also acts like a latch, and it implements Future: a result-bearing computation. The computation is a Callable — the result-bearing equivalent of Runnable — and the task is in one of three states: waiting to run, running, or completed, where completion subsumes normal completion, cancellation and exception. Once completed it stays completed forever.

Future.get returns immediately if the task is completed and otherwise blocks until it transitions, then returns the result or throws. The specification guarantees that this transfer of the result from the computing thread to the retrieving threads is a safe publication — which is why a FutureTask is a legitimate way to hand a mutable object to another thread.

Preloader in Listing 5.12 uses a FutureTask for an expensive computation whose result is needed later: start it early and the later wait is shorter. It exposes a start method rather than starting the thread in the constructor — starting a thread from a constructor or static initializer is inadvisable, since the object may not be fully constructed when the thread runs.

PRELOAD Listing 5.12 · Using FutureTask to preload data that is needed later 
public class Preloader {
    private final FutureTask<ProductInfo> future =
        new FutureTask<ProductInfo>(new Callable<ProductInfo>() {
            public ProductInfo call() throws DataLoadException {
                return loadProductInfo();
            }
        });
    private final Thread thread = new Thread(future);

    public void start() { thread.start(); }

    public ProductInfo get()
            throws DataLoadException, InterruptedException {
        try {
            return future.get();
        } catch (ExecutionException e) {
            Throwable cause = e.getCause();
            if (cause instanceof DataLoadException)
                throw (DataLoadException) cause;
            else
                throw launderThrowable(cause);
        }
    }
}

Tasks described by Callable can throw checked exceptions, unchecked exceptions or errors; whatever the task throws is wrapped in an ExecutionException and rethrown from Future.get. That complicates callers: they must deal with ExecutionException (and the unchecked CancellationException), and its cause arrives as a Throwable. The cause falls into one of three categories — a checked exception from the Callable, a RuntimeException, or an Error. Preloader tests for the known checked exceptions and rethrows them, leaving only unchecked ones for launderThrowable (Listing 5.13), which rethrows an Error, returns a RuntimeException to its caller, and otherwise throws IllegalStateException to signal a logic error.

UTILITY Listing 5.13 · Coercing an unchecked Throwable to a RuntimeException 
/** If the Throwable is an Error, throw it; if it is a
 *  RuntimeException return it, otherwise throw IllegalStateException
 */
public static RuntimeException launderThrowable(Throwable t) {
    if (t instanceof RuntimeException)
        return (RuntimeException) t;
    else if (t instanceof Error)
        throw (Error) t;
    else
        throw new IllegalStateException("Not unchecked", t);
}

5.5.3Semaphores

A counting semaphore controls the number of activities that can access a resource or perform an action at the same time. It manages a set of virtual permits, created with an initial count; activities acquire a permit before proceeding and release it when done. If none is available, acquire blocks until one is (or until interrupted or timed out). A binary semaphore — initial count one — can serve as a mutex with non-reentrant locking semantics: whoever holds the sole permit holds the mutex.

🪙

The implementation has no actual permit objects, and a Semaphore does not associate dispensed permits with threads — so a permit acquired in one thread can be released from another. Think of acquire as consuming a permit and release as creating one; a semaphore is not limited to the number of permits it was created with.

Semaphores implement resource pools such as database connection pools. A fixed-size pool that fails when empty is easy; what you want is to block when empty and unblock when nonempty. Initialize the semaphore to the pool size, acquire before fetching a resource, release after returning one, and acquire blocks until the pool is nonempty. (An easier blocking pool is a BlockingQueue holding the resources.)

Similarly a semaphore turns any collection into a blocking bounded collection, as BoundedHashSet in Listing 5.14 shows: the semaphore is initialized to the maximum size; add acquires a permit before adding and releases it again if nothing was actually added; a successful remove releases a permit, letting the next add proceed. The underlying Set knows nothing about the bound — BoundedHashSet owns that policy.

BOUNDED Listing 5.14 · Using Semaphore to bound a collection 
public class BoundedHashSet<T> {
    private final Set<T> set;
    private final Semaphore sem;

    public BoundedHashSet(int bound) {
        this.set = Collections.synchronizedSet(new HashSet<T>());
        sem = new Semaphore(bound);
    }

    public boolean add(T o) throws InterruptedException {
        sem.acquire();
        boolean wasAdded = false;
        try {
            wasAdded = set.add(o);
            return wasAdded;
        }
        finally {
            if (!wasAdded)
                sem.release();
        }
    }

    public boolean remove(Object o) {
        boolean wasRemoved = set.remove(o);
        if (wasRemoved)
            sem.release();
        return wasRemoved;
    }
}

5.5.4Barriers

Latches start a group of activities or wait for them to complete — but they are single-use: once in the terminal state, a latch cannot be reset. Barriers are similar in that they block a group of threads until some event has occurred; the key difference is that with a barrier all the threads must arrive at the barrier point in order to proceed. Latches wait for events; barriers wait for other threads. The book's analogy is the family rendezvous at the mall: everyone meet at McDonald's at 6:00, and once you're there stay there until everyone shows up.

CyclicBarrier lets a fixed number of parties rendezvous repeatedly, which suits parallel iterative algorithms that split a problem into a fixed number of independent subproblems. Threads call await at the barrier point and block until all have arrived; then all are released and the barrier resets for the next iteration. If a call times out or a waiting thread is interrupted, the barrier is broken and all outstanding await calls terminate with BrokenBarrierException. On success await returns a unique arrival index, usable to elect a leader that does something special next round. The constructor also accepts a barrier action — a Runnable run in one of the subtask threads after the barrier is passed but before the blocked threads are released.

Barriers appear in simulations, where the work for one step parallelizes but all of step k must finish before step k+1 begins — n-body particle updates, for instance. CellularAutomata in Listing 5.15 computes Conway's Life: assigning a thread per cell is impractical, so the board is partitioned into Ncpu parts, one per worker. Each step, workers compute new values for their part and wait at the barrier; the barrier action commits the new values to the model; then workers are released to compute the next step, checking hasConverged first.

BARRIER ACTION Listing 5.15 · Coordinating computation in a cellular automaton with CyclicBarrier 
public class CellularAutomata {
    private final Board mainBoard;
    private final CyclicBarrier barrier;
    private final Worker[] workers;

    public CellularAutomata(Board board) {
        this.mainBoard = board;
        int count = Runtime.getRuntime().availableProcessors();
        this.barrier = new CyclicBarrier(count,
                new Runnable() {
                    public void run() {
                        mainBoard.commitNewValues();
                    }});
        this.workers = new Worker[count];
        for (int i = 0; i < count; i++)
            workers[i] = new Worker(mainBoard.getSubBoard(count, i));
    }

    private class Worker implements Runnable {
        private final Board board;

        public Worker(Board board) { this.board = board; }
        public void run() {
            while (!board.hasConverged()) {
                for (int x = 0; x < board.getMaxX(); x++)
                    for (int y = 0; y < board.getMaxY(); y++)
                        board.setNewValue(x, y, computeValue(x, y));
                try {
                    barrier.await();
                } catch (InterruptedException ex) {
                    return;
                } catch (BrokenBarrierException ex) {
                    return;
                }
            }
        }
    }

    public void start() {
        for (int i = 0; i < workers.length; i++)
            new Thread(workers[i]).start();
        mainBoard.waitForConvergence();}
}

Another form of barrier is Exchanger, a two-party barrier at which the parties swap data. It suits asymmetric activities — one thread fills a buffer while another drains it, meeting to trade a full buffer for an empty one. When two threads exchange objects through an Exchanger, the exchange constitutes a safe publication of both objects to the other party. When to exchange is a responsiveness decision: exchanging only when the buffer is full (filler) or empty (drainer) minimizes exchanges but can delay processing when the arrival rate is unpredictable; exchanging a partially filled buffer after some elapsed time is the alternative.

5.6Building an Efficient, Scalable Result Cache

Nearly every server application caches. Like most frequently reinvented wheels, caching looks simpler than it is — and a naive cache turns a performance bottleneck into a scalability bottleneck.

public interface Computable<A, V> {

public class ExpensiveFunction
        implements Computable<String, BigInteger> {

public class Memorizer1<A, V> implements Computable<A, V> {
    @GuardedBy("this")
    private final Map<A, V> cache = new HashMap<A, V>();
    private final Computable<A, V> c;

    public Memorizer1(Computable<A, V> c) {
        this.c = c;
    }

    public synchronized V compute(A arg) throws InterruptedException {
        V result = cache.get(arg);
        if (result == null) {
            result = c.compute(arg);
            cache.put(arg, result);
        }
        return result;
    }
}

Memorizer1 caches in a HashMap, which is not thread-safe, so it takes the conservative route: synchronize the entire compute method. Thread safety, yes — but only one thread can execute compute at all. If one thread is busy on a long computation, every other thread calling compute blocks, even for values already computed. With several threads queued for uncached values, compute may take longer than it would have without memorization at all.

Memorizer2 (Listing 5.17) improves on that awful behaviour by replacing the HashMap with a ConcurrentHashMap. Since the map is thread-safe, no synchronization is needed when accessing it, and the serialization disappears.

CONCURRENT, BUT DUPLICATES Listing 5.17 · Replacing HashMap with ConcurrentHashMap 
public class Memorizer2<A, V> implements Computable<A, V> {
    private final Map<A, V> cache = new ConcurrentHashMap<A, V>();
    private final Computable<A, V> c;

    public Memorizer2(Computable<A, V> c) { this.c = c; }

    public V compute(A arg) throws InterruptedException {
        V result = cache.get(arg);
        if (result == null) {
            result = c.compute(arg);
            cache.put(arg, result);
        }
        return result;
    }
}

Better concurrency, but still defective as a cache: there is a window of vulnerability in which two threads calling compute at the same time both compute the same value. For memorization that is merely inefficient — the whole point of a cache is not to calculate the same thing twice. For a general-purpose object cache that promises once-and-only-once initialization, it is a safety problem.

The issue is that a thread starting an expensive computation does not tell anyone it is doing so, so others start the same computation. We want to represent "thread X is currently computing f(27)", so that a thread arriving later for f(27) knows the efficient route: go to X's house, wait until X is done, and ask what X got.

We have already met a class that does almost exactly this: FutureTask. It represents a computation that may or may not have completed, and get returns immediately if the result is available or blocks until it is. Memorizer3 (Listing 5.18) redefines the backing map as ConcurrentHashMap<A, Future<V>> and checks whether the calculation has been started (rather than finished): if not, it creates a FutureTask, registers it in the map and runs it; otherwise it waits for the existing computation. Whether the result is ready now or in progress is transparent to the caller.

NARROW WINDOW Listing 5.18 · Memorizing wrapper using FutureTask 
public class Memorizer3<A, V> implements Computable<A, V> {
    private final Map<A, Future<V>> cache
            = new ConcurrentHashMap<A, Future<V>>();
    private final Computable<A, V> c;

    public Memorizer3(Computable<A, V> c) { this.c = c; }

    public V compute(final A arg) throws InterruptedException {
        Future<V> f = cache.get(arg);
        if (f == null) {
            Callable<V> eval = new Callable<V>() {
                public V call() throws InterruptedException {
                    return c.compute(arg);
                }
            };
            FutureTask<V> ft = new FutureTask<V>(eval);
            f = ft;
            cache.put(arg, ft);
            ft.run(); // call to c.compute happens here
        }
        try {
            return f.get();
        } catch (ExecutionException e) {
            throw launderThrowable(e.getCause());
        }
    }
}

Almost perfect: very good concurrency (inherited from ConcurrentHashMap), efficient return of known results, patient waiting when someone else is computing. One defect remains — a small window in which two threads may compute the same value.

Memorizer3 is vulnerable because a put-if-absent compound action is performed on the backing map in a way that cannot be made atomic with locking. Memorizer (Listing 5.19) uses the atomic putIfAbsent of ConcurrentMap — the operation from Listing 5.7 — and closes the window: exactly one thread's FutureTask is installed, and only that thread runs it.

EXACTLY ONCE Listing 5.19 · Final implementation of Memorizer 
public class Memorizer<A, V> implements Computable<A, V> {
    private final ConcurrentMap<A, Future<V>> cache
        = new ConcurrentHashMap<A, Future<V>>();
    private final Computable<A, V> c;

    public Memorizer(Computable<A, V> c) { this.c = c; }

    public V compute(final A arg) throws InterruptedException {
        while (true) {
            Future<V> f = cache.get(arg);
            if (f == null) {
                Callable<V> eval = new Callable<V>() {
                    public V call() throws InterruptedException {
                        return c.compute(arg);
                    }
                };
                FutureTask<V> ft = new FutureTask<V>(eval);
                f = cache.putIfAbsent(arg, ft);
                if (f == null) { f = ft; ft.run(); }
            }
            try {
                return f.get();
            } catch (CancellationException e) {
                cache.remove(arg, f);
            } catch (ExecutionException e) {
                throw launderThrowable(e.getCause());
            }
        }
    }
}
🧹

Cache pollution. Caching a Future instead of a value means a cancelled or failed computation poisons the entry: later callers would see the same cancellation or failure. Memorizer therefore removes the Future when it detects cancellation, and you may want to do the same for a RuntimeException that might succeed on a retry. It still ignores expiration (a FutureTask subclass with a timestamp plus periodic scanning would do) and eviction (removing old entries so the cache does not grow without bound).

1Bounded producer–consumer, shut down cleanly

Listings 5.8 and 5.9 leave the consumers running forever. In practice a work queue needs a bound (§5.3, resource management), a way to stop (§5.4, interruption), and a poison pill so the consumers drain and exit.

PATTERN Bounded queue, graceful shutdown, counting work done 
public class IndexingService {
    private static final int BOUND = 1000;
    private static final File POISON = new File("");   // sentinel

    private final BlockingQueue<File> queue =
            new LinkedBlockingQueue<File>(BOUND);
    private final Indexer[] consumers;

    public IndexingService(int nConsumers) {
        consumers = new Indexer[nConsumers];
        for (int i = 0; i < nConsumers; i++) {
            consumers[i] = new Indexer(queue);
            new Thread(consumers[i], "indexer-" + i).start();
        }
    }

    /** Never blocks: sheds the file if the queue is saturated. */
    public boolean submit(File f) {
        return queue.offer(f);          // caller decides what to do on false
    }

    /** Blocks with a deadline instead of forever. */
    public boolean submit(File f, long timeout, TimeUnit unit)
            throws InterruptedException {
        return queue.offer(f, timeout, unit);
    }

    public long shutdown() throws InterruptedException {
        for (int i = 0; i < consumers.length; i++)
            queue.put(POISON);          // one pill per consumer
        long indexed = 0;
        for (int i = 0; i < consumers.length; i++)
            indexed += consumers[i].awaitCompletion();
        return indexed;
    }

    private static class Indexer implements Runnable {
        private final BlockingQueue<File> queue;
        private final CountDownLatch done = new CountDownLatch(1);
        private long count;

        Indexer(BlockingQueue<File> queue) { this.queue = queue; }

        public void run() {
            try {
                while (true) {
                    File f = queue.take();
                    if (f == POISON) return;      // drain-then-exit
                    indexFile(f);
                    count++;
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();   // Listing 5.10
            } finally {
                done.countDown();                     // Listing 5.11
            }
        }

        long awaitCompletion() throws InterruptedException {
            done.await();
            return count;
        }
    }
}

Summary of Part I — the concurrency cheat sheet

The book closes Part I with a page of rules. Condensed, they are:

  • It's the mutable state, stupid. Every concurrency bug is about coordinating access to shared mutable state — so the less of it there is, the easier correctness becomes.
  • Make fields final unless they need to be mutable.
  • Immutable objects are automatically thread-safe. They are simpler, safer, and can be shared freely without locking or defensive copying.
  • Encapsulation makes complexity manageable. Encapsulating state makes invariants preservable; encapsulating synchronization makes the policy enforcible.
  • Guard each mutable variable with a lock, and guard all variables in an invariant with the same lock.
  • Hold locks for the duration of compound actions.
  • A program that accesses a mutable variable from multiple threads without synchronization is a broken program.
  • Don't rely on clever reasoning about why you don't need to synchronize.
  • Include thread safety in the design process — or explicitly document that your class is not thread-safe.
  • Document your synchronization policy.

TL;DR — the six things worth remembering

  1. Think in tasks, not threads. A task is a unit of work with a natural boundary — usually a client request, or a page element in a GUI — and independence is what makes it parallelizable.
  2. Sequential execution is simple and wrong for servers. One blocking request stalls every pending one, and the CPU idles while the single thread waits on I/O.
  3. Thread-per-task is better, then unbounded. It buys responsiveness and parallelism, but nothing limits the thread count except the arrival rate — so heavy load turns into OutOfMemoryError.

6.1Executing Tasks in Threads

Most concurrent applications are organised around the execution of tasks — and the first design decision is where the task boundaries go.

Dividing an application's work into tasks simplifies program organisation, gives error recovery natural transaction boundaries, and provides a structure for parallelizing work. Ideally tasks are independent: work that does not depend on the state, result or side effects of other tasks. Independence is what lets tasks run in parallel when there are resources to run them on. For flexibility in scheduling and load balancing, each task should also represent a small fraction of the application's processing capacity.

Server applications need both good throughput and good responsiveness under normal load, and should degrade gracefully as they become overloaded rather than simply falling over. Good task boundaries plus a sensible execution policy (§6.2.2) are how you get there. Most servers offer a natural boundary for free: the individual client request. Web servers, mail servers, file servers, EJB containers and database servers all accept requests over network connections, and a request is usually both independent and appropriately sized — sending one mail message does not depend on the others in flight, and handling it consumes a small percentage of total capacity.

6.1.1Executing tasks sequentially

The simplest scheduling policy runs tasks one at a time in a single thread. SingleThreadWebServer processes HTTP requests arriving on port 80 sequentially; the details of request processing don't matter, only the concurrency characteristics of the policy.

SEQUENTIAL Listing 6.1 · Sequential web server 
class SingleThreadWebServer {
    public static void main(String[] args) throws IOException {
        ServerSocket socket = new ServerSocket(80);
        while (true) {
            Socket connection = socket.accept();
            handleRequest(connection);
        }
    }
}

It is simple and theoretically correct, and would perform poorly in production because it handles only one request at a time. The main thread alternates between accepting connections and processing the associated request; while it handles a request, new connections wait. That might work if handleRequest effectively returned immediately — which describes no web server in the real world.

Processing a request is a mix of computation and I/O: socket reads and writes that can block on network congestion, plus file I/O and database calls that can block too. In a single-threaded server, blocking not only delays the current request but prevents pending requests from being processed at all. One unusually slow request makes the server look unresponsive, and utilization is poor because the CPU sits idle while the single thread waits. Sequential processing rarely provides good throughput or responsiveness — the exceptions are tasks that are few and long-lived, or a server with a single client making one request at a time.

6.1.2Explicitly creating threads for tasks

A more responsive approach creates a new thread per request, as ThreadPerTaskWebServer does. The main loop still alternates between accepting and dispatching; the difference is that each request is handled in a fresh thread instead of in the main loop. Three things follow:

  • Task processing moves off the main thread, so the loop resumes waiting for the next connection quickly and new connections are accepted before earlier requests finish — better responsiveness.
  • Tasks run in parallel, so multiple requests can be serviced at once. Throughput improves on multiprocessors, and also on a single CPU when tasks block for I/O, lock acquisition or resources.
  • Task-handling code must now be thread-safe, because it can be invoked concurrently for multiple tasks.
THREAD PER TASK Listing 6.2 · Web server that starts a new thread for each request 
class ThreadPerTaskWebServer {
    public static void main(String[] args) throws IOException {
        ServerSocket socket = new ServerSocket(80);
        while (true) {
            final Socket connection = socket.accept();
            Runnable task = new Runnable() {
                    public void run() {
                        handleRequest(connection);
                    }
                };
            new Thread(task).start();
        }
    }
}

Under light to moderate load this is an improvement on sequential execution. As long as the request arrival rate does not exceed the server's capacity to handle requests, both responsiveness and throughput are better.

6.1.3Disadvantages of unbounded thread creation

For production use, the thread-per-task approach has practical drawbacks, especially when many threads are created:

🧵
Thread lifecycle overhead

Creation and teardown are not free. They cost time — adding latency to request processing — and consume processing in the JVM and the OS. For frequent, lightweight requests, a new thread per request burns significant computing resources.

💾
Resource consumption

Active threads consume memory. With more runnable threads than processors, threads sit idle; many idle threads tie up memory and pressure the garbage collector, and many threads competing for CPUs costs performance too. Once every CPU is busy, more threads do not help.

💥
Stability

There is a limit on how many threads can be created — set by JVM parameters, the requested stack size and the OS. Hit it and the likely result is OutOfMemoryError, and trying to recover from that is very risky. It is far easier to structure the program not to reach the limit.

Up to a point, more threads improve throughput; beyond it, more threads just slow the application down, and one thread too many can crash it. The way to stay out of danger is to place a bound on how many threads the application creates, and to test that even at that bound it does not run out of resources.

The problem with thread-per-task is precisely that nothing limits the number of threads except the rate at which remote users can throw HTTP requests at it. Like other concurrency hazards, this works fine during prototyping and surfaces only under heavy deployment load — so a malicious user, or enough ordinary users, can crash the server by pushing traffic past a threshold. For a server that is supposed to provide high availability and graceful degradation, that is a serious failing.

6.2The Executor Framework

Tasks are logical units of work; threads are only a mechanism for running them asynchronously. The library's primary abstraction for task execution is not Thread — it is Executor.

Both policies so far have serious limitations: the sequential approach suffers from poor responsiveness and throughput, and thread-per-task from poor resource management. Chapter 5 showed how bounded queues keep an overloaded application from running out of memory; thread pools offer the same benefit for thread management, and java.util.concurrent provides a flexible pool implementation as part of the Executor framework.

INTERFACE Listing 6.3 · Executor interface 
public interface Executor {
    void execute(Runnable command);
}

A one-method interface, but it is the basis for a flexible and powerful framework for asynchronous task execution that supports a wide variety of execution policies. It gives a standard means of decoupling task submission from task execution, describing tasks with Runnable. Implementations also provide lifecycle support and hooks for statistics, management and monitoring.

Executor is the producer–consumer pattern of §5.3 with a name: the activities that submit tasks are the producers, and the threads that execute them are the consumers. Using an Executor is usually the easiest way to implement a producer–consumer design.

6.2.1Example: web server using an Executor

TaskExecutionWebServer replaces the hard-coded thread creation with an Executor — here a fixed-size pool of 100 threads. Submission is decoupled from execution, so behaviour can be changed by substituting a different Executor implementation, without touching the task-submission code.

That distinction matters in practice: changing Executor implementations or configuration is far less invasive than changing how tasks are submitted. Executor configuration is generally a one-time event and can be exposed for deployment-time configuration, whereas task submission code tends to be strewn throughout the program and is much harder to expose.

POOL Listing 6.4 · Web server using a thread pool 
class TaskExecutionWebServer {
    private static final int NTHREADS = 100;
    private static final Executor exec
        = Executors.newFixedThreadPool(NTHREADS);
    public static void main(String[] args) throws IOException {
        ServerSocket socket = new ServerSocket(80);
        while (true) {
            final Socket connection = socket.accept();
            Runnable task = new Runnable() {
                public void run() {
                    handleRequest(connection);
                }
            };
            exec.execute(task);
        }
    }
}

It is easy to make this behave like the thread-per-task version — substitute an Executor that creates a thread per request — or like the sequential version, with an Executor that runs the task in the calling thread before execute returns.

    };
}

6.2.2Execution policies

The value of decoupling submission from execution is that it lets you specify — and later change without much trouble — the execution policy for a class of tasks. A policy specifies the what, where, when and how of task execution:

Question the policy answersTypical answers
In what thread will tasks run?The caller's thread, one new thread per task, a pool thread, a GUI event thread
In what order should tasks run?FIFO, LIFO, priority order
How many tasks may execute concurrently?One, a fixed number, one per CPU, unbounded
How many tasks may be queued pending execution?Unbounded, bounded with a rejection policy, none (synchronous handoff)
If a task must be rejected, which task is the victim — and how is the application told?Newest, oldest, throw RejectedExecutionException, run in the caller's thread, discard silently
What actions should be taken before or after executing a task?Logging, timing, statistics, thread-local setup, transaction demarcation

Execution policies are a resource-management tool, and the right one depends on available computing resources and quality-of-service requirements. Limiting concurrency keeps the application from failing through resource exhaustion or degrading through contention for scarce resources — much as a transaction monitor throttles transaction rates in an enterprise application. Separating the policy from submission also makes it practical to pick a policy at deployment time that matches the hardware.

🔁

Whenever you see new Thread(runnable).start() and think you might someday want a more flexible execution policy, seriously consider replacing it with an Executor.

6.2.3Thread pools

A thread pool manages a homogeneous set of worker threads, tightly bound to a work queue holding tasks awaiting execution. Workers have a simple life: take the next task from the queue, run it, go back to waiting. Compared with thread-per-task, reusing a thread amortizes creation and teardown across many requests; because the worker often already exists when a request arrives, creation latency is off the critical path; and a properly tuned pool keeps processors busy without so many threads that the application runs out of memory or thrashes.

FactoryBehaviourBound
newFixedThreadPool(n)Creates threads as tasks are submitted up to n, then holds the pool size constant (replacing a thread that dies from an unexpected exception)Threads: yes. Queue: unbounded
newCachedThreadPool()Reaps idle threads when demand drops, adds threads when demand grows, reuses idle threads for new tasksNone — unbounded
newSingleThreadExecutor()One worker, replaced if it dies; tasks are processed sequentially in queue orderThreads: one. Queue: unbounded
newScheduledThreadPool(n)Fixed-size pool with delayed and periodic execution — the Timer replacementThreads: yes

newFixedThreadPool and newCachedThreadPool return general-purpose ThreadPoolExecutor instances, which can also be constructed directly for more specialised policies (Chapter 8).

Switching TaskExecutionWebServer from thread-per-task to a pool has a big effect on stability: the server no longer fails under heavy load, and degrades more gracefully because it does not create thousands of threads competing for limited CPU and memory. Using an Executor also opens the door to tuning, management, monitoring, logging and error reporting that would have been far harder to bolt on afterwards.

⚠️

A bounded pool fixes the thread explosion, not the queue explosion. If the task arrival rate exceeds the service rate for long enough, an unbounded work queue still grows until memory runs out — just more slowly. Bound the queue too (§8.3.2) and choose a rejection policy deliberately.

6.2.4Executor lifecycle

An Executor is likely to create threads, and the JVM cannot exit until all non-daemon threads have terminated — so failing to shut an Executor down can prevent the JVM from exiting. And because execution is asynchronous, the state of previously submitted tasks is not immediately obvious: some completed, some running, some queued. Shutdown spans a spectrum from graceful (finish what you started, accept nothing new) to abrupt, so an execution service needs to expose that spectrum and report what happened.

ExecutorService extends Executor with lifecycle management and convenience submission methods.

LIFECYCLE Listing 6.7 · Lifecycle methods in ExecutorService 
public interface ExecutorService extends Executor {
    void shutdown();
    List<Runnable> shutdownNow();
    boolean isShutdown();
    boolean isTerminated();
    boolean awaitTermination(long timeout, TimeUnit unit)
        throws InterruptedException;
    //  ... additional convenience methods for task submission
}

The lifecycle has three states: running, shutting down and terminated. Every ExecutorService starts running. shutdown() is the graceful path — no new tasks are accepted, but previously submitted tasks, including those not yet started, are allowed to complete. shutdownNow() is the abrupt path — it attempts to cancel outstanding tasks and starts none of the queued ones.

Tasks submitted after shutdown are handled by the rejected execution handler (§8.3.3), which may silently discard the task or make execute throw the unchecked RejectedExecutionException. Once all tasks have completed, the service transitions to terminated; you can wait for that with awaitTermination or poll isTerminated. It is common to follow shutdown immediately with awaitTermination, which creates the effect of a synchronous shutdown.

GRACEFUL STOP Listing 6.8 · Web server with shutdown support 
class LifecycleWebServer {
    private final ExecutorService exec = ...;
    public void start() throws IOException {
        ServerSocket socket = new ServerSocket(80);
        while (!exec.isShutdown()) {
            try {
                final Socket conn = socket.accept();
                exec.execute(new Runnable() {
                    public void run() { handleRequest(conn); }
                });
            } catch (RejectedExecutionException e) {
                if (!exec.isShutdown())
                    log("task submission rejected", e);
            }
        }
    }
    public void stop() { exec.shutdown(); }
    void handleRequest(Socket connection) {
        Request req = readRequest(connection);
        if (isShutdownRequest(req))
            stop();
        else
            dispatchRequest(req);
    }
}

6.2.5Delayed and periodic tasks

Timer handles deferred ("run this in 100 ms") and periodic ("run this every 10 ms") tasks, but it has drawbacks and ScheduledThreadPoolExecutor should be thought of as its replacement. Construct it directly or via newScheduledThreadPool.

A Timer creates only one thread for all timer tasks, so one slow task damages the accuracy of the rest: if a recurring task runs every 10 ms and another task takes 40 ms, the recurring task either fires four times in rapid succession afterwards (fixed-rate) or misses four invocations entirely (fixed-delay). A scheduled thread pool removes that limitation by allowing several threads.

Worse, Timer behaves badly when a task throws an unchecked exception. The timer thread does not catch it, so the exception terminates the thread — and Timer does not resurrect it, assuming instead that the whole Timer was cancelled. Already-scheduled tasks never run and new ones cannot be scheduled. This is thread leakage (§7.3). OutOfTime demonstrates the confusion, which it then shares with the next caller: you might expect six seconds and a clean exit, but the program terminates after one second with IllegalStateException: Timer already cancelled.

BROKEN TIMER Listing 6.9 · Class illustrating confusing Timer behavior 
public class OutOfTime {
    public static void main(String[] args) throws Exception {
        Timer timer = new Timer();
        timer.schedule(new ThrowTask(), 1);
        SECONDS.sleep(1);
        timer.schedule(new ThrowTask(), 1);
        SECONDS.sleep(5);
    }
    static class ThrowTask extends TimerTask {
        public void run() { throw new RuntimeException(); }
    }
}

ScheduledThreadPoolExecutor deals properly with ill-behaved tasks; there is little reason to use Timer in Java 5.0 or later. If you need to build your own scheduling service you can still lean on the library through DelayQueue, a BlockingQueue that hands out an element only once its delay has expired, ordering elements by the time associated with that delay.

6.3Finding Exploitable Parallelism

In a server the task boundary is the request. In a desktop application — or inside a single server request — somebody has to go looking for it.

The Executor framework makes an execution policy easy to specify, but to use it you must be able to describe your work as a Runnable. Sometimes good task boundaries are not obvious: desktop applications, and server requests that contain exploitable parallelism of their own (database servers, for instance). The chapter's running example is the page-rendering portion of a browser: take a page of HTML and render it into an image buffer, where the HTML is marked-up text interspersed with image elements of known size and URL.

6.3.1Example: sequential page renderer

The simplest approach processes the document sequentially: render text markup as it is encountered, fetch and draw images as their references are encountered. It touches each element once — it doesn't even need to buffer the document — but it makes the user wait for all the text until the images are done.

A less annoying but still sequential approach renders the text first, leaving rectangular placeholders for the images, then goes back to download and draw them into the placeholders. That is SingleThreadRenderer. Downloading an image is mostly waiting for I/O, during which the CPU does almost nothing — so this underutilizes the CPU and makes the user wait longer than necessary.

SEQUENTIAL Listing 6.10 · Rendering page elements sequentially 
public class SingleThreadRenderer {
    void renderPage(CharSequence source) {
        renderText(source);
        List<ImageData> imageData = new ArrayList<ImageData>();
        for (ImageInfo imageInfo : scanForImageInfo(source))
            imageData.add(imageInfo.downloadImage());
        for (ImageData data : imageData)
            renderImage(data);
    }
}

6.3.2Result-bearing tasks: Callable and Future

Runnable is a limiting abstraction: run cannot return a value or throw checked exceptions, though it can have side effects. Many tasks are effectively deferred computations — a database query, a fetch over the network, a complicated function — and for those Callable is the better abstraction: its entry point call returns a value and may throw. Executors includes utilities for wrapping other task types, including Runnable and java.security.PrivilegedAction, as a Callable.

Tasks are usually finite, with a clear start and an eventual end. A task executed by an Executor has four lifecycle phases: created, submitted, started, completed. Because tasks can run for a long time we also want to cancel them: a task submitted but not started can always be cancelled, a started task can sometimes be cancelled if it is responsive to interruption, and cancelling a completed task has no effect.

INTERFACES Listing 6.11 · Callable and Future interfaces 
public interface Callable<V> {
    V call() throws Exception;
}

public interface Future<V> {
    boolean cancel(boolean mayInterruptIfRunning);
    boolean isCancelled();
    boolean isDone();
    V get() throws InterruptedException, ExecutionException,
                   CancellationException;
    V get(long timeout, TimeUnit unit)
        throws InterruptedException, ExecutionException,
               CancellationException, TimeoutException;
}

Future represents that lifecycle: it tests whether the task completed or was cancelled, retrieves the result, and cancels. Implicitly, a task lifecycle can only move forwards — like the ExecutorService lifecycle, once completed it stays completed forever. The behaviour of get depends on the state: it returns immediately or throws if the task has completed, and otherwise blocks. If the task completed by throwing, get rethrows it wrapped in ExecutionException; if it was cancelled, get throws CancellationException; the underlying exception is available from getCause.

There are several ways to get a Future. The submit methods of ExecutorService all return one, for either a Runnable or a Callable; you can also instantiate a FutureTask directly, and because it implements Runnable it can be submitted to an executor or simply run. As of Java 6, ExecutorService implementations can override newTaskFor to control how the Future for a submitted task is created; the default just builds a FutureTask.

HOOK Listing 6.12 · Default implementation of newTaskFor in ThreadPoolExecutor 
protected <T> RunnableFuture<T> newTaskFor(Callable<T> task) {
    return new FutureTask<T>(task);
}

Two safe-publication guarantees come free here, and they are what make this style thread-safe: submitting a Runnable or Callable to an Executor safely publishes it from the submitting thread to the executing thread (§3.5), and setting the result of a Future safely publishes that result from the computing thread to any thread that retrieves it with get.

6.3.3Example: page renderer with Future

As a first step towards concurrency, divide the renderer into two tasks: one renders the text, one downloads all the images. Because one is largely CPU-bound and the other I/O-bound, this can help even on a single CPU. FutureRenderer creates a Callable to download the images and submits it; when the main task reaches the point where it needs them, it calls Future.get. With luck the results are ready by then; if not, at least the download got a head start.

Because get is state-dependent, the caller need not know the task's state, and the safe-publication properties just described make the approach thread-safe. The exception handling covers the two things that can go wrong: the task threw, or the thread calling get was interrupted before the result was available.

TWO TASKS Listing 6.13 · Waiting for image download with Future 
public class FutureRenderer {
    private final ExecutorService executor = ...;
    void renderPage(CharSequence source) {
        final List<ImageInfo> imageInfos = scanForImageInfo(source);
        Callable<List<ImageData>> task =
                new Callable<List<ImageData>>() {
                    public List<ImageData> call() {
                        List<ImageData> result
                                = new ArrayList<ImageData>();
                        for (ImageInfo imageInfo : imageInfos)
                            result.add(imageInfo.downloadImage());
                        return result;
                    }
                };
        Future<List<ImageData>> future =  executor.submit(task);
        renderText(source);
        try {
            List<ImageData> imageData =  future.get();
            for (ImageData data : imageData)
                renderImage(data);
        } catch (InterruptedException e) {
            // Re-assert the thread's interrupted status
            Thread.currentThread().interrupt();
            // We don't need the result, so cancel the task too
            future.cancel(true);
        } catch (ExecutionException e) {
            throw launderThrowable(e.getCause());
        }
    }
}

FutureRenderer renders text while the images download, then draws them all when they arrive. The user sees something sooner and some parallelism is exploited — but we can do better. There is no reason for users to wait for all the images; they would rather see each one as it becomes available.

6.3.4Limitations of parallelizing heterogeneous tasks

Two people can divide the dinner dishes effectively — one washes, one dries — but assigning a different type of task to each worker does not scale. If several more people show up, it is not obvious how they can help without getting in the way or forcing a restructuring of the division of labour. Without finding finer-grained parallelism among similar tasks, this approach yields diminishing returns.

A second problem is disparate sizes. Divide A and B between two workers and let A take ten times as long as B: you have sped up the total process by 9%, not by two. And splitting work across workers always costs coordination overhead, which has to be more than repaid by the parallelism.

Concretely: if rendering text is much faster than downloading images — entirely possible — FutureRenderer performs about as well as the sequential version while being a lot more complicated. And with two threads the very best case is a factor of two. The real performance payoff of dividing work into tasks comes when there are a large number of independent, homogeneous tasks that can be processed concurrently.

6.3.5CompletionService: Executor meets BlockingQueue

To submit a batch of computations and retrieve results as they become available, you could keep the Future for each task and poll it with a zero timeout get — possible, but tedious. A completion service does it properly: it combines an Executor with a BlockingQueue. You submit Callable tasks and use queue-like take and poll to retrieve completed results, packaged as Futures, in completion order. ExecutorCompletionService implements it, delegating the computation to an Executor.

The implementation is straightforward. The constructor creates a BlockingQueue to hold completed results. FutureTask has a done method called when the computation completes; each submitted task is wrapped in a QueueingFuture, a FutureTask subclass that overrides done to put the result on the queue. take and poll delegate to the queue, blocking when no result is available yet.

MECHANISM Listing 6.14 · QueueingFuture class used by ExecutorCompletionService 
private class QueueingFuture<V> extends FutureTask<V> {
    QueueingFuture(Callable<V> c) { super(c); }
    QueueingFuture(Runnable t, V r) { super(t, r); }
    protected void done() {
        completionQueue.add(this);
    }
}

6.3.6Example: page renderer with CompletionService

A CompletionService improves the renderer in two ways: shorter total runtime and better responsiveness. Make a separate task per image and run them in a pool, turning sequential downloading into parallel downloading, and render each image the moment its result is taken from the service. The user gets a more dynamic interface.

STREAMING RESULTS Listing 6.15 · Using CompletionService to render page elements as they become available 
public class Renderer {
    private final ExecutorService executor;
    Renderer(ExecutorService executor) { this.executor = executor; }
    void renderPage(CharSequence source) {
        final List<ImageInfo> info = scanForImageInfo(source);
        CompletionService<ImageData> completionService =
            new ExecutorCompletionService<ImageData>(executor);
        for (final ImageInfo imageInfo : info)
            completionService.submit(new Callable<ImageData>() {
                 public ImageData call() {
                     return imageInfo.downloadImage();
                 }
            });
        renderText(source);
        try {
            for (int t = 0, n =  info.size(); t < n;  t++) {
                Future<ImageData> f = completionService.take();
                ImageData imageData = f.get();
                renderImage(imageData);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } catch (ExecutionException e) {
            throw launderThrowable(e.getCause());
        }
    }
}

Multiple ExecutorCompletionServices can share one Executor, so it is perfectly sensible to create one privately for a particular computation over a common pool. Used that way, a CompletionService is a handle for a batch of computations, much as a Future is a handle for a single one. Remember how many tasks you submitted and count the results retrieved, and you know when the batch is complete — even on a shared executor.

6.3.7Placing time limits on tasks

Sometimes a result is worthless if it arrives late. A web application might fetch an advertisement from an external server but show a default ad if it is not available within two seconds; a portal might fetch data from several sources in parallel and be willing to wait only so long before rendering the page without it.

The primary challenge is not waiting longer than the budget to get an answer or to learn that none is coming. The timed Future.get supports exactly that: it returns as soon as the result is ready and throws TimeoutException otherwise.

A secondary problem is stopping a task that has run out of time, so it does not keep burning cycles on a result nobody will use. Either the task manages its own budget and aborts, or the caller cancels it when the timeout expires — Future again: a timed get that throws TimeoutException can be followed by cancel, and if the task is written to be cancellable (Chapter 7) it can be terminated early.

TIME BUDGET Listing 6.16 · Fetching an advertisement with a time budget 
Page renderPageWithAd() throws InterruptedException {
    long endNanos = System.nanoTime() + TIME_BUDGET;
    Future<Ad> f = exec.submit(new FetchAdTask());
    // Render the page while waiting for the ad
    Page page = renderPageBody();
    Ad ad;
    try {
        // Only wait for the remaining time budget
        long timeLeft = endNanos - System.nanoTime();
        ad = f.get(timeLeft, NANOSECONDS);
    } catch (ExecutionException e) {
        ad = DEFAULT_AD;
    } catch (TimeoutException e) {
        ad = DEFAULT_AD;
        f.cancel(true);
    }
    page.setAd(ad);
    return page;
}

6.3.8Example: a travel reservations portal

The time-budget approach generalizes to any number of tasks. A travel portal takes dates and requirements and fetches bids from airlines, hotels and car rental companies — by web service, database query, EDI transaction or something else. Rather than letting the slowest provider set the page's response time, show only what arrives inside a budget, and either omit the rest or display a placeholder ("Did not hear from Air Java in time").

Bids are independent of one another, so one bid is a sensible task boundary. You could submit n tasks, retain the futures and do a timed get on each in turn — but there is an easier way: invokeAll. It takes a collection of tasks and returns a collection of futures with identical structure, adding them in the order imposed by the task collection's iterator, so a future can be associated with the callable it represents. The timed version returns when all tasks complete, the calling thread is interrupted, or the timeout expires — and any task not complete at that point is cancelled. On return, each task has either completed normally or been cancelled, and the client can call get or isCancelled to tell which.

1An execution policy in one place, with a real lifecycle

Listing 6.8 stops the server but never waits for the tasks in flight. A service that is actually shut down cleanly needs: one place where the policy is defined, submission that cannot outlive shutdown, a graceful stop followed by a bounded wait, and an abrupt fallback.

PATTERN Execution policy as configuration, with graceful and abrupt shutdown 
public class TaskService {
    /** The execution policy, in exactly one place. */
    private final ExecutorService exec;
    private final AtomicBoolean closed = new AtomicBoolean();

    public TaskService(int poolSize) {
        this.exec = new ThreadPoolExecutor(
                poolSize, poolSize,               // fixed size
                0L, TimeUnit.MILLISECONDS,
                new LinkedBlockingQueue<Runnable>(1000),  // bounded backlog
                new ThreadFactory() {             // name the threads
                    private final AtomicInteger n = new AtomicInteger();
                    public Thread newThread(Runnable r) {
                        return new Thread(r, "task-" + n.incrementAndGet());
                    }
                },
                new ThreadPoolExecutor.AbortPolicy());     // loud rejection
    }

    /** Submission cannot outlive shutdown. */
    public Future<?> submit(Callable<?> task) {
        if (closed.get())
            throw new RejectedExecutionException("service is shutting down");
        return exec.submit(task);
    }

    /** Graceful: stop accepting, let the backlog drain, but don't wait forever. */
    public boolean shutdown(long timeout, TimeUnit unit)
            throws InterruptedException {
        closed.set(true);
        exec.shutdown();                       // no new tasks accepted
        if (!exec.awaitTermination(timeout, unit)) {
            exec.shutdownNow();                // escalate to abrupt
            return exec.awaitTermination(5, TimeUnit.SECONDS);
        }
        return true;
    }

    /** Abrupt: cancel what is running, drop what is queued, report the dropped tasks. */
    public List<Runnable> shutdownNow() {
        closed.set(true);
        return exec.shutdownNow();
    }
}

Chapter 7 — Cancellation and Shutdown

Starting tasks is easy; stopping them safely is not. Java has no preemptive way to stop a thread — only interruption, a cooperative request that a task may honour at its next cancellation point. This chapter is about the protocols that make that work: cancellation policies, interruption policies, shutting down services that own threads, recovering from abnormal thread death, and the JVM's own orderly shutdown.

📖 pp. 85–104 🧩 4 sections · 26 listings · no figures ⏱️ ~26 min read 🏷️ Part II — Structuring Concurrent Applications

Chapter in one paragraph

TL;DR — the six things worth remembering

  1. Cancellation is cooperative, by design. Nothing may stop a task mid-flight and leave shared state inconsistent — so the task itself must agree to stop, and to clean up. Every cancellable task needs a cancellation policy: how to ask, when it checks, what it does.
  2. A boolean flag fails the moment anything blocks. BrokenPrimeProducer sets cancelled while blocked in put — the task never returns to check it, so it never dies.
  3. Interruption is the mechanism. interrupt sets a per-thread status; blocking methods clear it and throw InterruptedException; non-blocking code must poll it. It is "sticky" until someone clears it.
  4. Two responses are legitimate: propagate or restore. Swallowing is only allowed in code that owns the thread's interruption policy — that is, when you are about to terminate.
  5. Never interrupt a thread you don't own. Threads are owned by whoever created them, and a pool thread's interrupt means "cancel the current task" and/or "shut down the worker". Cancel tasks through their Future, not through the thread.
  6. Services need lifecycle methods. Graceful (shutdown) or abrupt (shutdownNow), poison pills for producer–consumer, tracking executors to recover interrupted work, uncaught exception handlers so a dead thread is never silent, and shutdown hooks — but not daemon threads and not finalizers — for the JVM itself.

7.1Task Cancellation

An activity is cancellable if external code can move it to completion before its normal completion. Doing that safely is the whole problem.

Why cancel at all?

  • User request — a "cancel" button in a GUI, or a management request through JMX.
  • Time-limited activities — search the problem space for ten minutes, then stop and take the best answer found.
  • Application events — one task finds a solution, so every other task still searching is cancelled.
  • Errors — a web crawler hits a full disk, so the other crawler tasks stop and record their state for a restart.
  • Shutdown — some decision has to be made about in-flight and queued work.

Java provides no safe mechanism for preemptively stopping a thread, and therefore none for stopping a task. The deprecated Thread.stop and suspend were attempts at one and were quickly recognised as seriously flawed. The cooperative approach is not a limitation to work around but a requirement: we rarely want a task to stop immediately, since that could leave shared data in an inconsistent state. The task code is usually better placed to assess what cleanup is needed than the code requesting cancellation.

The simplest cooperative mechanism is a "cancellation requested" flag that the task polls. PrimeGenerator enumerates primes until cancelled: cancel sets the flag and the run loop polls it before searching for the next prime. For this to work reliably the flag must be volatile, or the loop may never see the write.

VOLATILE FLAG Listing 7.1 · Using a volatile field to hold cancellation state

The generator will not necessarily stop after exactly one second — there is a delay between the request and the next check of the flag. cancel is called from a finally block so the generator is cancelled even if sleep is interrupted; if it were not called, the prime-seeking thread would run forever, burning CPU and preventing the JVM from exiting.

That is PrimeGenerator's cancellation policy in full: clients request cancellation by calling cancel; the task checks once per prime; it exits when it observes the request. A real cancellation policy specifies the "how, when and what" — how other code requests cancellation, when the task checks, and what it does in response. The book's analogy is stopping payment on a cheque: banks have rules about how to submit the request, what responsiveness they guarantee, and what procedures follow once payment is actually stopped.

7.1.1Interruption

The flag eventually works — unless the task is blocked. BrokenPrimeProducer generates primes onto a blocking queue. If the producer gets ahead of the consumer the queue fills and put blocks. Now the consumer cancels: cancel sets cancelled, but the producer will never check it, because it will never return from put — the consumer has stopped taking primes, so the queue never drains. The task is stuck forever.

The library's answer is interruption: a cooperative mechanism by which one thread signals another that it should, at its convenience and if it feels like it, stop what it is doing. Nothing in the API ties interruption to cancellation semantics, but in practice using it for anything else is fragile and hard to sustain.

API Listing 7.4 · Interruption methods in Thread 
public class Thread {
    public void interrupt() { ... }
    public boolean isInterrupted() { ... }
    public static boolean interrupted() { ... }
    ...
}

Each thread has a boolean interrupted status. interrupt sets it; isInterrupted reads the target's status; the poorly named static interrupted clears the current thread's status and returns its previous value — the only way to clear it. Blocking methods like Thread.sleep and Object.wait detect interruption and return early: they respond by clearing the status and throwing InterruptedException. The JVM guarantees no particular speed of detection, but in practice it is prompt.

If a thread is interrupted while not blocked, its status is simply set and it is up to the activity to poll it. Interruption is therefore "sticky": when it does not trigger an exception, the evidence persists until someone deliberately clears it. Calling interrupt does not stop the target; it delivers the message. A good way to think about it: interruption does not interrupt a running thread, it asks the thread to interrupt itself at the next convenient opportunity — a cancellation point. Methods like wait, sleep and join take such requests seriously. Well-behaved methods may ignore them, provided they leave the request in place; poorly behaved methods swallow it.

⚠️

Use the static interrupted with care, because it clears the status. If it returns true and you are not deliberately swallowing the interruption, do something with it — throw InterruptedException or restore the status by calling interrupt again.

BrokenPrimeProducer is fixed, and simplified, by using interruption instead of a flag: cancel() just calls interrupt(). There are two points per iteration where interruption is detected — inside the blocking put, and at the explicit status check in the loop header. The explicit test is not strictly necessary here, but it makes the producer more responsive: it checks before starting the lengthy search for a prime rather than after.

7.1.2Interruption policies

Just as tasks need a cancellation policy, threads need an interruption policy: how a thread interprets an interruption request — what it does when one is detected, which units of work are atomic with respect to interruption, and how quickly it reacts. The sensible default is thread- or service-level cancellation: exit as quickly as practical, clean up if necessary, and possibly notify an owning entity. Pausing and resuming a service is possible, but threads with nonstandard policies may have to be restricted to tasks written with that policy in mind.

🔑

Tasks do not own their threads — they borrow them. A single interrupt request may have more than one intended recipient: interrupting a pool thread can mean both "cancel the current task" and "shut down this worker". Code that does not own the thread should preserve the interrupted status so the owner can act on it, even if the guest code acts on it too. As the book puts it: house-sitting for someone, you don't throw out their mail — you save it and let them deal with it. This is exactly why most blocking library methods throw InterruptedException instead of swallowing it.

A task need not drop everything the instant it notices an interruption: it can postpone, remembering that it was interrupted, finish the unit of work it was performing, and then throw or otherwise indicate interruption — which protects data structures from corruption when an activity is interrupted mid-update. Either way, a task should assume nothing about its executing thread's policy, and should restore the status after catching:

Thread.currentThread().interrupt();

Symmetrically, cancellation code should not assume anything about an arbitrary thread's policy. A thread should be interrupted only by its owner — the class that created it — which then encapsulates the policy behind a proper cancellation mechanism such as a shutdown method.

7.1.3Responding to interruption

When you call an interruptible blocking method there are two practical strategies, as §5.4 introduced: propagate the exception (possibly after task-specific cleanup), making your method interruptible too; or restore the status so code higher up the stack can act.

If you cannot propagate — typically because your task is defined by a Runnable — restore the status by calling interrupt again. What you should not do is swallow it. PrimeProducer does swallow the interrupt, but with the specific knowledge that the thread is about to terminate and nothing higher on the stack will need to know. Most code does not know which thread it will run in, so it must preserve the status. Only code that implements a thread's interruption policy may swallow an interruption request.

Activities that do not support cancellation but still call interruptible methods must call them in a loop, retrying on interruption, and should save the status locally and restore it just before returning — not immediately on catching. Setting it too early risks an infinite loop, because most interruptible methods check the status on entry and throw straight away.

NON-CANCELABLE, STILL POLITE Listing 7.7 · Non-cancelable task that restores interruption before exit 
public Task getNextTask(BlockingQueue<Task> queue) {
    boolean interrupted = false;
    try {
        while (true) {
            try {
                return queue.take();
            } catch (InterruptedException e) {
                interrupted = true;
                // fall through and retry
            }
        }
    } finally {
        if (interrupted)
            Thread.currentThread().interrupt();
    }
}

Code that calls no interruptible blocking methods can still be responsive by polling Thread.currentThread().isInterrupted() throughout. Choosing the polling frequency trades efficiency against responsiveness; demanding high responsiveness rules out calling long-running methods that are not themselves responsive. Cancellation can also involve state other than the status: the interrupting thread can leave instructions elsewhere for the interrupted thread to read — with synchronization, naturally.

7.1.4Example: timed run

"Spend up to ten minutes looking for the answer" is a useful thing to be able to say. aSecondOfPrimes (§7.1) interrupts the generator after a second, but leaves a gap: if the task throws an unchecked exception first, nobody notices, because it ran in a separate thread that does not handle exceptions.

One appealing-but-wrong attempt runs the task in the calling thread and schedules another task to interrupt it after the timeout. That fixes exception handling, and quietly violates the rule that you must know a thread's interruption policy before interrupting it. timedRun can be called from any thread, so it cannot know; and if the task finishes early, the scheduled interrupt fires after timedRun has returned and the caller has moved on to who-knows-what.

BORROWED THREAD — DON'T DO THIS Listing 7.8 · Scheduling an interrupt on a borrowed thread 
private static final ScheduledExecutorService cancelExec = ...;
public static void timedRun(Runnable r,
                           long timeout, TimeUnit unit) {
    final Thread taskThread = Thread.currentThread();
    cancelExec.schedule(new Runnable() {
        public void run() { taskThread.interrupt(); }

    r.run();
}

Worse, if the task is not responsive to interruption, timedRun does not return until the task finishes — which may be long after the timeout, or never.

The next attempt runs the task in a dedicated thread with its own execution policy, and does a timed join, so timedRun returns even if the task ignores the interrupt. It captures a thrown exception in a volatile field — shared between threads, so the null check and the write must be safely published — and rethrows it in the caller's thread. It still inherits join's deficiency: you cannot tell whether control returned because the thread exited or because the join timed out.

7.1.5Cancellation via Future

Better to use the library than roll your own: Future already manages task lifecycle, deals with exceptions and facilitates cancellation. Future.cancel(mayInterruptIfRunning) returns whether the cancellation attempt succeeded — which tells you only that the interrupt was delivered, not that the task detected and acted on it. When the flag is true and the task is running, its thread is interrupted; passing false means "don't run this task if it hasn't started yet", which is the right choice for tasks that are not designed for interruption.

When is it safe to pass true? Threads created by the standard Executor implementations implement an interruption policy that lets tasks be cancelled through interruption, so cancelling a task through its Future is fine. Interrupting a pool thread directly is not, because you don't know which task is running when the request lands. That is one more reason to write tasks that treat interruption as cancellation: it is what makes them cancellable through their futures.

    } catch (ExecutionException e) {
        // exception thrown in task; rethrow
        throw launderThrowable(e.getCause());
    } finally {
        // Harmless if task already completed
        task.cancel(true);  // interrupt if running
    }
}

Whenever Future.get throws InterruptedException or TimeoutException and the result is no longer needed, cancel the task. Cancelling unconditionally in a finally block is a tidy idiom: cancelling a completed task has no effect.

7.2Stopping a Thread-based Service

Services own threads, and their lifetime outlives the method that created them. So they must expose a way to stop — and stopping one part means stopping the parts that depend on it.

Encapsulation says you should not manipulate a thread — interrupt it, change its priority — unless you own it. The thread API has no formal notion of ownership, but it is a useful one: the owner is usually the class that created the thread. A thread pool owns its workers; if those workers need interrupting, the pool should do it. Ownership is not transitive: an application may own a service which owns worker threads, but the application does not own the workers and should not try to stop them directly. Instead the service provides lifecycle methods — shutdown and shutdownNow, or equivalents for your own service.

7.2.1Example: a logging service

Logging can be as simple as inline println calls — stream classes are thread-safe, so no explicit synchronization is needed (though multi-line messages may need client-side locking to avoid interleaving, and inline logging costs performance at high volume, §11.6). The alternative is a service: log queues the message and a background thread writes it.

LogWriter is a multiple-producer, single-consumer design. Any activity calling log is a producer; the logger thread is the consumer. If the logger falls behind, the bounded queue blocks producers until it catches up.

NO SHUTDOWN Listing 7.13 · Producer–consumer logging service with no shutdown support 
public class LogWriter {
    private final BlockingQueue<String> queue;
    private final LoggerThread logger;
    public LogWriter(Writer writer) {
        this.queue = new LinkedBlockingQueue<String>(CAPACITY);
        this.logger = new LoggerThread(writer);
    }
    public void start() { logger.start(); }
    public void log(String msg) throws InterruptedException {
        queue.put(msg);
    }
    private class LoggerThread extends Thread {
        private final PrintWriter writer;
        ...
        public void run() {
            try {
                while (true)
                   writer.println(queue.take());
            } catch(InterruptedException ignored) {
            } finally {
                writer.close();
            }
        }
    }
}

Stopping the logger thread is easy — it sits in take, which is interruptible. But simply making it exit is not a satisfying shutdown: it discards messages already queued, and — more importantly — threads blocked in log because the queue is full will never be unblocked. Cancelling a producer–consumer activity requires cancelling both the producers and the consumers, and the producers here are not dedicated threads, so they cannot simply be interrupted.

Adding a "shutdown requested" flag that makes the logger drain the queue looks better, but it is a check-then-act race: a producer can observe "not yet shut down", be preempted, and then put after shutdown has begun — and block forever in log. Waiting a few seconds before declaring the queue drained only changes the likelihood of failure, not its nature.

RACY Listing 7.14 · Unreliable way to add shutdown support to the logging service 
public void log(String msg) throws InterruptedException {
    if (!shutdownRequested)
        queue.put(msg);
    else
        throw new IllegalStateException("logger is shut down");
}

The reliable fix is to make submitting a message atomic with the shutdown check — but without holding a lock across put, which can block. LogService does it with a guarded reservations counter: log atomically checks isShutdown and increments the reservation under the lock, then releases the lock and does the blocking put. The logger thread consumes until it sees shutdown requested and no outstanding reservations — at which point every message has either been written or is safely the producer's problem.

RELIABLE Listing 7.15 · Adding reliable cancellation to LogWriter 
public class LogService {
    private final BlockingQueue<String> queue;
    private final LoggerThread loggerThread;
    private final PrintWriter writer;
    @GuardedBy("this") private boolean isShutdown;
    @GuardedBy("this") private int reservations;
    public void start() { loggerThread.start(); }
    public void stop() {
        synchronized (this) { isShutdown = true; }
        loggerThread.interrupt();
    }
    public void log(String msg) throws InterruptedException {
        synchronized (this) {
            if (isShutdown)
                throw new IllegalStateException(...);
            ++reservations;
        }
        queue.put(msg);
    }
    private class LoggerThread extends Thread {
        public void run() {
            try {
                while (true) {
                    try {
                        synchronized (this) {
                            if (isShutdown && reservations == 0)
                                break;
                        }
                        String msg = queue.take();
                        synchronized (this) { --reservations; }
                        writer.println(msg);
                    } catch (InterruptedException e) { /*  retry  */ }
                }
            } finally {
                writer.close();
            }
        }
    }
}

§6.2.4 gave the two modes. In an abrupt shutdown shutdownNow attempts to cancel running tasks and returns the queued ones that never started. Other thread-owning services should offer the same choice.

Simple programs can start and stop a global ExecutorService from main. More sophisticated ones encapsulate it behind a service with its own lifecycle — LogService again, this time delegating to an ExecutorService instead of managing its own thread. That extends the ownership chain from application to service to thread, and each link manages the lifecycle of what it owns.

7.2.4Example: a one-shot execution service

If a method processes a batch and does not return until the batch is finished, use a private executor whose lifetime is bounded by the method call — and let invokeAll or invokeAny do the waiting. checkMail creates one, submits a task per host, and in a finally block shuts the executor down and awaits termination. (AtomicBoolean rather than a volatile boolean because a local variable captured by the inner Runnable must be final, which would preclude assigning to it.)

ONE-SHOT Listing 7.20 · Using a private executor whose lifetime is bounded by a method call 
boolean checkMail(Set<String> hosts, long timeout, TimeUnit unit)
        throws InterruptedException {
    ExecutorService exec = Executors.newCachedThreadPool();
    final AtomicBoolean hasNewMail = new AtomicBoolean(false);
    try {
        for (final String host : hosts)
            exec.execute(new Runnable() {
                public void run() {
                   if (checkMail(host))
                       hasNewMail.set(true);
                }
            });

        exec.shutdown();
        exec.awaitTermination(timeout, unit);
    }
    return hasNewMail.get();
}

7.2.5Limitations of shutdownNow

shutdownNow returns the tasks that were submitted but never started, so they can be logged or saved for later. But there is no general way to find out which tasks started and did not finish — so without the tasks checkpointing themselves, you cannot know the state of work that was in progress at shutdown time. (shutdownNow's returned Runnables may also be wrapper instances, not the objects you submitted.)

TrackingExecutor closes that gap: it encapsulates an ExecutorService and instruments execute to note, in a finally block, whether a task was still running when shutdown was requested and the thread's interrupted status was set — and if so, records it. After termination, getCancelledTasks returns them. For this to work, tasks must preserve the interrupted status when they return, which well-behaved tasks do anyway.

TRACKING Listing 7.21 · ExecutorService that keeps track of cancelled tasks after shutdown 
public class TrackingExecutor extends AbstractExecutorService {
    private final ExecutorService exec;
    private final Set<Runnable> tasksCancelledAtShutdown =
        Collections.synchronizedSet(new HashSet<Runnable>());
    ...
    public List<Runnable> getCancelledTasks() {
        if (!exec.isTerminated())
            throw new IllegalStateException(...);
        return new ArrayList<Runnable>(tasksCancelledAtShutdown);
    }

    public void execute(final Runnable runnable) {
        exec.execute(new Runnable() {
            public void run() {
                try {
                    runnable.run();
                } finally {
                    if (isShutdown()
                        && Thread.currentThread().isInterrupted())
                        tasksCancelledAtShutdown.add(runnable);
                }
            }
        });
    }

    // delegate other ExecutorService methods to exec
}

WebCrawler puts it to work. Crawling is unbounded work, so a crawler that must stop should remember where it got to: on stop it saves both the tasks that never started and those that were cancelled, and on start it resubmits them.

7.3Handling Abnormal Thread Termination

In a single-threaded console program, a crash is obvious. In a concurrent application a dead thread may look exactly like a quiet one.

The stack trace may be printed to a console nobody is watching, and the application may carry on as if nothing happened. The leading cause of premature thread death is RuntimeException: because it indicates a programming error, it is usually not caught, so it propagates and the thread terminates.

The consequences depend entirely on the thread's role. Losing one thread from a 50-thread pool is a performance footnote; losing a GUI event dispatch thread freezes the interface; and OutOfTime (§6.2.5) showed a service permanently out of commission because its single timer thread died. Task-processing threads — pool workers, the Swing event thread — spend their whole lives calling unknown code through an abstraction like Runnable, so they should be skeptical of it.

DEFENSIVE WORKER Listing 7.23 · Typical thread-pool worker thread structure 
public void run() {
    Throwable thrown = null;
    try {
        while (!isInterrupted())
            runTask(getTaskFromWorkQueue());
    } catch (Throwable e) {
        thrown = e;
    } finally {
        threadExited(this, thrown);
    }
}

This lets the thread die, but not before telling the framework, which can then replace it — or decide not to, because the pool is shutting down or demand has fallen. ThreadPoolExecutor and Swing both use this technique so one badly behaved task cannot stop subsequent ones from running. It is one of the few places where catching RuntimeException around untrusted code is the right call.

7.3.1Uncaught exception handlers

The reactive complement is the UncaughtExceptionHandler facility, which lets you detect a thread that has died from an uncaught exception. Before Java 5.0 the only way was to subclass ThreadGroup; now Thread.setUncaughtExceptionHandler sets one per thread and setDefaultUncaughtExceptionHandler sets the default. Only one handler is called: the JVM looks for the per-thread handler first, then a ThreadGroup handler, and the group's default implementation delegates up the parent chain until one handles it or it reaches the top-level group, which delegates to the default system handler — or prints the stack trace to the console if there is none.

public interface UncaughtExceptionHandler {
    void uncaughtException(Thread t, Throwable e);
}

What the handler does depends on quality-of-service requirements. The most common response is to log the message and stack trace; handlers can also try to restart the thread, shut the application down, page an operator, or take other corrective action.

📝

In long-running applications, always install uncaught exception handlers on all threads, if only to log. For pool threads, supply a ThreadFactory to the ThreadPoolExecutor constructor — and remember that only the thread's owner should change its handler.

There is one more subtlety worth knowing: exceptions reach the uncaught exception handler only for tasks submitted with execute. For tasks submitted with submit, any thrown exception — checked or not — is part of the task's return status, rethrown from Future.get wrapped in ExecutionException. If you want task-level failure notification, wrap the task in something that catches, or override the afterExecute hook.

7.4JVM Shutdown

The JVM shuts down in one of two ways — and only one of them gives you a chance to clean up.

An orderly shutdown is initiated when the last normal (non-daemon) thread terminates, when someone calls System.exit, or by platform-specific means such as Ctrl-C or SIGINT. An abrupt shutdown is Runtime.halt or the OS killing the process with SIGKILL.

7.4.1Shutdown hooks

In an orderly shutdown the JVM starts all registered shutdown hooks — unstarted threads registered with Runtime.addShutdownHook. The order is not guaranteed. Application threads that are still running continue to run concurrently with the shutdown, and the JVM makes no attempt to stop or interrupt them: they are abandoned when it halts. If a hook does not complete, the orderly shutdown hangs — and then the JVM has to be killed abruptly, which runs no hooks at all.

Hooks must therefore be thread-safe (they may run alongside anything), must make no assumptions about application state or why the JVM is shutting down, and must exit as quickly as possible — someone is waiting for the process to go away. Because all hooks run concurrently, a logger closed by one hook can break another. The recommended pattern is a single shutdown hook that runs a series of shutdown actions: sequentially, in one thread, avoiding races and deadlock between actions — and, where dependencies are known, in the right order.

HOOK Listing 7.26 · Registering a shutdown hook to stop the logging service 
public void start() {
    Runtime.getRuntime().addShutdownHook(new Thread() {
        public void run() {
            try { LogService.this.stop(); }
            catch (InterruptedException ignored) {}
        }
    });
}

7.4.2Daemon threads

Daemon threads exist so that a helper thread does not keep the JVM alive. When the JVM starts, all the threads it creates — GC and housekeeping — are daemons except main; new threads inherit the daemon status of the thread that created them. The only difference between the two kinds is what happens at exit: when a thread exits, the JVM takes an inventory, and if only daemons remain it starts an orderly shutdown. Then remaining daemons are abandoned — no finally blocks, no stack unwinding.

⚠️

Use daemon threads sparingly — few activities can be abandoned at any moment with no cleanup. They are especially dangerous for anything doing I/O. Keep them for housekeeping, such as a thread that periodically expires entries in an in-memory cache. Daemon threads are not a substitute for managing service lifecycle.

7.4.3Finalizers

The garbage collector reclaims memory, but file and socket handles must be returned to the OS explicitly. Finalizers were meant to help: an object with a nontrivial finalize gets it called after collection. In practice they are a poor tool — they run in a JVM-managed thread, so any state they touch is shared and must be synchronized; there is no guarantee of when, or even whether, they run; they impose significant performance cost; and they are extremely difficult to write correctly. finally blocks plus explicit close methods do a better job, with the sole exception of native-method-acquired resources.

Avoid finalizers.

1A cancellable, shutdown-able worker service

PATTERN Cancellation policy + interruption policy + lifecycle, in one class 
/**
 * Cancellation policy:
 *   request - cancelAll(), or shutdown() for graceful
 *   check   - inside the task, at its own cancellation points
 *   action  - interrupt the worker, task restores status, cleanup in finally
 */
public class JobService {
    private final ThreadPoolExecutor exec;      // owns the threads
    private final Set<Future<?>> inFlight =
            Collections.synchronizedSet(new HashSet<Future<?>>());

    public JobService(int nThreads, int maxBacklog) {
        this.exec = new ThreadPoolExecutor(
            nThreads, nThreads, 0L, TimeUnit.MILLISECONDS,
            new ArrayBlockingQueue<Runnable>(maxBacklog),   // bounded backlog
            new ThreadFactory() {
                private final AtomicInteger n = new AtomicInteger();
                public Thread newThread(Runnable r) {
                    Thread t = new Thread(r, "job-" + n.incrementAndGet());
                    // Only the owner sets the handler -- and now any death is visible.
                    t.setUncaughtExceptionHandler((th, e) ->
                        log("worker " + th.getName() + " died", e));
                    return t;
                }
            },
            new ThreadPoolExecutor.AbortPolicy());          // loud rejection
    }

    /** Submission returns the task's handle, which is also its cancellation handle. */
    public Future<?> submit(Job job) {
        Future<?> f = exec.submit(job::run);
        inFlight.add(f);
        return f;
    }

    /** Abrupt: cancel through futures, never by interrupting pool threads. */
    public List<Runnable> cancelAll() {
        synchronized (inFlight) {
            for (Future<?> f : inFlight)
                f.cancel(true);            // safe: pool threads have a known policy
        }
        return exec.shutdownNow();         // returns the never-started tasks
    }

    /** Graceful: accept nothing new, let the queue drain, escalate if it won't. */
    public boolean shutdown(long timeout, TimeUnit unit)
            throws InterruptedException {
        exec.shutdown();
        if (!exec.awaitTermination(timeout, unit)) {
            cancelAll();
            return exec.awaitTermination(5, TimeUnit.SECONDS);
        }
        return true;
    }

    /** A batch with one deadline: timed invokeAll cancels the stragglers itself. */
    public List<Result> runBatch(List<Job> jobs, long timeout, TimeUnit unit)
            throws InterruptedException {
        List<Callable<Result>> tasks = new ArrayList<Callable<Result>>();
        for (Job job : jobs)
            tasks.add(() -> job.call());
        List<Future<Result>> done = exec.invokeAll(tasks, timeout, unit);
        List<Result> results = new ArrayList<Result>();
        for (Future<Result> f : done) {
            try {
                results.add(f.get());
            } catch (CancellationException timedOut) {
                results.add(Result.SKIPPED);      // never started, or cancelled
            } catch (ExecutionException failed) {
                results.add(Result.failed(failed.getCause()));
            }
        }
        return results;
    }
}

2Shutting a whole application down in the right order

PATTERN One hook, sequential actions, bounded total time 
public final class Shutdown {
    private static final List<Runnable> ACTIONS =
            new CopyOnWriteArrayList<Runnable>();
    private static final AtomicBoolean STARTED = new AtomicBoolean();

    /** Register in dependency order: the last registered runs first. */
    public static void register(Runnable action) { ACTIONS.add(action); }

    public static void install() {
        Runtime.getRuntime().addShutdownHook(
                new Thread(Shutdown::runActions, "shutdown"));
    }

    /**
     * One thread, one pass, reverse order. Every action is isolated so a
     * failure cannot stop the rest -- a hook that throws delays JVM exit.
     */
    public static void runActions() {
        if (!STARTED.compareAndSet(false, true))
            return;                                   // at most once, ever
        for (int i = ACTIONS.size() - 1; i >= 0; i--) {
            try {
                ACTIONS.get(i).run();
            } catch (Throwable t) {
                System.err.println("shutdown action failed: " + t);
            }
        }
        ACTIONS.clear();
    }
}

// Wiring: services registered in dependency order, one hook to rule them all.
Shutdown.register(() -> cache.shutdown());     // runs last: nothing depends on it
Shutdown.register(() -> logService.stop());
Shutdown.register(() -> pool.shutdown(5, TimeUnit.SECONDS));   // runs first
Shutdown.install();

Note the pattern's shape: one hook, actions run in reverse registration order so dependencies stop before their dependents, every action wrapped so a failure cannot abort the rest, and no assumption that any other service is still alive.

Chapter 8 — Applying Thread Pools

Chapter 6 said the Executor framework decouples submission from execution. This chapter is the fine print: it is only a partial decoupling. Some tasks require a particular execution policy, some combinations of pool settings are quietly broken, and the difference between a pool that degrades and one that deadlocks is usually a queue size and a saturation policy.

📖 pp. 105–116 🧩 5 sections · 18 listings · no figures ⏱️ ~24 min read 🏷️ Part II — Structuring Concurrent Applications

Chapter in one paragraph

TL;DR — the six things worth remembering

  1. Not every task fits every policy. Dependent tasks need a pool big enough that nothing queues; tasks relying on thread confinement need a single-threaded executor; ThreadLocal in a pool is only safe when its lifetime is bounded by one task.
  2. Thread starvation deadlock is the tax on dependent tasks. A task that submits work to its own pool and waits can deadlock even in a large pool — and an unrelated resource pool (JDBC connections) can impose a hidden, smaller bound.
  3. Size pools from workload, not from habit. Nthreads = Ncpu × Ucpu × (1 + W/C) for CPU-bound work with waiting; for any other scarce resource, divide the resource by what each task holds.
  4. Three queue strategies, three failure modes. Unbounded queues hide overload until memory runs out; bounded queues force a saturation policy; synchronous handoff needs capacity or a rejection policy.
  5. Choose the saturation policy deliberately. Abort, discard, discard-oldest, or caller-runs — and remember caller-runs pushes overload back out through your application to the client.
  6. The framework is meant to be extended. Thread factories for names and exception handlers, beforeExecute/afterExecute/terminated for timing, and parallel recursion — with the work queue replacing the call stack.

8.1Implicit Couplings Between Tasks and Execution Policies

"Decoupled" was an overstatement. The framework gives you a lot of freedom in specifying an execution policy, but not all tasks are compatible with all policies.

Task characteristicWhat it requires of the policyWhat breaks otherwise
Independent tasksNothing — any pool size or configuration worksOnly performance changes
Dependent tasks (submit and wait)Pool large enough that tasks never queue or get rejected; or an unbounded poolThread starvation deadlock (§8.1.1)
Tasks that exploit thread confinementSequential execution — a single-threaded executor, whose stronger guarantees let task code skip synchronizationSafety is silently lost if moved to a pool

Tasks using ThreadLocalPer-task lifetime only — never as a channel between tasksStale values: pool threads are reused, reaped, and replaced

Thread pools work best with homogeneous, independent tasks. Mixing long- and short-running tasks risks clogging the pool unless it is very large; submitting tasks that depend on each other risks deadlock unless the pool is unbounded. Fortunately, the requests of a typical network server usually meet these guidelines. Where they don't, document the requirement next to the executor configuration, so a future maintainer doesn't "optimise" the pool and quietly trade safety or liveness for a benchmark number.

8.1.1Thread starvation deadlock

In a single-threaded executor, a task that submits another task to the same executor and waits for its result will always deadlock: the second task waits on the work queue for the first to finish, and the first waits for the second. The same thing happens in a larger pool once every thread is blocked waiting for a task still sitting in the queue. This is thread starvation deadlock, and it can occur whenever a pool task starts an unbounded blocking wait for something only another pool task can provide.

ThreadDeadlock is the canonical example — a page renderer that submits header and footer tasks to its own single-threaded executor and then blocks on their futures. Tasks coordinating through a barrier can deadlock the same way if the pool is too small for all the parties.

DEADLOCK — DON'T DO THIS Listing 8.1 · Task that deadlocks in a single-threaded executor 
public class ThreadDeadlock {
    ExecutorService exec = Executors.newSingleThreadExecutor();

    public class RenderPageTask implements Callable<String> {
        public String call() throws Exception {
            Future<String> header, footer;
            header = exec.submit(new LoadFileTask("header.html"));
            footer = exec.submit(new LoadFileTask("footer.html"));
            String page = renderBody();
            // Will deadlock -- task waiting for result of subtask
            return header.get() + page + footer.get();
        }
    }
}
⚠️

Pool size is not the only bound. If the application uses a JDBC pool of ten connections and every task needs one, then the thread pool is effectively ten threads — the rest block waiting for a connection. Any scarce pooled resource imports its own limit into your execution policy.

8.1.2Long-running tasks

Even without deadlock, a pool can be clogged: if tasks block for extended periods, short tasks queue behind them and service time rises for everyone. One mitigation is to use timed waits instead of unbounded ones — Thread.join, BlockingQueue.put, CountDownLatch.await, Selector.select all have timed forms. On timeout, mark the task failed and abort it or requeue it for later. Every task then makes progress towards success or failure, and threads are released. A pool that is frequently full of blocked tasks is a signal in itself: either the pool is too small or the tasks are holding threads they should not.

8.2Sizing Thread Pools

Pool sizes should rarely be hard-coded — and you only need to avoid the extremes.

The ideal size depends on the tasks and the deployment machine, so it belongs in configuration or in a computation over Runtime.availableProcessors(). Too big, and threads compete for scarce CPU and memory, raising memory use and risking exhaustion; too small, and processors sit idle while work waits.

⚙️
Compute-bound

An Ncpu-processor machine usually achieves optimum utilization with Ncpu + 1 threads — the extra one covers the occasional page fault or scheduling pause.

🌐
I/O-bound

Larger, because threads spend part of their time not schedulable. Estimate the ratio of wait time to compute time — profiling, instrumentation, or simply running a benchmark at several pool sizes and watching CPU utilization.

🔒
Resource-bound

For memory, file handles, sockets or connections, the arithmetic is easy: total resource ÷ resource per task = an upper bound on the pool.

The sizing formula, for keeping processors at a target utilization:

Nthreads = Ncpu × Ucpu × (1 + W/C)

Ncpu = Runtime.getRuntime().availableProcessors() · Ucpu = target CPU utilization, 0 ≤ U ≤ 1 · W/C = ratio of wait time to compute time

Note that the target utilization is the throttle: asking for 100% leaves no headroom. And thread pool size and resource pool size interact in both directions — if every task needs a connection, the thread pool is bounded by the connection pool; if pool tasks are the only consumers of connections, the connection pool is bounded by the thread pool.

8.3.1Thread creation and teardown

Three parameters govern thread lifecycle. Core size is the target: the pool tries to keep this many threads even when idle, and will not exceed it unless the work queue is full. Maximum size is the ceiling on concurrently active threads. Keep-alive is how long an idle thread may live before becoming a candidate for reaping, which only happens if the pool is above its core size.

Reaping idle threads gives resources back to the rest of the system, at the cost of re-creating them later — the same trade as everything else here. The factories are just points on this curve: newFixedThreadPool sets core = max, which has the effect of an infinite timeout; newCachedThreadPool sets core to 0, max to Integer.MAX_VALUE and a one-minute timeout, giving an infinitely expandable pool that contracts when demand falls.

8.3.2Managing queued tasks

A bounded pool limits concurrency, but not resource use: if requests arrive faster than they are handled they still queue — as Runnables plus list nodes rather than threads, which is much cheaper, but still unbounded growth. Bursts are normal and queues smooth them; sustained overload has to be throttled somewhere, or you run out of memory. Even before that, response time degrades steadily as the queue grows.

Queue strategyUsed byEffectRisk
Unbounded (LinkedBlockingQueue)newFixedThreadPool, newSingleThreadExecutorTasks always accepted; pool size stays at coreQueue grows without bound — OutOfMemoryError
Bounded (ArrayBlockingQueue, bounded LinkedBlockingQueue/PriorityBlockingQueue)Hand-built executorsPrevents exhaustion; forces a saturation policyMust tune queue size and pool size together
Synchronous handoff (SynchronousQueue)newCachedThreadPoolNo queue at all: direct producer→worker handoff, lower latencyNeeds an unbounded pool or a rejection policy

A large queue with a small pool reduces memory, CPU and context switching at the cost of throughput and latency; a small queue with a large pool reacts faster but accepts less slack. PriorityBlockingQueue gives you control over order (natural ordering or a Comparator) rather than just capacity — at the price of the queue not being FIFO. And a warning that returns in §8.3.3: bounding either the pool or the queue is only safe for independent tasks; with dependent tasks it converts overload into starvation deadlock. The alternative configuration for tasks that submit and wait is a bounded pool with a SynchronousQueue and the caller-runs policy.

8.3.3Saturation policies

When the queue is full — and also when a task is submitted to an executor that has been shut down — the saturation policy decides what happens. Set it with setRejectedExecutionHandler; four implementations ship with the library.

PolicyWhat it doesWhen it's the right choice
AbortPolicy (default)Throws RejectedExecutionExceptionYou want to handle overflow yourself, and a loud failure is safer than a silent drop
DiscardPolicySilently discards the new taskTasks are idempotent and losing one is genuinely acceptable
DiscardOldestPolicyDrops the task that would run next, then retries the new oneOnly for FIFO-ish queues — with a priority queue it discards the highest-priority element
CallerRunsPolicyRuns the task in the submitting threadYou want throttling with no loss and no exceptions — the usual choice for a server

Caller-runs is the interesting one, because it implements throttling by pushing work back to the caller. In a web server, once the pool is busy and the queue full, the next task runs in the acceptor thread. That thread is then busy for a while: it cannot submit more tasks and it cannot call accept, so incoming requests queue in the TCP layer instead of the application. If overload persists, the TCP layer decides it has buffered enough and starts refusing connections too. The overload is pushed outward — from pool threads to the work queue to the application to the TCP layer to the client — which is precisely graceful degradation.

There is no built-in policy that makes execute block. For that, bound the injection rate with a semaphore: use an unbounded queue (there is no reason to bound both) and set the permit count to pool size plus the number of queued tasks you are willing to hold, since the semaphore counts tasks both running and waiting.

THROTTLE Listing 8.4 · Using a Semaphore to throttle task submission 
@ThreadSafe
public class BoundedExecutor {
    private final Executor exec;
    private final Semaphore semaphore;

    public BoundedExecutor(Executor exec, int bound) {
        this.exec = exec;
        this.semaphore = new Semaphore(bound);
    }

    public void submitTask(final Runnable command)
            throws InterruptedException {
        semaphore.acquire();
        try {
            exec.execute(new Runnable() {
                public void run() {
                    try {
                        command.run();
                    } finally {
                        semaphore.release();
                    }
                }
            });
        } catch (RejectedExecutionException e) {
            semaphore.release();
        }
    }
}

INSTRUMENTED THREAD Listing 8.7 · Custom thread base class 
public class MyAppThread extends Thread {
    public static final String DEFAULT_NAME = "MyAppThread";
    private static volatile boolean debugLifecycle = false;
    private static final AtomicInteger created = new AtomicInteger();
    private static final AtomicInteger alive = new AtomicInteger();
    private static final Logger log = Logger.getAnonymousLogger();

    public MyAppThread(Runnable r) { this(r, DEFAULT_NAME); }

    public MyAppThread(Runnable runnable, String name) {
        super(runnable, name + "-" + created.incrementAndGet());
        setUncaughtExceptionHandler(
            new Thread.UncaughtExceptionHandler() {
                public void uncaughtException(Thread t,
                                              Throwable e) {
                    log.log(Level.SEVERE,
                        "UNCAUGHT in thread " + t.getName(), e);
                }
            });
    }

    public void run() {
        // Copy debug flag to ensure consistent value throughout.
        boolean debug = debugLifecycle;
        if (debug) log.log(Level.FINE, "Created "+getName());
        try {
            alive.incrementAndGet();
            super.run();
        } finally {
            alive.decrementAndGet();
            if (debug) log.log(Level.FINE, "Exiting "+getName());
        }
    }

    public static int getThreadsCreated() { return created.get(); }
    public static int getThreadsAlive() { return alive.get(); }
    public static boolean getDebug() { return debugLifecycle; }
    public static void setDebug(boolean b) { debugLifecycle = b; }
}

8.4Extending ThreadPoolExecutor

Three hooks — beforeExecute, afterExecute, terminated — turn a pool into a place to put logging, timing and statistics.

The first two run in the thread that executes the task, which is what makes them useful and what you must keep in mind: beforeExecute can store a value in a ThreadLocal and afterExecute will find it in the same thread. afterExecute is called whether the task returns normally or throws an exception — but not if it throws an Error, and not if beforeExecute itself throws a RuntimeException (in which case the task never runs). terminated runs once, after the pool has finished shutting down, and is the place to flush whatever the hooks collected.

TIMING Listing 8.9 · Thread pool extended with logging and timing 
public class TimingThreadPool extends ThreadPoolExecutor {
    private final ThreadLocal<Long> startTime
            = new ThreadLocal<Long>();
    private final Logger log = Logger.getLogger("TimingThreadPool");
    private final AtomicLong numTasks = new AtomicLong();
    private final AtomicLong totalTime = new AtomicLong();

    protected void beforeExecute(Thread t, Runnable r) {
        super.beforeExecute(t, r);
        log.fine(String.format("Thread %s: start %s", t, r));
        startTime.set(System.nanoTime());
    }

    protected void afterExecute(Runnable r, Throwable t) {
        try {
            long endTime = System.nanoTime();
            long taskTime = endTime - startTime.get();
            numTasks.incrementAndGet();
            totalTime.addAndGet(taskTime);
            log.fine(String.format("Thread %s: end %s, time=%dns",
                    t, r, taskTime));
        } finally {
            super.afterExecute(r, t);
        }
    }

    protected void terminated() {
        try {
            log.info(String.format("Terminated: avg time=%dns",
                    totalTime.get() / numTasks.get()));
        } finally {
            super.terminated();
        }
    }
}

8.5Parallelizing Recursive Algorithms

Loops with independent iterations and nontrivial bodies are the easy win. Recursion is the same idea with the stack replaced by a work queue.

If the loop iterations are independent and you needn't wait for all of them before proceeding, an Executor turns a sequential loop into a parallel one. processInParallel returns as soon as every task is queued rather than when they finish; use invokeAll to wait for all of them, or a CompletionService to consume results as they arrive. Iterations are worth parallelizing when they are independent and the body does enough work to justify the cost of managing a task.

LOOP Listing 8.10 · Transforming sequential execution into parallel execution 
void processSequentially(List<Element> elements) {
    for (Element e : elements)
        process(e);
}

void processInParallel(Executor exec, List<Element> elements) {
    for (final Element e : elements)
        exec.execute(new Runnable() {
            public void run() { process(e); }
        });
}

The easier recursive case is where an iteration does not need the results of the recursive calls it makes. sequentialRecursive walks a tree depth-first, computing each node's result as it visits; parallelRecursive walks the same tree but submits the computation, so the traversal stays sequential and only the computations run in parallel. The caller then needs a way to know when the work is done — typically a private executor, shutdown, and awaitTermination, collecting into a ConcurrentLinkedQueue.

RECURSION Listing 8.11 · Transforming sequential tail-recursion into parallelized recursion 
public<T> void sequentialRecursive(List<Node<T>> nodes,
                                   Collection<T> results) {
    for (Node<T> n : nodes) {
        results.add(n.compute());
        sequentialRecursive(n.getChildren(), results);
    }
}

public<T> void parallelRecursive(final Executor exec,
                                 List<Node<T>> nodes,
                                 final Collection<T> results) {
    for (final Node<T> n : nodes) {
        exec.execute(new Runnable() {
            public void run() {
                results.add(n.compute());
            }
        });
        parallelRecursive(exec, n.getChildren(), results);
    }
}
WAIT FOR ALL Listing 8.12 · Waiting for results to be calculated in parallel 
public<T> Collection<T> getParallelResults(List<Node<T>> nodes)
        throws InterruptedException {
    ExecutorService exec = Executors.newCachedThreadPool();
    Queue<T> resultQueue = new ConcurrentLinkedQueue<T>();
    parallelRecursive(exec, nodes, resultQueue);
    exec.shutdown();

}

8.5.1Example: a puzzle framework

The payoff case is a puzzle solver: find a sequence of moves from a start position to a goal. A Puzzle<P, M> is an initial position, a goal test, the legal moves from a position, and the result of applying a move. A Node is an immutable link — position, the move that produced it, and the previous node — so following the links back reconstructs the solution.

ABSTRACTION Listing 8.13 · Abstraction for puzzles like the "sliding blocks puzzle" 
public interface Puzzle<P, M> {
    P initialPosition();
    boolean isGoal(P position);
    Set<M> legalMoves(P position);
    P move(P position, M move);
}
IMMUTABLE NODE Listing 8.14 · Link node for the puzzle solver framework 
@Immutable
static class Node<P, M> {
    final P pos;
    final M move;
    final Node<P, M> prev;

    Node(P pos, M move, Node<P, M> prev) {...}

    List<M> asMoveList() {
        List<M> solution = new LinkedList<M>();
        for (Node<P, M> n = this; n.move != null; n = n.prev)
            solution.add(0, n.move);
        return solution;
    }
}

The sequential solver is a plain depth-first search that returns the first solution found — not necessarily the shortest — and terminates when it finds one or exhausts the space.

SEQUENTIAL Listing 8.15 · Sequential puzzle solver 
public class SequentialPuzzleSolver<P, M> {
    private final Puzzle<P, M> puzzle;
    private final Set<P> seen = new HashSet<P>();

    public SequentialPuzzleSolver(Puzzle<P, M> puzzle) {
        this.puzzle = puzzle;
    }

    public List<M> solve() {
        P pos = puzzle.initialPosition();
        return search(new Node<P, M>(pos, null, null));
    }

    private List<M> search(Node<P, M> node) {
        if (!seen.contains(node.pos)) {
            seen.add(node.pos);
            if (puzzle.isGoal(node.pos))
                return node.asMoveList();
            for (M move : puzzle.legalMoves(node.pos)) {
                P pos = puzzle.move(node.pos, move);
                Node<P, M> child = new Node<P, M>(pos, move, node);
                List<M> result = search(child);
                if (result != null)
                    return result;
            }
        }
        return null;
    }

The concurrent version makes each solver task a Node that is also a Runnable: it evaluates legal moves, prunes positions already seen, checks whether anyone has solved the puzzle yet, and submits the unsearched positions. Two details do the real work. The seen set becomes a ConcurrentHashMap, because putIfAbsent makes "add this position only if it is new" atomic — the same race as Memorizer, one chapter's worth of experience later. Stopping the search needs a latch that also carries a result: ValueLatch holds one value that only the first setter installs, lets callers test whether it has been set, and lets the main thread block until it is. The first task to find a solution also shuts the executor down so no new tasks are accepted; setting the rejection handler to discard means subsequent submissions fail silently instead of throwing, and the pool drains and terminates.

@ThreadSafe
public class ValueLatch<T> {
    @GuardedBy("this") private T value = null;
    private final CountDownLatch done = new CountDownLatch(1);

    public boolean isSet() {
        return (done.getCount() == 0);
    }

    public synchronized void setValue(T newValue) {
        if (!isSet()) {
            value = newValue;
            done.countDown();
        }
    }

    public T getValue() throws InterruptedException {
        done.await();
        synchronized (this) {
            return value;
        }
    }
}

1One executor factory, sized from the machine

PATTERN Pool sized from N_cpu and W/C, bounded queue, caller-runs, named threads 
public final class Pools {
    private static final int N_CPU =
            Runtime.getRuntime().availableProcessors();

    /**
     * N_threads = N_cpu * U_cpu * (1 + W/C)
     *   U_cpu - target utilization, 0..1
     *   W/C   - ratio of wait time to compute time (profile it, don't guess)
     */
    public static int sizeFor(double targetUtil, double waitToCompute) {
        if (targetUtil <= 0 || targetUtil > 1 || waitToCompute < 0)
            throw new IllegalArgumentException("bad sizing input");
        return Math.max(1,
                (int) Math.ceil(N_CPU * targetUtil * (1 + waitToCompute)));
    }

    /** CPU-bound work: N_cpu + 1 covers page faults and scheduling gaps. */
    public static ThreadPoolExecutor computePool(String name) {
        int n = N_CPU + 1;
        return new ThreadPoolExecutor(n, n, 0L, TimeUnit.MILLISECONDS,
                new LinkedBlockingQueue<Runnable>(1000),   // bounded: no silent growth
                named(name),
                new ThreadPoolExecutor.CallerRunsPolicy());  // backpressure, no loss
    }

    /** I/O-bound work: more threads, same discipline. */
    public static ThreadPoolExecutor ioPool(String name, int maxBacklog) {
        int n = sizeFor(0.9, 4.0);          // e.g. 4x wait-to-compute
        return new ThreadPoolExecutor(n, n, 60L, TimeUnit.SECONDS,
                new ArrayBlockingQueue<Runnable>(maxBacklog),
                named(name),
                new ThreadPoolExecutor.AbortPolicy());       // we handle overflow
    }

    /** Threads you can find in a thread dump, with deaths that get logged. */
    private static ThreadFactory named(final String prefix) {
        final AtomicInteger n = new AtomicInteger();
        return new ThreadFactory() {
            public Thread newThread(Runnable r) {
                Thread t = new Thread(r, prefix + "-" + n.incrementAndGet());
                t.setUncaughtExceptionHandler((th, e) ->
                        System.err.println("uncaught in " + th.getName() + ": " + e));
                return t;                   // non-daemon: we own the lifecycle
            }
        };
    }
}

2A pool that reports itself

PATTERN Hooks for latency percentiles, plus the gauges that tell you the pool is clogged 
public class InstrumentedPool extends ThreadPoolExecutor {
    private final ThreadLocal<Long> started = new ThreadLocal<Long>();
    private final LongAdder count = new LongAdder();
    private final LongAdder totalNanos = new LongAdder();
    private final AtomicLong maxNanos = new AtomicLong();

    public InstrumentedPool(int core, int max, BlockingQueue<Runnable> q,
                            ThreadFactory tf, RejectedExecutionHandler h) {
        super(core, max, 60L, TimeUnit.SECONDS, q, tf, h);
        // Let core threads time out: an idle pool should shrink (Java 6+).
        allowCoreThreadTimeOut(true);
    }

    @Override protected void beforeExecute(Thread t, Runnable r) {
        super.beforeExecute(t, r);
        started.set(System.nanoTime());
    }

    @Override protected void afterExecute(Runnable r, Throwable failure) {
        try {
            Long begin = started.get();
            if (begin != null) {
                long elapsed = System.nanoTime() - begin;
                count.increment();
                totalNanos.add(elapsed);
                long seen;
                do {                              // max, without a lock or a reset
                    seen = maxNanos.get();
                } while (elapsed > seen && !maxNanos.compareAndSet(seen, elapsed));
                started.remove();                 // never leak into the next task
            }
            if (failure != null)      // non-null for Errors only: execute()
                System.err.println("task died: " + failure);  // reports Exceptions via UEH
        } finally {
            super.afterExecute(r, failure);
        }
    }

    @Override protected void terminated() {
        try {
            long n = count.sum();
            System.out.printf("pool done: %d tasks, avg %.1f ms, max %.1f ms%n",
                    n,
                    n == 0 ? 0.0 : totalNanos.sum() / 1e6 / n,
                    maxNanos.get() / 1e6);
        } finally {
            super.terminated();
        }
    }

    /** Queue depth is the leading indicator of a clogged pool. */
    public String health() {
        return String.format("active=%d queued=%d completed=%d poolSize=%d",
                getActiveCount(), getQueue().size(),
                getCompletedTaskCount(), getPoolSize());
    }
}

Chapter 9 — GUI Applications

Every swing you have ever made at a frozen window was a thread bug. GUI toolkits are single-threaded subsystems: all presentation state lives in one event dispatch thread, and thread confinement — not synchronization — is what keeps it consistent. That single decision gives you a simple programming model and one hard rule: never block the event thread. The rest of the chapter is about obeying that rule without losing the ability to cancel, report progress, and share data.

TL;DR — the six things worth remembering

  1. GUI toolkits are single-threaded on purpose. Multithreaded GUI frameworks were tried repeatedly and abandoned: the two-way flow between input events and application callbacks makes inconsistent lock ordering inevitable (§9.1).
  2. The single-thread rule. Swing components and models may be created, modified, and queried only from the event dispatch thread. Safety comes from confinement, not from synchronized.
  3. The event thread is an Executor. Events are tasks, the event queue is a work queue, and invokeLater/invokeAndWait are execute/submit().get() — which is why GuiExecutor is nine lines long.
  4. Never block the event thread. A long task run there freezes the UI — the user cannot even press Cancel, because the cancel listener is itself an event waiting behind the task.
  5. Long tasks hop threads. Start in the event thread, run in a background pool, then hop back to the event thread to touch presentation objects. Cancellation and progress belong in a reusable helper, not in each listener.
  6. Shared data models need a plan. Either make the model thread-safe, or split it: presentation model confined to the event thread, shared model thread-safe, updates flowing as snapshots or increments.

9.1Why Are GUIs Single-threaded?

Not for lack of trying. Multithreaded GUI toolkits are one of the recurring "failed dreams" of computer science, and the reason is structural rather than accidental.

Old GUI applications processed events from a "main event loop". Modern frameworks are only slightly different: they create a dedicated event dispatch thread (EDT) that pulls events off a queue and dispatches them to application-defined handlers. Qt, NextStep, MacOS Cocoa, X Windows and Swing all converged on this design.

The reason is the direction in which work flows. User-initiated actions bubble up from the OS into the application: the OS detects a click, the toolkit turns it into a mouse event, and it arrives at a listener as a higher-level "button pressed" event. Application-initiated actions bubble down: changing a component's background colour starts in application code and is dispatched to a component class and onward to the OS for rendering.

The recipe for deadlock

Activities access the same GUI objects in opposite orders. Add a requirement that each object be thread-safe, and each thread must acquire the objects' locks — in whatever order its direction of travel implies. Inconsistent lock ordering, and therefore deadlock (Chapter 10), is the predictable result.

Model–view–controller makes it worse rather than better. Factoring a user interaction into cooperating model, view and controller objects simplifies the application, but the controller calls into the model, the model notifies the view, and the controller can also call into the view — which may call back into the model to query state. Three objects, two directions, no global order.

📎

Graham Hamilton, then a Sun VP, put it plainly on his weblog: a multithreaded GUI toolkit can be made to work if it is very carefully designed, exposes its locking methodology in gory detail, and if you are very smart, very careful, and hold the whole structure of the toolkit in your head. "If you get one of these things slightly wrong, things will mostly work, but you will get occasional hangs (due to deadlocks) or glitches (due to races)." That set of characteristics does not scale to widespread commercial use — which is why your toolkit is single-threaded.

Single-threaded GUI frameworks achieve thread safety through thread confinement: every GUI object, visual component and data model is accessed exclusively from the event thread. The burden is pushed back onto the application developer, who must make sure the confinement actually holds.

9.1.1Sequential event processing

GUI applications process fine-grained events — mouse clicks, key presses, timer expirations. Events are a kind of task, and the AWT/Swing event machinery is structurally an Executor with a single worker and an unbounded queue.

One thread means tasks run sequentially: one finishes before the next begins, and no two overlap. That simplifies task code considerably — you never have to reason about interference from another task. The price is that a slow task makes every other task wait. If those other tasks are what respond to user input or paint feedback, the application looks frozen: a long task in the event thread means the user cannot even click Cancel, because the cancel button's listener is an event queued behind the task that is running.

So: tasks that execute in the event thread must return control quickly. Anything long-running — spell-checking a document, walking the file system, fetching a resource over the network — must run in another thread, and any update to the UI (progress, completion) must come back to the event thread. That is the whole of §9.3 in one sentence, and it can get complicated quickly.

9.1.2Thread confinement in Swing

All Swing components (JButton, JTable, …) and data model objects (TableModel, TreeModel) are confined to the event thread. GUI objects are kept consistent not by synchronization but by confinement: tasks in the event thread need no synchronization to touch presentation objects, and code outside the event thread may not touch them at all.

📏

The Swing single-thread rule. Swing components and models should be created, modified, and queried only from the event-dispatching thread.

As with all rules there are exceptions, all of them documented as thread-safe in the Javadoc:

  • SwingUtilities.isEventDispatchThread — asks whether the current thread is the event thread;
  • SwingUtilities.invokeLater — schedules a Runnable on the event thread; callable from any thread;
  • SwingUtilities.invokeAndWait — schedules a task on the event thread and blocks the caller until it completes; callable only from a non-GUI thread;
  • methods that enqueue a repaint or revalidation request on the event queue — callable from any thread;
  • methods that add and remove listeners — callable from any thread, though listeners are always invoked in the event thread.

invokeLater and invokeAndWait behave a great deal like Executor.execute and ExecutorService.submit(...).get(). In fact the threading-related methods of SwingUtilities can be implemented with a single-threaded executor, as in Listing 9.1 — not how Swing is implemented, since it predates the Executor framework, but probably how it would be if written today.

BOOK Listing 9.1 · Implementing SwingUtilities using an Executor 
public class SwingUtilities {
    private static final ExecutorService exec =
        Executors.newSingleThreadExecutor(new SwingThreadFactory());
    private static volatile Thread swingThread;

    private static class SwingThreadFactory implements ThreadFactory {
        public Thread newThread(Runnable r) {
            swingThread = new Thread(r);
            return swingThread;
        }
    }

    public static boolean isEventDispatchThread() {
        return Thread.currentThread() == swingThread;
    }

    public static void invokeLater(Runnable task) {
        exec.execute(task);
    }

    public static void invokeAndWait(Runnable task)
            throws InterruptedException, InvocationTargetException {
        Future f = exec.submit(task);
        try {
            f.get();
        } catch (ExecutionException e) {
            throw new InvocationTargetException(e);
        }
    }
}

Two details make this more than a curiosity. The event thread is a single-threaded Executor that processes tasks from the event queue — and, like a thread pool, it occasionally loses its worker thread and replaces it, which is invisible to tasks. (swingThread is volatile precisely because the factory writes it from the new thread while any thread may read it in isEventDispatchThread.)

Sequential single-threaded execution is the right execution policy when tasks are short-lived, when scheduling predictability does not matter, or when it is imperative that tasks not run concurrently. GUI event handling is all three. GuiExecutor (Listing 9.2) goes the other way and builds an Executor on top of SwingUtilities — one that runs a task inline if it is already on the event thread, and hands it to invokeLater otherwise. That inline case matters: a task that is already on the event thread must not queue itself behind the work it is currently doing.

BOOK Listing 9.2 · Executor built atop SwingUtilities 
public class GuiExecutor extends AbstractExecutorService {

    private GuiExecutor() { }

The same idea transfers to other toolkits: SWT offers Display.asyncExec, which is invokeLater under another name. What transfers everywhere is the shape — a single-threaded subsystem plus a hand-off primitive — not the class name.

9.2Short-running GUI Tasks

Most GUI code never has to think about threads. It is worth knowing exactly where that free ride ends.

Events originate in the event thread and bubble up to application listeners, which usually compute something that affects presentation objects. For simple, short-running tasks the entire action can stay in the event thread.

Listing 9.3 is the canonical example: a button that changes colour when pressed. The toolkit delivers an ActionEvent on the event thread to every registered listener; the listener picks a colour and sets the button's background. The event originates in the toolkit and is delivered to the application; the application modifies the GUI in response.

BOOK Listing 9.3 · Simple event listener 
final Random random = new Random();
final JButton button = new JButton("Change Color");
...

    public void actionPerformed(ActionEvent e) {
        button.setBackground(new Color(random.nextInt()));

That trivial example characterizes the majority of interactions between GUI applications and GUI toolkits. So long as tasks are short-lived and touch only GUI objects — or other thread-confined or thread-safe application objects — you can almost totally ignore threading and do everything from the event thread, and the right thing happens.

A slightly more complicated variant, shown in Figure 9.2, adds a formal data model such as a TableModel or TreeModel. Swing splits most visual components into a model (the data) and a view (the rules for displaying it). Models fire events when their data changes and views subscribe. So a listener that changes a table updates the model and calls one of the fireXxx methods; those invoke the view's table model listeners, which update the view.

⚠️

The fireXxx methods of Swing data models call the model's listeners directly rather than posting an event to the queue. That is efficient and keeps ordering obvious, but it means fireXxx may only be called from the event thread — calling it from a background thread runs the views' listeners on that background thread, breaking the single-thread rule in the least visible way possible.

9.3Long-running GUI Tasks

If every task were short, the whole application could live in the event thread and you would never think about threads. Spell checking, background compilation and remote fetches end that idyll.

Swing makes it easy to have a task run in the event thread but — prior to Java 6 — provided no mechanism for helping GUI tasks execute code in other threads. Swing doesn't need to help: you can create your own Executor for long-running tasks. A cached thread pool is a good choice here, because GUI applications rarely launch large numbers of long-running tasks, so there is little risk of the pool growing without bound. (Contrast Chapter 8: the same pool would be a poor choice for a server.)

Start with the simplest version — a task with no cancellation, no progress, and no completion update — and add the features one at a time. Listing 9.4 binds a long-running task to a button.

BOOK Listing 9.4 · Binding a long-running task to a visual component 
ExecutorService backgroundExec = Executors.newCachedThreadPool();
...
button.addActionListener(new ActionListener() {
    public void actionPerformed(ActionEvent e) {
        backgroundExec.execute(new Runnable() {
            public void run() { doBigComputation(); }
        });
}});

Regardless of the two layers of inner classes, this is fairly straightforward: the listener is called in the event thread and submits a Runnable to the pool. But it is "fire and forget", which is rarely what a user wants — there is usually visual feedback when a long task completes. And you cannot touch presentation objects from the background thread, so on completion the task must submit another task to run in the event thread.

Listing 9.5 does that the obvious way, and is starting to get complicated: three layers of inner classes. The listener dims the button and sets a label, then submits the background task; when that finishes it queues a third task on the event thread that re-enables the button and restores the label.

BOOK Listing 9.5 · Long-running task with user feedback

        button.setEnabled(false);
        label.setText("busy");
        backgroundExec.execute(new Runnable() {
            public void run() {
                try {
                    doBigComputation();
                } finally {
                    GuiExecutor.instance().execute(new Runnable() {

                            label.setText("idle");

                }
            }
        });
    }

The task triggered by the button is really three sequential subtasks whose execution alternates between the event thread and the background thread: update the UI and start the background work; do the work; queue the UI update. This thread hopping is typical of GUI code. Note the finally — the interface must be restored even if the computation throws, or the button stays disabled forever.

9.3.1Cancellation

Any task long enough to need a background thread is long enough that the user may want to cancel it. You could implement cancellation with thread interruption directly, but Future was designed to manage cancellable tasks and is much easier to use.

Calling cancel(true) on a Future interrupts the thread executing the task if it is running. If the task is written to be responsive to interruption (Chapter 7), it can return early. Listing 9.6 polls the thread's interrupted status and bails out.

9.3.2Progress and completion indication

Future simplified cancellation; FutureTask also has a done hook that facilitates completion notification. done is called after the background Callable completes. By having done trigger a completion task in the event thread, we can build a BackgroundTask class with an onCompletion hook that always runs on the event thread (Listing 9.7).

BackgroundTask also supports progress: the compute method can call setProgress, which causes onProgress to be invoked in the event thread. To use it you implement compute, which runs in the background thread, and optionally override onCompletion and onProgress, which run in the event thread.

BOOK Listing 9.7 · Background task class supporting cancellation, completion notification, and progress notification 
abstract class BackgroundTask<V> implements Runnable, Future<V> {
    private final FutureTask<V> computation = new Computation();

    private class Computation extends FutureTask<V> {
        public Computation() {
            super(new Callable<V>() {
                public V call() throws Exception {
                    return BackgroundTask.this.compute() ;
                }
            });
        }
        protected final void done() {
            GuiExecutor.instance().execute(new Runnable() {
                public void run() {
                    V value = null;
                    Throwable thrown = null;
                    boolean cancelled = false;
                    try {
                        value = get();
                    } catch (ExecutionException e) {
                        thrown = e.getCause();
                    } catch (CancellationException e) {
                        cancelled = true;
                    } catch (InterruptedException consumed) {
                    } finally {
                        onCompletion(value, thrown, cancelled);
                    }
                };
            });
        }
    }
    protected void setProgress(final int current, final int max) {
        GuiExecutor.instance().execute(new Runnable() {
            public void run() { onProgress(current, max); }
        });
    }
    // Called in the background thread
    protected abstract V compute()  throws Exception;
    // Called in the event thread
    protected void onCompletion(V result, Throwable exception,
                                     boolean cancelled)  { }
    protected void  onProgress(int current, int max)  { }
    // Other Future methods forwarded to computation
}

9.3.3SwingWorker

The framework built above — FutureTask plus an Executor plus an event-thread hand-off — applies to any single-threaded GUI framework, not just Swing. In Swing, most of it ships in SwingWorker, which provides cancellation, completion notification and progress indication. Versions have been published in The Swing Connection and The Java Tutorial, and an updated version is included in Java 6. Prefer it in new code; know how it is built, because you will meet home-grown equivalents in every Swing codebase written before 2007.

9.4Shared Data Models

Everything so far assumed the data lives in the presentation objects. The moment a database, file system or remote service is behind the table, more than one thread touches the data and the single-thread rule starts to cost something.

Swing presentation objects — including data models such as TableModel and TreeModel — are confined to the event thread. In simple programs all mutable state is in the presentation objects and the only other thread is the main thread, so enforcing the rule is easy: don't touch the model from main. More complicated programs use other threads to move data to and from a persistent store so as not to compromise responsiveness.

In the simplest case the model's data is entered by the user or loaded once at startup, and no thread but the event thread ever touches it. But sometimes the presentation model is only a view onto another data source — a database, a file system, a remote service — and then several threads touch the data as it moves in and out of the application.

The example that motivates the whole section

A tree control displaying the contents of a remote file system. Enumerating the whole file system before showing the tree would take too much time and memory, so the tree is populated lazily as nodes are expanded. Enumerating even one directory on a remote volume can take a long time, so the enumeration belongs in a background task. When it completes, the data has to get into the tree model somehow: a thread-safe tree model, a invokeLater hand-off from the background task, or the event thread polling for availability.

9.4.1Thread-safe data models

As long as responsiveness is not unduly hurt by blocking, multiple threads can simply share a thread-safe data model. If the model supports fine-grained concurrency, the event thread and background threads share it without responsiveness problems — DelegatingVehicleTracker (Ch. 4, p. 65) uses a ConcurrentHashMap whose retrieval operations offer a high degree of concurrency.

The downside is that such a model does not offer a consistent snapshot of the data, which may or may not be a requirement. And a thread-safe model must still generate change events so that views update.

Sometimes thread safety, consistency and responsiveness are all achievable with a versioned data model such as CopyOnWriteArrayList. An iterator obtained from a copy-on-write collection traverses the collection as it existed when the iterator was created — a stable snapshot by construction. But copy-on-write performs well only when traversals greatly outnumber modifications, which is probably not true of, say, a vehicle-tracking application where every vehicle moves. More specialised versioned structures avoid the restriction, but building one that is both efficiently concurrent and does not retain old versions longer than needed is not easy; consider it only when other approaches are impractical.

9.4.2Split data models

From the GUI's point of view, TableModel and TreeModel are the official repository for data to be displayed. But these model objects are often themselves views of objects managed by the application. A program with both a presentation-domain and an application-domain model is said to have a split-model design (Fowler, 2005).

🖥️
Presentation model

Confined to the event thread, exactly like any other Swing model. It holds only what is on screen and needs no synchronization at all.

🗄️
Shared model

Thread-safe, touched by both the event thread and application threads. It holds the real domain state and publishes change notifications.

🔔
The wire between them

The presentation model registers listeners on the shared model; each update either carries a snapshot of the relevant state or tells the presentation model to re-read it.

The snapshot approach is simple and works well when the model is small, updates are infrequent, and the two models have a similar shape. When the data is large, updates are frequent, or one side holds information the other cannot see, it is more efficient to send incremental updates instead. That has the effect of serialising updates on the shared model and replaying them in the event thread against the presentation model — and finer-grained information about what changed improves perceived quality: if one vehicle moves, repaint the affected region, not the whole display.

🧭

Choose a split-model design when a data model must be shared by more than one thread and a thread-safe data model would be inadvisable because of blocking, consistency, or complexity. That is the decision rule the chapter gives, and it is the one to quote in a design review.

9.5Other Forms of Single-threaded Subsystems

Thread confinement is not a GUI technique. It is the general answer to "this thing is not thread-safe and never will be".

Thread confinement can be used whenever a facility is implemented as a single-threaded subsystem. Sometimes it is forced on you for reasons that have nothing to do with avoiding synchronization or deadlock: some native libraries require that all access — including System.loadLibrary — be made from the same thread.

Borrowing the approach taken by GUI frameworks, you can create a dedicated thread or single-threaded executor for accessing the library, and provide a proxy that intercepts calls to the thread-confined object and submits them as tasks to that thread. Future and newSingleThreadExecutor make this easy: the proxy submits the task and immediately calls Future.get to wait for the result. If the confined class implements an interface, dynamic proxies can automate the whole thing — every method becomes "submit a Callable, wait for the result".

The general pattern: confine, then hand off

  1. Pick the one thread that is allowed to touch the object.
  2. Give that thread a work queue — an Executor is the queue.
  3. Every caller submits a task and, if it needs an answer, waits on the returned Future.
  4. Never let the confined object's references escape to another thread; only tasks cross the boundary.

The event dispatch thread is exactly this pattern with a toolkit attached. That is why GuiExecutor could be written in nine lines — and why the same nine lines work for a native library, a document model, or any other "must be single-threaded" resource.

The chapter's Summary. GUI frameworks are nearly always implemented as single-threaded subsystems in which all presentation-related code runs as tasks in an event thread. Because there is only a single event thread, long-running tasks can compromise responsiveness and so should be executed in background threads. Helper classes like SwingWorker — or the BackgroundTask class built here — which support cancellation, progress indication and completion indication, can simplify the development of long-running tasks that have both GUI and non-GUI components.

§Patterns worth stealing

The eight listings above are the book's. These two turn them into the helpers a Swing codebase actually needs: a checked hand-off, and a cancellable task with progress that cannot forget to clean up.

1Assert the thread, don't hope for it

PATTERN On-EDT assertion, safe hand-off, and a synchronous call that refuses to deadlock 
public final class Edt {
    private Edt() { }

    /** Fail fast: a violated single-thread rule shows up at the call site. */
    public static void checkOnEdt() {
        if (!SwingUtilities.isEventDispatchThread())
            throw new IllegalStateException(
                    "must be called on the EDT, but was " +
                    Thread.currentThread().getName());
    }

    /** From any thread: run later on the EDT. Never blocks. */
    public static void later(Runnable task) {
        if (SwingUtilities.isEventDispatchThread())
            task.run();                 // already there: queueing would invert order
        else
            SwingUtilities.invokeLater(task);
    }

    /**
     * From a background thread only: run on the EDT and wait for the result.
     * Calling it ON the EDT would wait for an event that can never be
     * dispatched -- an instant, guaranteed deadlock.
     */
    public static <T> T call(Callable<T> body)
            throws Exception {
        if (SwingUtilities.isEventDispatchThread())
            throw new IllegalStateException("call() on the EDT deadlocks");
        FutureTask<T> f = new FutureTask<T>(body);
        SwingUtilities.invokeLater(f);
        try {
            return f.get();
        } catch (ExecutionException e) {
            Throwable cause = e.getCause();
            if (cause instanceof Exception) throw (Exception) cause;
            if (cause instanceof Error) throw (Error) cause;
            throw e;
        }
    }
}

2A background task that cannot leak its state

PATTERN Cancellable, progress-reporting task whose completion always lands on the EDT 
public abstract class GuiJob<V> implements Runnable {
    private final AtomicInteger progress = new AtomicInteger();
    private final FutureTask<V> task = new FutureTask<V>(
            new Callable<V>() {
                public V call() throws Exception { return compute(); }
            }) {
        @Override protected void done() {                 // runs on the pool thread
            Edt.later(new Runnable() {
                public void run() { finish(); }           // ... hop to the EDT
            });
        }
    };

    /** Background thread. Poll isCancelled() rather than the interrupt flag. */
    protected abstract V compute() throws Exception;

    /** EDT. Called exactly once, whatever happened -- success, failure, cancel. */
    protected abstract void onDone(V value, Throwable failure, boolean cancelled);

    protected void onProgress(int done, int total) { }

    /** Background thread; the UI update is marshalled, not performed here. */
    protected final void report(int done, int total) {
        if (progress.getAndSet(done) != done)
            Edt.later(new Runnable() {
                public void run() { onProgress(done, total); }
            });
    }

    public final boolean isCancelled() { return task.isCancelled(); }

    public final void cancel() { task.cancel(true); }      // interrupts compute()

    public final void run() { task.run(); }                // submit to backgroundExec

    private void finish() {
        V value = null;
        Throwable failure = null;
        boolean cancelled = false;
        try {
            value = task.get();
        } catch (ExecutionException e) {
            failure = e.getCause();
        } catch (CancellationException e) {
            cancelled = true;
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();            // must be on the EDT: never expected
            return;
        } finally {
            onDone(value, failure, cancelled);             // ordering preserved: onDone runs last
        }
    }
}
💡

The two patterns answer the two questions every Swing codebase eventually asks: "am I allowed to touch this here?" (checkOnEdt) and "did I remember to put the UI back?" (a single onDone that is called on success, failure and cancellation). Both failures are invisible in manual testing and obvious in a stack trace or a stuck button.

The one habit

For every listener, ask two questions: how long can this run? and which thread am I on when I touch the UI? A handler that answers "long" and "the EDT" is a bug report waiting for a user to file it.

Five questions the chapter leaves you with

  1. Which of my listeners can block — and what is the worst-case duration of each?
  2. When a background task ends, what exactly puts the UI back into a consistent state, on which thread?
  3. Can the user cancel the long operation, and does the code notice within a reasonable time?
  4. Is my table/tree model shared with any other thread, and if so, which of the three strategies (thread-safe, versioned, split) did I choose on purpose?
  5. If the EDT were frozen for ten seconds right now, would any of my logs tell me which handler did it?
