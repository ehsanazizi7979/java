Spring in the real world

Spring is a toolbox that handles common application plumbing, so you can focus on what your application actually does.

THE KEY IDEAS

  • Why a framework? Applications repeatedly need object management, web requests, database access, and tests. A framework gives these jobs a consistent structure instead of making you build everything from scratch.
  • Inversion of control: rather than your code constructing and coordinating every object, Spring creates and connects selected objects for you. Your code supplies the parts; Spring manages their wiring.
  • Spring is an ecosystem. Spring Core provides the container and aspects; Spring MVC handles web requests; Spring Data helps with persistence; Spring Boot supplies convenient defaults and dependency starters.
  • It is not only for websites. The same ideas can help in backend services, test utilities, and other Java applications.
  • Choose deliberately. A framework adds dependencies and a learning curve. A very small program, strict footprint requirements, or an already suitable solution may not need it.
✳

Remember
Think of Spring as the workshop infrastructure, not the product you are building.

The Spring context: Defining beans

A bean is an object that Spring knows about and manages inside its application context.

THE KEY IDEAS

  • The context is a container. Plain objects you create with new do not automatically become Spring beans. Only objects registered with the container receive Spring’s management.
  • Use @Bean on a configuration method when you want explicit control over creating an object, including objects from a third-party library.
  • Use @Component and component scanning for your own classes. Spring finds annotated classes and creates their beans; specialized stereotypes include @Service and @Repository.
  • Register programmatically with the context when you need conditional or dynamic registration. It is useful, but not the usual first choice for ordinary application classes.
  • Names and types matter. Spring can look up a bean by type or name; when several beans share a type, the injection point may need a qualifier or a primary choice.
✳

Remember
If Spring is supposed to inject or enhance an object, make sure that object is a bean.

ILLUSTRATIVE EXAMPLE

Two common ways to register an object; use either approach for the same bean, not both.

Java
@Configuration
class AppConfig {
    @Bean
    Parrot parrot() {
        return new Parrot();
    }
}

// Alternatively, annotate your own class and scan its package:
@Component
class Parrot { }

The Spring context: Wiring beans

Dependency injection means Spring supplies one object with the other objects it needs.

THE KEY IDEAS

  • A dependency is a helper. If a person has a parrot, the person object needs a reference to the parrot object. Both can be beans and Spring can connect them.
  • Constructor injection makes required dependencies explicit and allows fields to be final. A class with one constructor generally does not need @Autowired on it.
  • Other options: Spring can supply @Bean method parameters, fields, or setters. Constructor injection is usually easier to test and avoids partially initialized objects.
  • Resolve ambiguity. If several beans match an interface or type, mark a default with @Primary or choose a named bean with @Qualifier.
  • Avoid circular dependencies. If A needs B to be constructed and B needs A, neither can be constructed first. Redesign the responsibilities rather than hiding the cycle.
✳

Remember
Ask for the dependency you need; let Spring supply the matching bean.

ILLUSTRATIVE EXAMPLE

Spring injects the specifically named parrot through the constructor.

Java
@Component
class Person {
    private final Parrot parrot;

    Person(@Qualifier("parrot2") Parrot parrot) {
        this.parrot = parrot;
    }
}
CHAPTER 04PDF page 99 ↗

The Spring context: Using abstractions

An interface describes what a helper can do without tying its caller to one particular implementation.

THE KEY IDEAS

  • Separate the contract from the implementation. A printer can ask for a Sorter without knowing whether it sorts by address or by name.
  • Loose coupling makes change easier. You can replace a real implementation with a different one or with a test double without rewriting the caller.
  • Spring can inject an interface. The actual bean must be a concrete class that implements that interface; the interface itself is not instantiated.
  • Choose among implementations with @Primary or @Qualifier when more than one bean satisfies the same contract.
  • Name responsibilities clearly. @Service identifies business logic and @Repository identifies persistence logic. These are specialized component stereotypes.
✳

Remember
Depend on what the helper does, not on how it does it.

ILLUSTRATIVE EXAMPLE

The printer depends on a contract; Spring supplies an implementation.

Java
interface Sorter {
    void sortDetails();
}

@Service
class DeliveryDetailsPrinter {
    private final Sorter sorter;

    DeliveryDetailsPrinter(Sorter sorter) {
        this.sorter = sorter;
    }
}

The Spring context: Bean scopes and life cycle

A bean’s scope decides how long an instance lives and when Spring creates another one.

THE KEY IDEAS

  • Singleton is the default. Spring normally keeps one instance per bean definition and application context—not necessarily one instance for the entire Java process.
  • Singletons are shared. Multiple requests may use the same instance at once. Prefer stateless or immutable services, or protect shared mutable state against races.
  • Prototype means a fresh instance per lookup. It is useful when a new object is needed for each task, but the caller must consider any cleanup the object needs.
  • Eager versus lazy: singleton beans are normally created at startup; @Lazy can defer creation until first use. Laziness moves startup failures to a later time.
  • Watch mixed scopes. Injecting a prototype directly into a singleton resolves it once when the singleton is created. Use a provider when the singleton needs a fresh prototype for each operation.
✳

Remember
Scope is about ownership and lifetime; it does not automatically make mutable objects thread-safe.

ILLUSTRATIVE EXAMPLE

A provider requests a new prototype each time the method is called.

Java
@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
class TaskState { }

@Service
class TaskService {
    private final ObjectProvider<TaskState> states;
    TaskService(ObjectProvider<TaskState> states) {
        this.states = states;
    }
    TaskState newState() { return states.getObject(); }
}

Using aspects with Spring AOP

An aspect adds shared behavior around selected method calls without mixing it into every business method.

THE KEY IDEAS

  • Cross-cutting work includes timing, logging, transactions, and some security checks. Keeping it separate can make business code easier to read.
  • Advice is the extra behavior; a pointcut describes which methods receive it. @Before, @AfterReturning, @AfterThrowing, and @Around run at different times.
  • Around advice controls the call. It normally calls proceed() to continue, and can observe arguments, results, or exceptions. Forgetting to proceed skips the original method.
  • Spring usually uses proxies. Calls that do not pass through the proxy, such as a method calling another method on the same object, may bypass advice.
  • Use aspects sparingly. Hidden behavior can make an application harder to understand. When several aspects apply, define their order if it affects the result.
✳

Remember
An aspect is like a wrapper around a method—not a replacement for clear business logic.

ILLUSTRATIVE EXAMPLE

A small timing aspect; the service package in the pointcut is an example.

Java
@Aspect
@Component
class TimingAspect {
    @Around("execution(* example.service.*.*(..))")
    Object time(ProceedingJoinPoint call) throws Throwable {
        long start = System.nanoTime();
        try {
            return call.proceed();
        } finally {
            System.out.println(System.nanoTime() - start);
        }
    }
}

Understanding Spring Boot and Spring MVC

Spring Boot gets a web application running with sensible defaults; Spring MVC routes requests to your code.

THE KEY IDEAS

  • Client and server have different jobs. A browser sends an HTTP request; the backend processes it and sends an HTTP response.
  • A servlet container such as Tomcat handles the HTTP connection and passes requests to the Java application. Boot can run one embedded inside the app.
  • Boot starters collect related dependencies, and auto-configuration creates useful components when appropriate. You can override defaults when your application needs something different.
  • Spring MVC (model–view–controller) uses a dispatcher to find the controller method for a request. A regular @Controller can return the name of an HTML view.
  • Start small. A Boot entry point, a web starter, a controller, and a view template are enough to see the basic request–response flow.
✳

Remember
Boot sets up the web machinery; MVC directs the request to the right controller.

ILLUSTRATIVE EXAMPLE

A minimal Boot entry point and a controller that chooses a view.

Java
@SpringBootApplication
class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

@Controller
class HomeController {
    @GetMapping("/home")
    String home() { return "home"; }
}
CHAPTER 08PDF page 200 ↗

Implementing web apps with Spring Boot and Spring MVC

A dynamic page is a template filled with data that the controller prepares for a particular request.

THE KEY IDEAS

  • The controller builds a model. It adds values to a Model and returns a view name. A template engine such as Thymeleaf combines the template and model into HTML.
  • Inputs can come from the URL. @RequestParam reads a query parameter such as ?name=Ana; @PathVariable reads a required part of the path such as /products/7.
  • HTTP methods communicate intent. GET retrieves; POST usually creates or submits; PUT replaces, PATCH partially updates, and DELETE removes. Do not change server state in a GET handler.
  • Forms usually submit GET or POST. A POST handler can read submitted fields and pass them to a service. Use validation and, for browser forms, appropriate CSRF protection.
  • Keep responsibilities separate. The controller handles web input and output; a service handles business rules instead of putting all behavior in the template or controller.
✳

Remember
The template is the page’s shape; the model is the data that fills it.

ILLUSTRATIVE EXAMPLE

The query parameter becomes data that the view can display.

Java
@GetMapping("/greeting")
String greet(@RequestParam(defaultValue = "friend") String name,
             Model model) {
    model.addAttribute("name", name);
    return "greeting"; // e.g., templates/greeting.html
}
CHAPTER 09PDF page 223 ↗

Using the Spring web scopes

Web scopes let a bean’s lifetime follow a request, a user session, or the web application.

THE KEY IDEAS

  • Request scope: a new instance is associated with each HTTP request. It is useful for short-lived request-specific information.
  • Session scope: one instance is associated with an HTTP session and can hold data across that session’s requests, such as a small shopping cart.
  • Application scope: an instance is shared at the servlet-application level. Shared mutable data can be accessed concurrently and needs careful coordination.
  • Session data is not automatically safe. A user can send simultaneous requests; mutable session state can race. Sessions also complicate scaling and failover between servers.
  • Use the smallest practical lifetime. Avoid unnecessarily storing sensitive or large objects in memory; use durable storage when data must survive a session or restart.
✳

Remember
Request = one interaction; session = one conversation; application = shared by everyone.

ILLUSTRATIVE EXAMPLE

Spring creates a request-scoped object for each HTTP request.

Java
@Component
@RequestScope
class RequestInfo {
    private String message;
    // getters and setters
}

Implementing REST services

A REST endpoint lets a client exchange data with a backend, commonly using JSON rather than an HTML view.

THE KEY IDEAS

  • REST (representational state transfer) is a way to design services around resources and standard HTTP operations. An endpoint is a URL and operation that clients can call.
  • @RestController makes return values response bodies. Spring’s HTTP message converters can turn a Java object into JSON and JSON back into a Java object.
  • Read input from the right place. Use path variables or query parameters for URL data and @RequestBody for structured request content.
  • Set a useful response. ResponseEntity can set the body, status, and headers—for example, 201 Created after creating a resource.
  • Handle failures consistently. @RestControllerAdvice and @ExceptionHandler can translate errors into clear API responses without repeating code in each controller.
  • Validate and protect input. A JSON parser does not make input trustworthy; check required fields and apply authentication and authorization when necessary.
✳

Remember
An HTML controller chooses a page; a REST controller normally returns data.

ILLUSTRATIVE EXAMPLE

The request body becomes a Product; the response contains the saved product.

Java
@RestController
class ProductController {
    private final ProductService products;
    ProductController(ProductService products) {
        this.products = products;
    }

    @PostMapping("/products")
    ResponseEntity<Product> add(@RequestBody Product product) {
        Product saved = products.save(product);
        return ResponseEntity.status(HttpStatus.CREATED).body(saved);
    }
}
CHAPTER 11PDF page 269 ↗

Consuming REST endpoints

A Spring application can also act as a client and call another application’s HTTP API.

THE KEY IDEAS

  • Client versus server is a role. A payment service may serve a request from your app while your app is simultaneously serving a request from a browser.
  • OpenFeign lets you describe an HTTP client with an interface and annotations. Spring Cloud supplies the implementation when the Feign integration is enabled.
  • RestTemplate is the older synchronous client shown in the book. WebClient supports reactive, nonblocking use. Modern Spring also offers RestClient for synchronous calls.
  • Handle the network as unreliable. Configure timeouts, handle error responses, and be careful with retries: repeating a payment request can create a duplicate unless the operation is designed for it.
  • Keep remote details at the edge. A client or proxy class should handle URLs, headers, and conversion so business services do not need to know the HTTP mechanics.
✳

Remember
Treat another service like an outside dependency that can be slow, unavailable, or return an error.

ILLUSTRATIVE EXAMPLE

A declarative payment client. It also needs the OpenFeign dependency and client scanning.

Java
@FeignClient(name = "payments", url = "${payment.url}")
interface PaymentClient {
    @PostMapping("/payment")
    Payment create(@RequestBody Payment payment);
}
CHAPTER 12PDF page 288 ↗

Using data sources in Spring apps

A data source supplies database connections; JdbcTemplate makes common SQL operations easier to write.

THE KEY IDEAS

  • JDBC (Java Database Connectivity) is the Java database interface. The JDK defines the API, and a database-specific JDBC driver implements the connection to a particular database.
  • A connection pool reuses connections. Spring Boot commonly configures HikariCP when the required dependencies and database settings are present. Reuse avoids opening a new connection for every operation.
  • JdbcTemplate handles routine JDBC work. Use update for changes and query with a row mapper for results.
  • Use parameters, not string concatenation. Placeholders such as ? keep data separate from SQL and help prevent SQL injection.
  • Configure connections safely. Set the URL and credentials through application configuration or a custom DataSource; keep real secrets out of source control. Multiple databases require clearly identified beans.
✳

Remember
DataSource manages connections; JdbcTemplate uses them to run SQL.

ILLUSTRATIVE EXAMPLE

The question marks are parameters, not text pasted into the SQL.

Java
jdbcTemplate.update(
    "INSERT INTO purchase (product, price) VALUES (?, ?)",
    productName, price
);

List<String> names = jdbcTemplate.query(
    "SELECT product FROM purchase",
    (rs, rowNumber) -> rs.getString("product")
);

Using transactions in Spring apps

A transaction groups related database changes so they can succeed together or be rolled back together.

THE KEY IDEAS

  • Why it matters: a transfer must not subtract money from one account if adding it to the other fails. Partial changes can leave data inconsistent.
  • Commit or rollback. A successful transaction commits its changes; a rollback discards changes made within that transaction, subject to the database and transaction manager.
  • @Transactional marks a method or class for transaction management. Spring normally wraps calls through a proxy and begins or joins a transaction.
  • Know the defaults. By default Spring rolls back on unchecked exceptions and errors, not every checked exception. Configure rollback rules when the use case requires them.
  • Mind the boundaries. Self-invocation can bypass proxy advice, and a database transaction cannot automatically undo an external email or HTTP call. Concurrency and isolation also matter for money transfers.
✳

Remember
A transaction is an all-or-nothing boundary for the database operations it actually manages.

ILLUSTRATIVE EXAMPLE

Both repository operations run inside the transaction when called through the Spring proxy.

Java
@Transactional
public void transfer(long from, long to, BigDecimal amount) {
    accounts.debit(from, amount);
    accounts.credit(to, amount);
}
CHAPTER 14PDF page 326 ↗

Implementing data persistence with Spring Data

Spring Data lets you express common persistence operations as repository interfaces instead of hand-writing every implementation.

THE KEY IDEAS

  • Pick the right module. Spring Data JDBC, JPA, and MongoDB are different modules for different persistence technologies; their behavior and supported query syntax differ.
  • Extend a repository contract. CrudRepository supplies common create, read, update, and delete operations. Paging and sorting interfaces add other capabilities; exact inheritance varies by version.
  • Spring supplies the implementation. Your interface describes the operations, and the framework creates a repository bean for it.
  • Add queries in two ways: a method name such as findByName can be translated into a query, or an explicit @Query can state the query directly.
  • Keep queries understandable. Very long derived names are hard to read. Test the generated or explicit query, and use the correct module’s annotations for modifying queries.
✳

Remember
A repository is the application’s dedicated doorway to stored data.

ILLUSTRATIVE EXAMPLE

Spring Data JDBC can create this repository implementation from the interface.

Java
interface AccountRepository extends CrudRepository<Account, Long> {
    List<Account> findByName(String name);

    @Query("SELECT * FROM account WHERE name = :name")
    List<Account> findAccounts(@Param("name") String name);
}
CHAPTER 15PDF page 347 ↗

Testing your Spring app

Tests check that your code behaves as expected today and continues to do so after changes.

THE KEY IDEAS

  • Unit tests check one small piece of logic in isolation. They are usually fast and make failures easier to locate.
  • Integration tests check how components work together—for example, a Spring controller, its configuration, and a database. They catch wiring and configuration problems unit tests can miss.
  • Mocks are controlled stand-ins for dependencies. Use them to focus a test, but do not assume a mocked dependency proves the real integration works.
  • Arrange, act, assert. Set up the scenario, perform one action, then verify the result. Include both happy paths and meaningful error or boundary cases.
  • Run tests repeatedly. Automated tests in a build or continuous-integration pipeline give quick feedback when application code or dependencies change.
✳

Remember
Use fast unit tests for logic and focused integration tests for the connections between pieces.

ILLUSTRATIVE EXAMPLE

A focused unit-test sketch using a mocked repository and JUnit assertions.

Java
@Test
void missingAccountIsReported() {
    when(accounts.findById(42L)).thenReturn(Optional.empty());

    assertThrows(AccountNotFoundException.class,
                 () -> service.findAccount(42L));
}

Security today

Security is not a single login screen: it is a set of protections built into the whole system from the beginning.

THE KEY IDEAS

  • Authentication asks “Who are you?” Authorization asks “What are you allowed to do?” An identified user is not automatically allowed to access everything.
  • Use layers. Network controls, secure configuration, authentication, authorization, data protection, and monitoring each address different risks. One layer should not be the only defense.
  • Protect confidentiality, integrity, and availability. Data should be visible only to permitted people, resistant to improper changes, and available when needed.
  • Think like an attacker. Identify valuable assets, possible entry points, and likely abuse cases before choosing controls.
  • Small leaks matter. Passwords, tokens, and personal information can escape through logs, error messages, or exposed configuration. Keep secrets out of all three.
✳

Remember
Make security part of the design, not a feature added just before release.

CHAPTER 02PDF page 40 ↗

Hello, Spring Security

Spring Security intercepts requests, authenticates the caller, and applies rules before allowing access.

THE KEY IDEAS

  • Adding the security dependency changes defaults. A basic Spring Boot app is protected by default, with a development user and generated password under the usual auto-configuration conditions.
  • The filter chain is the entry point. Security filters inspect requests before they reach controller methods.
  • Authentication has separate jobs. An authentication manager delegates to a provider; user details and password encoders can help the provider check credentials.
  • The security context holds the resulting authentication information so later code can make authorization decisions.
  • Customize with a SecurityFilterChain bean. Choose authentication methods and rules explicitly; development defaults and sample users are not a production identity system.
✳

Remember
The request is checked before the controller handles it.

ILLUSTRATIVE EXAMPLE

Require authentication for /hello and deny other requests. Use HTTP Basic only over TLS.

Java
@Bean
SecurityFilterChain security(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
            .requestMatchers("/hello").authenticated()
            .anyRequest().denyAll())
        .httpBasic(Customizer.withDefaults());
    return http.build();
}

CHAPTER 03PDF page 68 ↗

Managing users

Spring Security needs a consistent description of a user and a way to look that user up.

THE KEY IDEAS

  • UserDetails describes security information such as a username, password hash, authorities, and account status. A GrantedAuthority represents one permission or role-like string.
  • UserDetailsService finds a user by username. The authentication provider can use the result while checking a login.
  • UserDetailsManager adds user-management operations such as creating, updating, and deleting users.
  • Implementations differ. In-memory users are convenient for learning or tests; JDBC and LDAP-backed approaches are available for users managed outside application memory.
  • Separate concerns. Your application’s user record may contain profile data, but authentication should only expose the details needed for security. Protect stored password hashes and account data.
✳

Remember
UserDetails describes a user; UserDetailsService explains how to find one.

ILLUSTRATIVE EXAMPLE

A small in-memory demo; supply the password from configuration and define a PasswordEncoder separately.

Java
@Bean
UserDetailsService users(PasswordEncoder encoder,
                         @Value("${demo.password}") String password) {
    UserDetails user = User.withUsername("alex")
        .password(encoder.encode(password))
        .authorities("report:read")
        .build();
    return new InMemoryUserDetailsManager(user);
}
CHAPTER 04PDF page 93 ↗

Managing passwords

A password should be checked against a slow, salted password hash—not stored or compared as plain text.

THE KEY IDEAS

  • PasswordEncoder has two main jobs: encode a new password and check a supplied password with matches. You do not decrypt a password hash.
  • Use a password-specific algorithm. Adaptive algorithms such as bcrypt, scrypt, or Argon2 are designed to make password guessing expensive. Choose parameters suitable for your system.
  • DelegatingPasswordEncoder records an algorithm identifier such as {bcrypt} with the stored hash. This helps verify older hashes while upgrading encoding strategies over time.
  • Do not use no-op encoding in production. It stores passwords without protection. Do not invent your own cryptographic algorithm or treat a fast general-purpose hash as a password-storage solution.
  • Encryption is different from hashing. Encryption is reversible with a key and is useful for secrets an application must recover. Key generation, storage, and rotation must be handled securely.
✳

Remember
Store a strong password hash, verify with matches, and keep encryption keys separate from encrypted data.

ILLUSTRATIVE EXAMPLE

The delegating encoder selects a password-storage strategy and can recognize tagged hashes.

Java
@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

// When creating a user: encoder.encode(rawPassword)
// When checking a login: encoder.matches(rawPassword, storedHash)

A web app’s security begins with filters

A filter chain is a series of checkpoints that can inspect a request and decide whether to pass it onward.

THE KEY IDEAS

  • Order matters. A filter may run before or after authentication, so it sees different information depending on its position.
  • Each filter can continue the chain or stop processing and return a response. A filter that forgets to continue can prevent the controller from running.
  • Customize only when needed. Spring supplies many filters. Add a custom one before, after, or at the position of an existing filter when a built-in option does not meet the requirement.
  • Avoid ambiguous order. Placing multiple custom filters at the same position does not guarantee their relative order.
  • Never log secrets. Request logs and audit events should not contain passwords, authorization headers, access tokens, or unnecessary personal data.
✳

Remember
Think of filters as ordered security checkpoints on the way to a controller.

ILLUSTRATIVE EXAMPLE

Place an existing custom filter before the username/password authentication filter.

Java
http.addFilterBefore(
    auditFilter,
    UsernamePasswordAuthenticationFilter.class
);
CHAPTER 06PDF page 126 ↗

Implementing authentications

An AuthenticationProvider checks a particular kind of credential and produces an authenticated identity.

THE KEY IDEAS

  • Authentication represents an authentication request or result. The manager delegates to a provider that supports the presented authentication type.
  • Keep responsibilities separate. A provider can use a UserDetailsService to find users and a PasswordEncoder to verify passwords rather than implementing every job itself.
  • The security context stores the result. It can be read later to identify the caller, but an anonymous authentication can also appear; use authorization rules to enforce access.
  • Thread boundaries matter. The context is normally thread-local in servlet applications. Work sent to another thread may need Spring’s delegating security-context wrappers; do not assume it is automatically copied everywhere.
  • Choose a login mechanism. HTTP Basic sends credentials with requests and requires TLS; form login provides a browser login flow, typically with a session. Customize these carefully rather than writing ad hoc checks.
✳

Remember
The provider checks identity; the security context carries the result for later decisions.

ILLUSTRATIVE EXAMPLE

Read the current authentication; it may represent an anonymous caller.

Java
Authentication authentication =
    SecurityContextHolder.getContext().getAuthentication();

if (authentication != null) {
    String currentName = authentication.getName();
}
PART 03

Authorization

06 CHAPTERS
CHAPTER 07PDF page 162 ↗

Configuring endpoint-level authorization: Restricting access

After identifying a caller, authorization decides which actions that caller may perform.

THE KEY IDEAS

  • Authorities are permissions. For example, report:read can represent permission to read reports. Grant only what the user or service needs.
  • Roles are a common grouping convention. In Spring Security, hasRole("ADMIN") normally checks for the authority ROLE_ADMIN; hasAuthority checks the exact string.
  • Different rules express different intentions. authenticated() requires an authenticated caller; permitAll() allows access without requiring login; denyAll() denies it.
  • Authentication is not authorization. A valid login should still receive a forbidden response when it lacks the required permission.
  • Start from least privilege. Make public endpoints intentional and deny or require authentication for everything else rather than accidentally exposing new routes.
✳

Remember
A valid ID proves who someone is; it does not give them every key.

ILLUSTRATIVE EXAMPLE

Check a role or an exact authority; the role check uses the ROLE_ convention.

Java
auth.requestMatchers("/admin/**").hasRole("ADMIN")
    .requestMatchers("/reports/**").hasAuthority("report:read")
    .anyRequest().denyAll();
CHAPTER 08PDF page 181 ↗

Configuring endpoint-level authorization: Applying restrictions

Request matchers decide which security rule applies to a path, an HTTP method, or a more specific request pattern.

THE KEY IDEAS

  • Match the request you mean. requestMatchers can select paths such as /reports/** and can also restrict a rule to a method such as GET.
  • Order the rules carefully. Spring uses the first matching authorization rule, so put specific patterns before broad ones and finish with a deliberate anyRequest() rule.
  • Different methods can need different permissions. Reading a report and deleting it should not automatically require the same access.
  • Regular-expression matchers can express patterns that simple path matching cannot, but they are easier to get wrong. Test both matching and nonmatching paths.
  • Protect new endpoints by default. A final denyAll() makes an unlisted route inaccessible until someone deliberately adds a rule.
✳

Remember
Specific rules first, a safe catch-all last.

ILLUSTRATIVE EXAMPLE

Different requests receive different rules; unlisted requests are denied.

Java
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/public/**").permitAll()
    .requestMatchers(HttpMethod.GET, "/reports/**")
        .hasAuthority("report:read")
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .anyRequest().denyAll());
CHAPTER 09PDF page 200 ↗

Configuring CSRF protection

Cross-site request forgery tricks a browser into sending an unwanted request with credentials it automatically includes.

THE KEY IDEAS

  • The attack: a user is signed in to a trusted site, then visits a malicious site that causes their browser to send an unwanted action to the trusted site.
  • The risk exists with automatically sent credentials, especially session cookies and sometimes browser-managed HTTP Basic credentials. The server may otherwise mistake the forged request for an intentional one.
  • CSRF tokens add a check. The legitimate application includes a token with a state-changing request; Spring checks it against the expected token. CSRF protection is enabled by default in standard servlet security.
  • Use safe HTTP methods correctly. GET should not change state. Send a CSRF token with protected POST, PUT, PATCH, and DELETE requests or forms.
  • Customize carefully. Token repositories and request handlers control storage and presentation. Disable protection only after analyzing the authentication and client model—not just to make a failing POST work.
✳

Remember
CORS and CSRF are different: allowing a browser origin does not replace CSRF protection.

ILLUSTRATIVE EXAMPLE

A server-rendered form can include Spring’s CSRF token as a hidden field.

HTML
<form action="/transfer" method="post">
  <input type="hidden" th:name="${_csrf.parameterName}"
         th:value="${_csrf.token}">
  <button type="submit">Transfer</button>
</form>
CHAPTER 10PDF page 224 ↗

Configuring CORS

Cross-origin resource sharing (CORS) tells a browser when a page from one origin may read responses from another origin.

THE KEY IDEAS

  • An origin is scheme, host, and port. For example, https://app.example.com and https://api.example.com are different origins.
  • The browser enforces the rules. A server opts in with response headers; for some requests the browser first sends an OPTIONS preflight to ask whether the method and headers are allowed.
  • Configure narrowly. Allow only the origins, methods, and headers your frontend needs. For credentialed requests, use specific trusted origins rather than a wildcard.
  • Spring offers local and central configuration. Use @CrossOrigin on a controller or configure CORS centrally and integrate it with the security filter chain.
  • CORS is not authorization. It does not stop non-browser clients, and some cross-origin requests can be sent even when their responses cannot be read. Keep access controls and CSRF defenses in place.
✳

Remember
CORS governs browser cross-origin access; it is not a general-purpose security boundary.

ILLUSTRATIVE EXAMPLE

Allow one known browser origin for this endpoint.

Java
@CrossOrigin(origins = "https://app.example.com")
@GetMapping("/products")
List<Product> products() {
    return productService.findAll();
}
CHAPTER 11PDF page 234 ↗

Implementing authorization at the method level

Method security protects business operations even when they can be reached through more than one endpoint.

THE KEY IDEAS

  • Enable it explicitly with @EnableMethodSecurity; endpoint rules alone do not automatically protect every service method.
  • @PreAuthorize checks a Spring Expression Language (SpEL) rule before the method runs. Use it for rules such as “only an administrator or the owner may call this.”
  • @PostAuthorize checks the returned value after the method has run. It is unsuitable as the sole protection for a method that has already made side effects.
  • Complex rules deserve their own component. A custom permission evaluator or authorization component can keep ownership rules readable and reusable.
  • Proxy boundaries still matter. Calls inside the same object can bypass proxy-based method security. Test the actual path through the Spring-managed bean.
✳

Remember
Use endpoint rules at the door and method rules near the business operation.

ILLUSTRATIVE EXAMPLE

Enable method security, then allow only users with the ADMIN role.

Java
@Configuration
@EnableMethodSecurity
class MethodSecurityConfig { }

@PreAuthorize("hasRole('ADMIN')")
public void deleteReport(long id) {
    reports.deleteById(id);
}
CHAPTER 12PDF page 260 ↗

Implementing filtering at the method level

Method filtering removes disallowed elements from a collection rather than allowing or denying the whole method call.

THE KEY IDEAS

  • @PreFilter filters supported collection or array arguments before the method executes. filterObject refers to each candidate element in the expression.
  • @PostFilter filters supported returned collections or arrays after the method runs. For example, only documents owned by the current user may remain.
  • Filtering is not call authorization. A method may still run with an empty input or return an empty collection. Combine filtering with preauthorization if the call itself must be denied.
  • Filter as close to the data as possible. Fetching every database row and removing most in memory wastes resources and can break pagination; prefer an ownership condition in the database query.
  • Use appropriate collections and test behavior. Framework filtering can modify the supplied collection; check compatibility with the types and method-security configuration in use.
✳

Remember
Filtering selects which items pass through; authorization can decide whether the call happens at all.

ILLUSTRATIVE EXAMPLE

Illustrative post-filtering; a database query scoped to the owner is often better.

Java
@PostFilter("filterObject.owner == authentication.name")
public List<Document> findDocuments() {
    return documents.findAll();
}
PART 04

OAuth 2 & OpenID Connect

04 CHAPTERS
CHAPTER 13PDF page 282 ↗

What are OAuth 2 and OpenID Connect?

OAuth 2 lets a client obtain limited access to a protected resource; OpenID Connect adds a standardized identity layer.

THE KEY IDEAS

  • Four roles: the resource owner is usually the user; the client is the app seeking access; the authorization server issues tokens; the resource server protects the API or data.
  • An access token is a permission-bearing credential. An opaque token is typically checked through introspection; a JSON Web Token (JWT) can carry claims and be validated locally using a trusted key and appropriate claim checks.
  • Authorization code + PKCE (proof key for code exchange) is a common user-facing flow: the user signs in at the authorization server, the client receives a code, and PKCE helps prevent a stolen code from being redeemed.
  • Scopes describe the requested or granted access. For example, a reports.read scope can limit a token to reading reports.
  • Client credentials is for a client acting on its own behalf, often service-to-service. A refresh token can obtain a new access token without repeating the full user login when the server permits it.
  • OpenID Connect (OIDC) uses OAuth 2 flows and adds an ID token and identity information. An ID token is for the client’s login; do not treat it as an API access token.
  • Tokens need protection. Use TLS, validate redirect URIs, limit scopes and lifetimes, avoid leaking tokens, and protect against replay and CSRF. A signed JWT is not necessarily encrypted.
✳

Remember
OAuth grants scoped access; OIDC tells a client about the signed-in user.

ILLUSTRATIVE EXAMPLE

A client sends the access token to the protected API. Never put a real token in a public example.

HTTP
GET /invoices HTTP/1.1
Host: api.example.com
Authorization: Bearer <access-token>
CHAPTER 14PDF page 300 ↗

Implementing an OAuth 2 authorization server

The authorization server knows which clients and users are allowed to participate and issues the tokens they need.

THE KEY IDEAS

  • Register clients. A RegisteredClientRepository stores client identifiers, authentication methods, allowed grant types, redirect URIs, and scopes.
  • Manage users and consent. User-facing grants also need user authentication and, where appropriate, consent. Client credentials represent the client itself, not an end user.
  • Sign JWTs with protected keys. The authorization server uses private signing keys and can publish public keys as a JSON Web Key (JWK) set for resource servers to validate signatures.
  • Opaque tokens use introspection. A resource server asks the authorization server whether a token is active and what it permits.
  • Plan for revocation. Revocation can immediately affect introspected tokens, but a resource server validating a self-contained JWT locally may not learn of revocation until expiry unless an additional check is used.
  • A sample server is not a production setup. Use HTTPS, secure and durable client/key storage, carefully configured lifetimes, and a well-tested identity solution.
✳

Remember
The authorization server issues credentials; the resource server decides whether to accept them.

ILLUSTRATIVE EXAMPLE

A client-credentials registration sketch. The secret must come from secure configuration.

Java
RegisteredClient client = RegisteredClient
    .withId(UUID.randomUUID().toString())
    .clientId("reports-client")
    .clientSecret(encoder.encode(clientSecret))
    .clientAuthenticationMethod(ClientAuthenticationMethod.CLIENT_SECRET_BASIC)
    .authorizationGrantType(AuthorizationGrantType.CLIENT_CREDENTIALS)
    .scope("reports.read")
    .build();
CHAPTER 15PDF page 322 ↗

Implementing an OAuth 2 resource server

The resource server protects an API and verifies the access token presented by a client.

THE KEY IDEAS

  • For JWTs, obtain trusted public keys from the configured issuer or JWK set and validate the signature, expected issuer, lifetime, and intended audience as appropriate.
  • For opaque tokens, call a trusted introspection endpoint using the resource server’s client credentials. The response tells the server whether the token is active and provides its attributes.
  • Turn claims into permissions. Spring commonly maps OAuth scopes to authorities with the SCOPE_ prefix; rules must match the authorities actually configured.
  • Customization is possible. A converter can map different claims to authorities. An authentication-manager resolver can choose a trusted validation strategy for a multitenant system.
  • Do not trust unverified token contents. In multi-issuer systems, allowlist trusted issuers rather than fetching keys from an arbitrary issuer supplied by a token.
✳

Remember
A token is not trusted just because it looks like a JWT; verify it and enforce the right permissions.

ILLUSTRATIVE EXAMPLE

A JWT resource server rule. Also configure a trusted issuer and any required audience validator.

Java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth
            .requestMatchers("/reports/**")
                .hasAuthority("SCOPE_reports.read")
            .anyRequest().denyAll())
        .oauth2ResourceServer(oauth ->
            oauth.jwt(Customizer.withDefaults()));
    return http.build();
}
CHAPTER 16PDF page 349 ↗

Implementing an OAuth 2 client

An OAuth client requests tokens and uses them to sign users in or call another protected service.

THE KEY IDEAS

  • OAuth/OIDC login redirects the user to an identity provider. After the flow completes, Spring creates an authentication in the application’s security context.
  • Register the client with the provider. Configure its client ID, secret when applicable, scopes, and redirect URI. Common providers have useful built-in defaults; custom providers need their endpoint or issuer details.
  • Use OIDC for identity. The openid scope selects OpenID Connect where supported. Validate the provider configuration and keep credentials in secure configuration.
  • A backend can also be a client. For service-to-service calls, client credentials can obtain an access token without pretending that a human user is present.
  • Let the client manager handle token acquisition. Spring’s OAuth client support can obtain and manage authorized clients so the HTTP-calling code does not reimplement the protocol.
✳

Remember
A client consumes tokens; it is different from the server that issues them or the API that validates them.

ILLUSTRATIVE EXAMPLE

Enable a provider-based login after configuring an OAuth client registration.

Java
http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/", "/login/**").permitAll()
        .anyRequest().authenticated())
    .oauth2Login(Customizer.withDefaults());

Going reactive

01 CHAPTER
CHAPTER 17PDF page 372 ↗

Implementing security in reactive applications

Reactive applications process streams of values asynchronously, so they use the reactive versions of Spring Security’s components.

THE KEY IDEAS

  • Reactive is a different programming model, not an automatic speed boost. It can be useful for nonblocking I/O or streams, but it adds complexity and is not ideal for every application.
  • Reactor types represent streams. Mono represents zero or one value; Flux represents zero or more. A subscriber consumes the publisher’s signals.
  • Use reactive security types. ReactiveUserDetailsService, ServerHttpSecurity, and SecurityWebFilterChain play roles similar to their servlet counterparts.
  • Endpoint rules use authorizeExchange. Reactive method security and reactive OAuth 2 resource-server support are also available.
  • Avoid blocking the reactive pipeline. Use nonblocking dependencies where possible, and understand that reactive security context propagation differs from a simple thread-local model.
✳

Remember
The security ideas stay similar; the APIs and execution model change for reactive applications.

ILLUSTRATIVE EXAMPLE

A reactive web filter chain; this is not the servlet HttpSecurity API.

Java
@Bean
SecurityWebFilterChain security(ServerHttpSecurity http) {
    return http.authorizeExchange(auth -> auth
            .pathMatchers("/public/**").permitAll()
            .anyExchange().authenticated())
        .httpBasic(Customizer.withDefaults())
        .build();
}

Testing security

01 CHAPTER
CHAPTER 18PDF page 398 ↗

Testing security configurations

Security rules need tests for both allowed and denied requests, not just tests that a controller returns the right data.

THE KEY IDEAS

  • Test authorization separately. @WithMockUser or a mock-user request helper creates a test security context so you can check roles and authorities without repeating a real login in every test.
  • Mock users do not test authentication. Write separate tests for credential checking, login failures, custom providers, or token validation as appropriate.
  • Test both sides of a rule. Check an anonymous caller, a user without the permission, and a user with it. Also test ownership and method-level rules.
  • Exercise browser protections. Test state-changing requests with and without a CSRF token; test allowed and disallowed CORS origins and preflight requests where relevant.
  • Use the right client. MockMvc is useful for servlet applications; WebTestClient supports reactive tests. Run security tests after dependency and configuration changes.
✳

Remember
A passing mock-user test proves a rule, not that real credentials or tokens are valid.

ILLUSTRATIVE EXAMPLE

A MockMvc authorization test; it assumes /reports requires the report:read authority.

Java
@Test
@WithMockUser(authorities = "report:read")
void permittedUserCanReadReports() throws Exception {
    mvc.perform(get("/reports"))
       .andExpect(status().isOk());
}

@Test
@WithMockUser(authorities = "other")
void userWithoutPermissionIsForbidden() throws Exception {
    mvc.perform(get("/reports"))
       .andExpect(status().isForbidden());
}
