Chapter 1 — Introduction

Why concurrency at all? This chapter is the book's argument: threads are an inescapable feature of Java, they buy you throughput, simpler code and responsive UIs — and in exchange they hand you three new classes of bugs: safety, liveness and performance hazards.

Brian Goetz, with Tim Peierls, Joshua Bloch, Joseph Bowbeer, David Holmes & Doug Lea

📖 Pages 1–9 🧩 4 sections · 2 listings · 1 figure ⏱️ ~10 min read 🏷️ Part I — Fundamentals

Chapter in one paragraph

TL;DR — the five things worth remembering

  1. Concurrency exists because of hardware and human nature. Processes were invented for resource utilization, fairness and convenience; threads were invented for exactly the same three reasons, but inside a process.
  2. Threads buy you three things: use of multiple processors (throughput), a simpler sequential-looking model for asynchronous work, and a UI that does not freeze.
  3. Safely hazard: race conditions. value++ is not one operation but three (read, add, write). Without synchronization, two threads can read the same value and produce duplicate results.
  4. Liveness hazards: safety means nothing bad ever happens; liveness means something good eventually happens. Deadlock, starvation and livelock are the ways "eventually" never arrives.
  5. Thread-safety is contagious. Even if you never call new Thread(), Timer, servlets, RMI, Swing/AWT and the JVM itself will call your code from threads you do not own.

1.1A (Very) Brief History of Concurrency

From bare metal → processes → threads: every step was about not wasting an expensive machine.

The sequence-only machine

Early computers had no operating system at all. They ran one program from beginning to end, and that program had direct access to every resource of the machine. Writing for the bare metal was hard, and running one program at a time was a terrible use of hardware that was expensive and scarce.

Processes: isolation with coarse-grained sharing

Operating systems evolved to run several programs at once, each in its own process — an isolated, independently executing program to which the OS allocates resources such as memory, file handles and security credentials. When processes needed to talk to each other, they used deliberately coarse-grained mechanisms: sockets, signal handlers, shared memory, semaphores and files.

⚙️
Resource utilization

Programs must wait for I/O and can do no useful work while waiting. Better to run someone else in that gap.

⚖️
Fairness

Multiple users and programs may have equal claims on the machine. Time-slicing beats "run to completion, then the next one".

🧰
Convenience

Writing several small single-task programs that coordinate is often easier than writing one program that does everything.

The sequential programming model

Each process in an early timesharing system was effectively a virtual von Neumann computer: a memory space holding instructions and data, instructions executed one after another per the machine language semantics, and interaction with the outside world through OS I/O primitives. For every instruction executed there is a well-defined "next instruction". Nearly every language in use today follows this model, so the specification tells you exactly "what comes next" after any action.

The model is intuitive because it mirrors how people work: get out of bed, put on your bathrobe, go downstairs, start the tea. Each of those is itself a sequence of finer actions — and one of them, waiting for the water to boil, is inherently asynchronous. While the kettle heats you can wait, or start the toast, or fetch the newspaper, while staying aware that your attention will soon be needed. The kettle and toaster "know" they are used asynchronously, so they signal audibly when done. The same balance of sequentiality and asynchrony characterises efficient people — and efficient programs.

Threads: concurrency inside a single process

The same three motivations — utilization, fairness, convenience — drove the move from processes to threads. Threads let multiple streams of control flow coexist within a process. They share process-wide resources (memory, file handles), but each thread has its own program counter, stack and local variables. They are the natural decomposition for exploiting hardware parallelism, and most modern OSs schedule threads, not processes — hence the nickname "lightweight processes".

Shared between threads of one processPrivate to each thread
The memory address space — same variables, same heap, so sharing is finer grained than any inter-process mechanism Program counter, stack, local variables
⚠️

The catch, stated in the first page: without explicit coordination, threads run simultaneously and asynchronously. A thread may modify variables that another thread is in the middle of using, with unpredictable results. That single sentence is the whole book.

1.2Benefits of Threads

Used properly, threads lower development and maintenance cost and raise performance.

Threads make it easier to model how humans actually work by turning asynchronous workflows into mostly sequential ones, and they turn convoluted code into straight-line code that is easier to write, read and maintain. They help GUI applications stay responsive, help server applications with utilization and throughput, and even simplify the JVM itself — the garbage collector usually runs in one or more dedicated threads. Most non-trivial Java applications depend on threads for their organization.

1.2.1Exploiting multiple processors

Multiprocessors were once exotic; now even low-end servers and mid-range desktops have several cores, and the trend only accelerates — clock rates are getting harder to scale, so manufacturers add cores per chip instead.

Because the basic unit of scheduling is the thread, a single-threaded program can use at most one processor: on a 2-core machine it leaves half the CPU idle, on a 100-core machine it gives up 99%. A well-designed multithreaded program can execute on many cores at once and improve throughput. Threads also help on a single-processor machine: when one thread blocks on synchronous I/O the CPU would sit idle, but another thread can run — like reading the newspaper while the water boils instead of waiting for it first.

1.2.2Simplicity of modeling

One type of task ("fix these twelve bugs") is easier to manage than five types with competing priorities; context switching between them costs you. Software is the same: a program that processes one kind of task sequentially is simpler to write, less error-prone and easier to test than one juggling many at once. Assigning a thread to each type of task — or to each element of a simulation — gives the illusion of sequentiality and insulates your domain logic from scheduling details, interleaved operations, asynchronous I/O and resource waits.

Frameworks such as servlets and RMI exploit exactly this: the framework handles request management, thread creation and load balancing, and calls your component at the right point in the workflow. The servlet author does not have to think about how many other requests are in flight or whether the socket streams block — the service method can process its request synchronously, as if it were a single-threaded program.

1.2.3Simplified handling of asynchronous events

A server accepting connections from many clients is much easier to write when each connection gets its own thread and may use straightforward synchronous I/O, instead of a single loop multiplexing non-blocking channels. Historically OSes capped threads per process at a few hundred, which is why multiplexed I/O (select, poll) and java.nio exist. Modern OS thread support has improved dramatically — the NPTL package in Linux was designed for hundreds of thousands of threads — so the thread-per-client model is practical far more often than it used to be.

1.2.4More responsive user interfaces

Old GUIs were single-threaded: you either polled for events everywhere (messy and intrusive) or ran all application code through a "main event loop". Any slow code called from that loop froze the interface, because later events could not be processed until control returned.

AWT and Swing replace the main event loop with an event dispatch thread (EDT). Most GUI frameworks are single-threaded subsystems, so the loop is effectively still there — it just runs in a thread owned by the toolkit rather than by your application. Short-lived tasks keep the UI responsive; a long-running task in the EDT (spell-checking a big document, fetching over the network) ruins responsiveness — and worse, the user cannot even cancel it, because the cancel button's event is queued behind the very task it would cancel. Move the long task to another thread and the event thread stays free.

💡

All four benefits are really one idea: threads let you write straight-line, synchronous-looking code while the world stays asynchronous. The cost of that illusion is paid in the next section.

1.3Risks of Threads

A double-edged sword: Java's language support, library support and formal memory model make portable concurrent code possible — and make every mainstream developer responsible for it.

1.3.1Safety hazards

Thread safety is unusually subtle because, without sufficient synchronization, the ordering of operations across threads is unpredictable — and sometimes surprising. UnsafeSequence (Listing 1.1) is supposed to return a unique value on every call. It is perfectly correct single-threaded, and broken multi-threaded.

DON'T DO THIS Listing 1.1 · Non-thread-safe Sequence Generator 
@NotThreadSafe
public class UnsafeSequence {
    private int value;

    /** Returns a unique value. */
    public int getNext() {
        return value++;
    }
}

With unlucky timing two threads call getNext() and receive the same value. value++ looks atomic but is three operations: read the value, add one, write the new value. Both threads can read the same value, both add one, both write — and one increment vanishes. Figure 1.1 shows exactly this interleaving.

Interleaving diagrams like this one always depict time running left to right, one row per thread, and usually show the worst case, to warn against assuming things happen in a particular order. As the book notes in a footnote, the real worst case can be even worse than these diagrams suggest, because of reordering (Chapter 3).

Annotations you will meet all over this book

@NotThreadSafe, @ThreadSafe and @Immutable are custom, documentation-only annotations (Appendix A) that describe a class's concurrency contract; @GuardedBy (Section 2.4) records which lock protects a field. They help three audiences: users can trust @ThreadSafe classes, maintainers know which guarantees must be preserved, and analysis tools can flag violations.

UnsafeSequence demonstrates a race condition: whether the specification is honoured depends on how the runtime happens to interleave operations — which is not a state of affairs you want to ship. Making getNext synchronized fixes it (Listing 1.2), for reasons that occupy Chapters 2 and 3.

THREAD-SAFE Listing 1.2 · Thread-safe Sequence Generator 
@ThreadSafe
public class Sequence {
    @GuardedBy("this") private int nextValue;

    public synchronized int getNext() {
        return nextValue++;
    }
}

Without synchronization the compiler, the hardware and the runtime may take substantial liberties with the timing and ordering of actions — caching variables in registers or processor-local caches where they are temporarily (or permanently) invisible to other threads. These tricks exist for performance and are generally desirable, but they put the burden on you to identify clearly where data is shared across threads. Chapter 16 has the gory details of the JMM; follow the rules in Chapters 2 and 3 and you can skip them.

1.3.2Liveness hazards

Safety is not negotiable. But safety is only half of correctness. In a single-threaded program, an accidental infinite loop means the code after the loop never runs; with threads you get entire new failure modes.

ConcernSloganFailure looks like
Safety "Nothing bad ever happens." Wrong results — corrupted counts, duplicate sequence numbers, half-updated objects.
Liveness "Something good eventually happens." Permanent inability to make progress: deadlock (Ch. 10.1), starvation (10.3.1), livelock (10.3.3).
Performance "…and it happens quickly." Poor service time, responsiveness, throughput, resource consumption or scalability.

If thread A waits forever for a resource that thread B holds exclusively and never releases, A makes no progress. Like most concurrency bugs, liveness failures depend on the relative timing of events in different threads, so they are elusive — they routinely escape development and testing.

1.3.3Performance hazards

A well-designed concurrent application is a net performance win, but threads have real runtime costs:

  • Context switches — the scheduler suspends the running thread so another can run: saving and restoring execution context, loss of locality, and CPU time spent scheduling instead of running.
  • Synchronization — can inhibit compiler optimizations, flush or invalidate memory caches, and create traffic on the shared memory bus. Chapter 11 covers measuring and reducing these costs.

1.4Threads are Everywhere

You do not have to create a thread to be writing multithreaded code.

Frameworks create threads on your behalf, and code called from those threads must be thread-safe. That places a real design burden on developers, because thread-safe classes need more care and analysis than non-thread-safe ones. Every Java application uses threads: when the JVM starts it creates housekeeping threads (garbage collection, finalization) plus a main thread for main().

⏲️
Timer

TimerTasks run in a thread owned by the Timer, not by your application. Any state a task touches must be safe for every other path that touches it — usually achieved by making the shared objects themselves thread-safe.

🌐
Servlets & JSP

The spec requires a servlet to be callable from multiple threads at once. Even a one-request-at-a-time servlet shares ServletContext and HttpSession state with filters and other servlets.

📡
RMI

Remote calls arrive on RMI-managed threads. The same remote method on the same object can be invoked concurrently. Remote objects must guard their own state too, not just state shared with others.

🖥️
Swing & AWT

Swing components such as JTable are not thread-safe. Safety comes from confinement to the event thread; to touch the GUI from elsewhere, hand the work to the event thread.

When a framework introduces concurrency it is usually impossible to confine the concurrency-awareness to framework code, because frameworks make callbacks into application components that in turn touch application state. Thread safety is contagious: it starts with the framework entry point and ripples through every code path that reaches shared state.

🔁

The ripple, in one line: framework thread → your component → shared application state → every other code path that reads or writes that same state.

“It would be nice to believe that concurrency is an ‘optional’ or ‘advanced’ language feature, but the reality is that nearly all Java applications are multithreaded.” — Chapter 1, Section 1.4

1The hazard, in full

RACE CONDITION UnsafeSequence — annotated walkthrough 
@NotThreadSafe
public class UnsafeSequence {
    private int value;

    /**
     * Returns a unique value.
     *
     * Looks atomic, is not. value++ compiles to three actions:
     *   1. read  value      (both threads may read 9)
     *   2. add   1          (both threads compute 10)
     *   3. write value      (both threads store 10 -> one increment lost)
     *
     * The class is correct single-threaded and incorrect multi-threaded.
     */
    public int getNext() {
        return value++;
    }
}

2Reproducing it — a runnable main

Race conditions are probabilistic: a single run may look fine, so loop many times with several threads. When you see two threads receive the same number, or a final count smaller than the number of calls, you have caught it.

DEMO RaceDemo — two threads, many calls 
public class RaceDemo {

    public static void main(String[] args) throws InterruptedException {
        for (int attempt = 0; attempt < 20; attempt++) {
            UnsafeSequence seq = new UnsafeSequence();
            int callsPerThread = 10_000;

            Thread t1 = new Thread(() -> { for (int i = 0; i < callsPerThread; i++) seq.getNext(); });
            Thread t2 = new Thread(() -> { for (int i = 0; i < callsPerThread; i++) seq.getNext(); });

            t1.start();
            t2.start();
            t1.join();
            t2.join();

            int expected = 2 * callsPerThread;
            // getNext() is private about its counter; expose a getter or read the
            // value through reflection/Instrumentation to compare. Typical output:
            //   expected 20000, got 19674  -> lost updates
            System.out.println("attempt " + attempt + ": expected " + expected);
        }
    }
}

In practice, value++ is fast enough that lost updates are easy to miss; that is precisely why the book calls these bugs subtle. Adding a tiny amount of work between the read and the write — or simply running on more cores — makes them far more likely.

3Fix A — the book's answer: synchronized

SAFE Sequence — mutual exclusion via the intrinsic lock 
@ThreadSafe
public class Sequence {

    // @GuardedBy("this"): every read and write of nextValue happens with
    // this object's monitor held. Documentation, not enforcement.
    @GuardedBy("this") private int nextValue;

    public synchronized int getNext() {
        return nextValue++;
    }
}

synchronized makes the read-modify-write atomic with respect to other threads holding the same lock, and it adds the memory-visibility guarantees that stop the compiler, hardware and runtime from hiding the update in a register (Chapters 2, 3 and 16).

4Fix B — the library alternative: AtomicInteger

Chapter 2's pattern: when a class already implements the atomicity you need, use it instead of hand-rolling a lock. No blocking, and the intent is obvious to a reader.

SAFE AtomicSequence — lock-free counter 
import java.util.concurrent.atomic.AtomicInteger;

@ThreadSafe
public class AtomicSequence {
    private final AtomicInteger value = new AtomicInteger();

    /** Returns a unique value; getAndIncrement is atomic, so no lost updates. */
    public int getNext() {
        return value.getAndIncrement();
    }
}

5Same problem, different carrier: the counter servlet

Chapter 1's hazard shows up again in Chapter 2's UnsafeCountingFactorizer, where the shared count is incremented from many request threads. Same lesson, different packaging — which is why the chapter ends with "threads are everywhere."

BRIDGE TO CH. 2 CountingFactorizer — the shape of the problem 
@ThreadSafe
public class CountingFactorizer implements Servlet {

    // One instance serves every request, on many threads at once.
    private final AtomicLong count = new AtomicLong(0);

    public long getCount() { return count.get(); }

    public void service(ServletRequest req, ServletResponse resp) {
        count.incrementAndGet();            // atomic -> no lost counts
        // ... factor the number and write the response ...
    }
}

✓Cheat sheet & self-check

✅
Do

Ask "who else can be in this code right now?" for every field. Prefer existing thread-safe types. Confine mutable state when you can. Annotate your concurrency intent.

🚫
Avoid

Treating read-modify-write as atomic. Assuming interleavings are benign. Long tasks on the EDT or the servlet thread. Waiting on a resource another thread may never release.

🧪
Test like a concurrency bug

Run many iterations, many threads, on more than one core. A passing test proves little; a failing one proves everything.

Five questions the chapter leaves you with

  1. Which of the three benefits (throughput, simplicity, responsiveness) is my application actually buying?
  2. Where is my mutable state, and who else can reach it?
  3. Which operations must be atomic, and are they?
  4. What could stop my program from ever making progress again?
  5. Which framework is already calling me from a thread I did not create?

Notes carried over from the chapter
