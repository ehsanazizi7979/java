⚡ TL;DR — Chapter 1 in 30 seconds

  • Performance is art + science. Science = measurements and rigor. Art = deep knowledge + experience + intuition. This book builds the knowledge that grows into art.
  • Two pillars: (1) tune the JVM itself with flags (JIT, GC, memory), and (2) use the Java platform well in code (language + standard API). You need both — DevOps has erased the old “developers vs. performance team” split.
  • Scope: Oracle HotSpot JDK 8 (8u222) and 11 (11.0.5), both LTS. Flags and defaults are HotSpot-specific and version-specific.
  • Hardware reality: multicore + hyper-threading (4 cores look like 8 CPUs but give ~5–6×), plus VMs and Docker containers that change how the JVM sizes itself (ergonomics).
  • Five principles: better algorithms > less code > don’t fear “premature optimization” when the choice is free > look beyond Java for the bottleneck > optimize the common case.

1. The big idea: performance is art and science (p. 1–2)

Performance engineering looks like magic from the outside — the way a smartphone would look magical to a medieval knight. Oaks’ point is that the “magic” is really deep knowledge applied repeatedly. You cannot shortcut experience and intuition, but you can systematically learn the knowledge that experience is built from. That is the book’s goal.

The knowledge splits into two broad categories:

  • The JVM itself — how it is configured (tuning flags) shapes almost everything about program speed. This is analogous to choosing C++ compiler flags or PHP php.ini settings: familiar, but easy to get wrong.
  • The Java platform — how language features (e.g. threading, synchronization) and standard-API features (e.g. string handling) affect performance. The book treats language and API together for this purpose.

Historically these were separate jobs: developers wrote code, the performance group tuned. Oaks argues that split was never useful — anyone working with Java should understand both how code behaves in the JVM and which tunings help. DevOps is now forcing that convergence anyway.

3. Platforms and conventions (pp. 2–8)

3.1 Java platforms: HotSpot, JDK 8 & 11 (pp. 3–4)

  • What “Java” means here: the Oracle HotSpot JVM + JDK, Java SE 8 and 11. The JDK (not just the JRE subset) is the focus because its tools matter for performance analysis. OpenJDK-derived builds (e.g. AdoptOpenJDK) are treated as equivalent for this book’s purposes.
  • Versions pinned: Java 8 at jdk8u222 and Java 11 at 11.0.5 (current when written). Use at least these — early Java 8 (through ~8u60) lacks major performance features, especially around G1 GC.
  • Why LTS: both releases carry long-term support (Java 8 through at least 2023 via AdoptOpenJDK / extended Oracle support; Java 11 through at least 2022; next LTS expected late 2021). Interim releases (9, 10, 12, 13…) are supported for only ~6 months, so the book focuses on LTS and only peeks at interim features that landed in 11.
  • Other JVMs exist (e.g. Eclipse OpenJ9 via AdoptOpenJDK, other vendor forks). They must pass compatibility tests to use the Java name, but tuning flags are product-specific — concepts transfer, exact flags do not. In this book, “Java” and “JVM” always mean HotSpot.
  • Flags drift: defaults change between releases. The book’s flags are valid for 8u222 / 11.0.5; always check release notes for later updates.

3.2 JVM tuning flags: syntax, ergonomics, and builds (pp. 4–5)

With few exceptions, HotSpot flags come in two shapes:

# Boolean flags: enable / disable
-XX:+FlagName   # enable
-XX:-FlagName   # disable

# Parameterized flags: set a value
-XX:FlagName=something

# Example from the chapter: N is an arbitrary value
-XX:NewRatio=N

# Print every flag with its effective default (see Ch. 3, "Basic VM Information")
-XX:+PrintFlagsFinal

Code 1 — JVM flag syntax as defined in Chapter 1 (p. 4). N / something are placeholders for a real value.

  • Defaults are contextual: they depend on the host platform and other command-line arguments. The automatic adjustment of flags to the environment is called ergonomics.
  • How to see the truth: run with -XX:+PrintFlagsFinal (default false) to dump the effective default for any flag in your exact environment.
  • Product vs. developer builds: the downloadable JVM is the product build. Source builds (debug, developer, …) expose many more experimental flags. The book generally ignores those developer-only flags.

3.3 Hardware platforms: multicore, hyper-threading, and containers (pp. 5–8)

Multicore + hyper-threading

Virtually every machine today is multicore. Each core can run two hardware threads (Intel’s hyper-threading, AMD’s simultaneous multithreading — same thing). The core executes only one thread at a time, but when that thread stalls (e.g. waiting for main memory), the core switches to the other thread instead of wasting cycles.

So a 4-core machine with hyper-threading looks like 8 CPUs to the OS and JVM, but the 8 are not equal: 4 CPU-bound tasks get a clean 4× throughput. The 5th–8th tasks only run during stalls (20–40% of the time), each adding roughly 30%. Net: ~5–6× a single core, not 8×. This matters for GC parallelization (Ch. 5) and thread scaling (Ch. 9).

Software containers: VMs and Docker

  • Virtual machines: a fully isolated OS on a subset of host hardware (e.g. 2 cores / 16 GB carved from a 128-core cloud host). To Java, a VM is indistinguishable from a physical machine — tune it the same way.
  • Docker containers: just a constrained process inside a running OS. Isolation is weaker, and resource limits (CPU, memory) can be set per container.
  • VM oversubscription & throttling: cloud vendors may pack more VMs than physical cores (betting not all are busy) or allow CPU bursts but throttle sustained use. Both hurt performance — but they affect everything in the VM equally, not Java specifically.
⚠ Docker + Java ergonomics trap (pp. 7–8) Many JVM settings (default heap size, GC thread count, some thread pools) are sized ergonomically from machine CPU/memory. In early Java 8 (before update 192), the JVM saw the host’s totals, not the container limit — so it could size the heap larger than the container’s memory and get killed (OOM) when the heap grew. Java 8u192+ and all Java 11 respect container limits. Best fix: upgrade. Workaround on old Java 8: set heap/CPU values by hand (flagged in later chapters).
# Illustrative only — the chapter describes the problem in prose;
# these are the kinds of manual settings old Java 8 needed in Docker.
# Prefer upgrading to 8u192+ / 11, which read container limits automatically.

# Example: container limited to 2 cores / 8 GB on a 4-core / 16 GB host
-Xmx8g              # cap heap to container memory (avoid OOM-kill)
-XX:ActiveProcessorCount=2  # tell GC / pools the real CPU count

Code 2 — Illustrative container-sizing flags. Not quoted from the book; shown to make the ergonomics issue concrete. Exact flags vary by chapter topic (heap in Ch. 5, pools in Ch. 9).

One more Docker note: the rich JDK diagnostic tools (Ch. 3) are often not available inside a container — plan your observability accordingly.

4. The complete performance story (pp. 8–14)

JVM tuning is only part of the picture. This section introduces five outside influences that are at least as important as the flags — and that the rest of the book assumes you keep in mind.

4.1 Write better algorithms (p. 9)

There is no -XX:+RunReallyFast. The JVM can optimize bounds checks and unroll loops, but it cannot turn a bad algorithm into a good one. Oaks’ example: looping an array to find one item will always lose to a hash map, no matter how well the loop is optimized. Algorithm choice dominates micro-tuning.

// Illustrative contrast of the chapter's array-vs-hash-map point (p. 9).
// The book makes this point in prose; code below is our illustration.

// ❌ Linear scan: O(n) per lookup
for (int i = 0; i < items.length; i++) {
    if (items[i].equals(target)) return items[i];
}

// ✅ Hash lookup: O(1) average
Map<String, Item> index = new HashMap<>();
for (Item it : items) index.put(it.key(), it);
Item found = index.get(targetKey);

Code 3 — Illustrative only. The lesson: no JIT optimization rescues the wrong data structure.

4.2 Write less code: “death by 1,000 cuts” (pp. 9–10)

A small, well-written program beats a large, well-written program — in Java specifically because:

  • more code to compile → longer until it runs fast;
  • more objects allocated/discarded → more GC work; more retained → longer GC cycles;
  • more classes to load from disk → slower startup;
  • more code executed → worse cache fit and longer execution.

The trap: every developer adds “just a tiny feature” (often unused). Each costs a few percent. After a few releases you are down 10% — and the creep is hard to reverse, except when a threshold (memory, code cache) trips and tests catch one big cliff. Streamline when you can; be aware of the trade-off every time you add code.

4.3 Oh, go ahead — prematurely optimize (pp. 10–11)

Donald Knuth’s famous dictum — “premature optimization is the root of all evil” (with the fuller context: forget small efficiencies ~97% of the time) — is often misread as “performance doesn’t matter.” Oaks’ reading:

  • What Knuth warns against: algorithmic/design changes that complicate structure for speed, done before profiling proves a large win. Write clean, straightforward code first.
  • What Knuth does not forbid: choosing the better-performing option when two simple, straightforward ways exist. Every line is a choice; if one is free and faster, take it.

The chapter’s logging example is the canonical case. The “bad” version concatenates a string and calls two methods even when the log level is off. The “good” version guards with isLoggable and uses parameterized logging — same readability, no wasted work:

// ❌ BAD — from Chapter 1 (p. 11): work happens even if FINE is off
log.log(Level.FINE, "I am here, and the value of X is "
        + calcX() + " and Y is " + calcY());

// ✅ GOOD — from Chapter 1 (p. 11): no concat, no calls, no array unless enabled
if (log.isLoggable(Level.FINE)) {
    log.log(Level.FINE,
            "I am here, and the value of X is {} and Y is {}",
            new Object[]{calcX(), calcY()});
}

Code 4 — The chapter’s logging example (p. 11), reproduced as short excerpts for study. Note: even IDEs are imperfect here — NetBeans flags the concatenation but its suggested fix still keeps the wasted method calls.

💡 How to apply this Don’t let out-of-context dogma stop you from thinking. The test is: is the faster version just as clean and easy to read? If yes, it isn’t “premature optimization” — it’s good coding. (Ch. 9 revisits this with a benign-looking loop over a vector.)

4.4 Look elsewhere: the database is always the bottleneck (pp. 12–13)

Standalone Java with no external resources: Java performance is (mostly) all that matters. Add a database, a load balancer, a backend system — and the Java tier may be the least of your problems. This book assumes you have already done the holistic analysis (CPU, I/O latency, throughput of every tier) and confirmed Java is the bottleneck worth fixing. That system-level work is not Java-specific and is out of scope here.

Figure 4 — In a distributed system, measure every tier before tuning any tier. Speeding up Java when the database is saturated only adds load and makes the whole system slower.

📖 Anecdote: the bug was in the test harness (p. 12) A customer upgraded an app server and saw requests get slower over time. After ruling out the server itself (and with no database to blame), profiling showed the culprit was Apache JMeter: it kept every response in a list and re-scanned the whole list on each new response to compute the 90th-percentile response time. Lesson: performance bugs can live anywhere in the system — check the newest component first (Occam’s razor), but be ready to look everywhere, including your own test tools.
⚠ The overload paradox If the database (or a CPU-bound server, or a contended lock) is already saturated, making the Java caller faster increases load on the saturated component and can make overall performance worse. Don’t then wrongly conclude the Java improvement was bad — the system was already over the edge. (Ch. 9 shows an extreme JVM-only version of this.)

4.5 Optimize for the common case (p. 13)

Not all performance aspects are equal. Focus where it counts:

  • Profile, then fix the hot spots — the operations taking the most time. (And don’t just stare at leaf methods in a profile; see Ch. 3.)
  • Occam’s razor for diagnosis: simplest explanation first. A bug in new code is more likely than a machine config issue, which is more likely than a JVM/OS bug. Obscure platform bugs exist, but rule out the credible causes first.
  • Fast path for common operations: if most users accept a 10% error margin and few need 1%, optimize the 10% path — even if that slows the 1% path.

5. Chapter summary (pp. 13–14, paraphrased)

Java gives you the features and tools to get the best performance from an application, and this book shows how to use the JVM to end up with fast-running programs. But remember: the JVM is a small part of the overall performance picture. In real environments, databases and backend systems matter at least as much as the JVM. That system-level analysis is assumed done — the book’s job is the Java component.

Equally important is the interaction between JVM and the rest of the system — direct interactions (e.g. the best way to make database calls) and indirect ones (e.g. native-memory use on a shared machine). The chapters ahead address both.

One-paragraph version Learn the JVM deeply (flags, JIT, GC, memory), use the platform well (code, APIs, threading, servers, DB), choose good algorithms, keep code lean, take free performance wins without fear, measure the whole system to find the real bottleneck, and spend optimization effort on the common case. That is the complete performance story.

6. Key takeaways & self-check

✅ Key takeaways

  • Performance = science (measurement) + art (knowledge → experience → intuition).
  • Two pillars: JVM tuning flags and platform best practices — learn both.
  • Book scope: HotSpot JDK 8u222 & 11.0.5 (LTS). Flags are HotSpot- and version-specific.
  • Flag syntax: -XX:+/-Flag (boolean) and -XX:Flag=value (parameterized). Defaults come from ergonomics; inspect with -XX:+PrintFlagsFinal.
  • 4 cores + hyper-threading ≈ 8 visible CPUs but only ~5–6× throughput.
  • Docker ergonomics: pre-8u192 Java 8 ignores container limits (OOM-kill risk). Upgrade to 8u192+ / 11.
  • Algorithms first: no flag fixes the wrong data structure (array scan vs. hash map).
  • Write less code: every addition costs compile time, GC work, startup, and cache.
  • Premature optimization ≠ choosing the free, clean, faster option (guarded logging).
  • Find the real bottleneck across all tiers — including your test harness (JMeter story).
  • Speeding up a caller of a saturated system makes it slower. Fix saturation first.
  • Optimize the common case: profile hot spots, Occam’s razor, fast path for common operations.

🧪 Self-check (try answering before peeking)

Q1. Why does a 4-core hyper-threaded machine not give 8× throughput?

Each core runs one thread at a time; the second thread only fills stall cycles (20–40% overlap). Tasks 5–8 each add ~30%, for ~5–6× total. (p. 6)

Q2. What is ergonomics, and how do you see a flag’s effective default?

Ergonomics = automatic sizing of flags from platform + command line. Run with -XX:+PrintFlagsFinal to dump effective defaults. (p. 5)

Q3. What’s wrong with the “bad” logging line, and what’s the fix?

It concatenates a string and calls calcX()/calcY() even when FINE logging is off. Fix: guard with isLoggable(Level.FINE) and use parameterized {} logging. (p. 11)

Q4. The database is saturated. You make the Java code faster. What happens to overall performance?

It can get worse: faster Java sends more load to the overloaded DB. Fix the saturation first; don’t blame the Java change. (p. 13)

Q5. Knuth says premature optimization is the root of all evil. What does Oaks say it does not mean?

It does not forbid choosing the better-performing of two equally simple options. Only complicating design for unproven speed gains is what to avoid. (pp. 10–11)
